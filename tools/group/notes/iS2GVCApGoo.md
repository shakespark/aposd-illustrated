# Comments: I agree with the problem, not with the solution

- 原帖：https://groups.google.com/g/software-design-book/c/iS2GVCApGoo
- 精读：2026-10-03，读到第 13 条（2023-11-18 ～ 2024-05-26）
- 主题：书里说接口的非形式部分"只能用注释描述"，读者认为单元测试也能、甚至更好；作者承认测试更精确，但坚持注释更好找、更好读。
- 对应：第 12 章 12.1（"好代码自文档化"）/ 第 4 章 4.2（同一句话也出现在这里）/ 第 13 章 13.5（接口注释）/ 第 19 章 19.3（单元测试）/ 第 10 章 10.5（substring 例子）/ 训练场 / 专题 ai-era（末两条）
- 性质：真正的分歧 · 勘误或澄清 · 可改编成训练题的例子
- 优先级：A。这是"测试即文档"这个最常见反方的正面交锋，而且作者在 [7] 里有明确的部分让步和一次认错，值得写进第 12 章的"边界与反方"。

## 读者说了什么（转述）

1. **质疑**（Alexander Biskup，[1]）：引第 12 章的句子——接口的非形式方面（方法做什么、结果的含义）只能在注释里描述——认为注释既不是唯一办法也不是最好的办法。用 `substring(start, end)` 举例：一行注释"包含 end 指向的字符，例如……"，和一个名字就叫"包含 end 指向的字符"的测试，说的是同一件事；但测试还能防回归，有意改行为时也会自动提示不一致。至少对只在一个团队内部使用的 API，测试更好。
2. **从"使用体验"看**（Venkat Dinavahi，[2]）：我要用这个函数时，选项一是去找测试文件——在哪？看哪一个测试？看完能不能明白怎么用？选项二是敲出函数名，注释就弹出来。这位读者明确选后者；测试用来保证行为正确，但替代不了告诉我怎么用的注释。
3. **"完整"才是关键词**（Peter Ludemann，[4]）：接住作者 [3] 里"要完整"这个条件——边界情况一多，注释要么很长，要么难懂；好的测试会覆盖这些边界。列了约十个 substring 的越界/空串/负数调用，说要简洁地描述它们很难。举 cplusplus.com 上 `string::substr` 的文档为例，说它没讲 pos 为负、len 为负等情况。对作者"很多测试只测实现"这句表示不理解。自述在 Google（单元测试文化很强）时，即使文档写得好，也大量依靠单元测试来理解代码，重构或替换实现时尤其如此。结论：写测试时把它当成一种文档，特别是关于边界情况的文档。
4. **只通过公开 API 测**（Artem Shevchenko，[5]）：Google 的原则是只测契约以免测试脆弱（见《Software Engineering at Google》的单元测试一章），这样的测试通常能很好地说明契约。
5. **对例子的纠正**（Ciaran McHale，[6]）：`size_t` 是无符号类型，不可能为负；`substr(-1, 2)` 能编译是 C++ 的隐式转换所致，不是文档的缺陷。所以这个例子选得不好，但不否定 Peter Ludemann 的论点本身。
6. **比较要公平**（Daniel T.，[8]）：是拿好测试比好注释，还是别的组合？好测试按定义就该好读。客观能说的是：测试更精确（英语不如代码精确）；测试只要通过就保证是对的，注释没有这个保证。自己读过不少费解的文档注释，看懂之后发现和函数行为对不上。最后说别陷入二选一——好注释和好测试都要。[11] 又补一句给"不要注释"派：没有人会不读文档就把一个 API 引进自己的代码库。
7. **折中工具**（Paul Becker，[9]）：Python 的 doctest，把测试写进文档里。
8. **短 docstring**（Gregg Irwin，[10]）：Red 语言的做法是 docstring 保持简短，供 `help` 函数显示，主要用于速查和传达意图——意图是测试说不出来的。
9. **题外**（Ciaran McHale，[12]；Steven Rose，[13]）：[12] 说每个人都觉得"比我写得少是失职，比我写得多是浪费"；回顾 man page、Javadoc/Doxygen 都是在降低写文档的成本，下一个能进一步降低成本的工具（也许基于 AI）会流行。[13] 认为 AI 的价值不在生成大量没人读的文档，而在交互式地回答关于代码的问题；但能解释代码的 AI 多半也能直接给出解法，于是这种对话的价值也有限。

## 作者的回应

作者发了两条（[3]、[7]）。

**[3]：站在 Venkat Dinavahi 一边，但留了口子。**
- 承认"也许有注释以外的方式来描述接口"，但对这种方式提了条件。原话：
  > "it needs to be complete and easy to find and understand"（John Ousterhout，[3]）
  
  这比书里"只能用注释"的措辞松了一点。
- 认为测试不符合"好找、好懂"：一个方法的很多测试只是在测实现而不是 API，只想了解 API 的人得先读这些测试，然后才发现它们与自己无关。

**[7]：回应 Peter Ludemann，部分让步。**
- **让步**：同意（好的）单元测试可能比文字注释给出**更精确**的接口规格。原话：
  > "I agree that (good) unit tests may provide a more precise specification of a module's interface than textual comments."（John Ousterhout，[7]）
- **坚持**：问题在于测试难读得多。就拿 `string::substr` 那段文档说，文字描述虽不简单，仍比一组单元测试好读——读测试的人还得先了解测试框架、mock 设施等等。所以模块的使用者从文字描述里更快拿到需要的信息。
- **新的类比**：有人会出于同样的理由（精确）主张给 API 写形式化规格，但作者认为那在实践中同样会难用得多。也就是说，作者把"测试当文档"和"形式化规格"归为一类：精确，但不好用。
- **认错**：承认 [3] 里"很多测试只测实现不测 API"的措辞草率并道歉，同意每个测试都在以某种方式使用被测模块的 API。作者原本想说的是：可能有好几个测试都对应 API 的同一部分，看其中一个就够了，让人读许多个是额外负担。但作者接着说，想过之后自己也不完全确定这一点成立。

**没有让步的**：作者没有说书里那句话错了，也没有说会改。立场是"测试可以更精确，但注释仍是使用者最快、最容易得到信息的地方"。

**作者没有回应的**：[8] 之后的全部内容——Daniel T. 的"测试保证正确而注释不保证"（即准确性，而不只是精确性）、doctest、短 docstring、AI——作者都未再回复。特别是"准确性"这一点，直接对着书里 12.3"注释会过时"那一节，作者在这里没有接。

## 挂到站点哪里

- 第 12 章"边界与反方"（12.1 处）：新增一条"测试能不能替代接口注释"。结构：读者论点（测试精确、防回归、保证不过时）→ 作者的让步（更精确）→ 作者的坚持（好找、好读；形式化规格的类比）→ 未决点（准确性；作者自己撤回了一半的"多个测试对应同一处 API"）。最后可以给出读者里的折中：doctest、"只通过公开 API 测"、两者都要。
- 第 4 章 4.2：书里同一句话的另一处出现，加一个指向上面那条的链接即可。
- 第 13 章 13.5：Peter Ludemann 的"边界情况一多，注释要么长要么含糊"是对接口注释的真实压力；可配合 10.5——书里正是用 Java 的 `substring` 讲"把越界定义掉"，如果接口这样设计，那十个边界情况的大部分一句话就能说清，注释和测试之争就缓和了。这层联系是我的归纳，串里没人这么说，上站时要标明。
- 第 19 章 19.3：加一句"作者认可测试可以是更精确的规格，但不认为它能替代文档"，指回第 12 章。
- 训练场：一道题——给一个 `substr(pos, len)` 式的 C++ 函数（原创），分别给出 (A) 三四行接口注释、(B) 八个测试用例的名字和断言。问：使用者想知道 `pos == size()` 时会怎样，从哪份材料更快得到答案？实现者要换内部实现时更依赖哪份？让读者自己体会两者分工。

## 待核实

- Peter Ludemann 说 cplusplus.com 的 `substr` 文档没覆盖"负数"情况；Ciaran McHale 说那是因为参数是无符号的 `size_t`。后者是 C++ 的常识，但按规矩仍标为读者说法；改编训练题时应以 C++ 标准对 `std::string::substr` 的规定为准，自己核对。
- Alexander Biskup 的示例里 `"apple".substring(0, 2) == "app"`（含 end）是这位读者自己设定的语义，与 Java 的 `substring`（不含 end）不同，引用时别混。
- Artem Shevchenko 所引《Software Engineering at Google》"只通过公开 API 测试"的出处没有查。
- Peter Ludemann 关于在 Google 靠单元测试理解代码的说法是个人经验。
