# Inquiry on Pass-through Methods from "A Philosophy of Software Design"

- 原帖：https://groups.google.com/g/software-design-book/c/CTt_XD_ZekA
- 精读：2026-10-03，读到第 3 条（2024-08-17 ～ 2024-08-26）
- 主题：A 用到 B 的一些方法，C 同时要用 A 和 B；该让 C 直接依赖 A 和 B 两个模块，还是让 A 把 B 的方法转一道、使 C 只依赖 A。
- 对应：第 7 章 7.1（透传方法）；次要：第 2 章（依赖）
- 性质：勘误或澄清 + 可改编成训练题的例子
- 优先级：C。作者的回答干脆，但就是 7.1 节的直接应用，站点第 7 章已有同一结论的更细材料（2026 年 "Tell, Don't Ask" 那一段）。唯一稍新的是"依赖的功能总量不变"这个数法，适合出一道选择题。

## 读者说了什么（转述）

Yaowen Zhang（[1][3]）：

1. 抽象地问：模块 A 需要 B 的某些方法，模块 C 需要 A 和 B 两边的方法。是让 C 直接接入 A 和 B，还是让 A 提供对 B 的透传方法、C 只依赖 A？两种做法对模块化和可维护性各有什么影响？
2. 得到回答后说明自己原先的想法：让 C 只依赖 A，似乎能把与 B 的交互"抽象掉"，减轻开发 C 的人的负担。接受作者意见后，这位读者把缺点总结为 A 的职责变多、间接依赖带来隐藏的复杂性（这是读者自己的归纳，作者没有这样说）。

## 作者的回应

作者只有 [2] 一条。

- **直接从 C 调用 A 和 B。**
- 理由一：把 B 的方法在 A 里反映成透传方法，会多出一批不提供任何新功能的接口，增加整个系统的复杂性。
- 理由二（一个数法）：设 C 用到 A 自己的 X 个方法和 B 的 Y 个方法。让 C 依赖 A 里的 X + Y 个方法，和让 C 依赖 A 的 X 个加 B 的 Y 个相比，没有任何好处。原话："The functionality that C depends on is the same in both cases."（John Ousterhout）

也就是说，作者不把"依赖的模块个数"当作要压低的量；要看的是依赖的功能有多少、接口总数有多少。这与 2026 年"the ideal world"那一串里"模块的个数不等于依赖的条数"是同一个意思（站点第 2 章已收）。

没有涉及的：如果 A 转交时确实多做了事（换了抽象、加了约束、藏住了 B 的某些细节），结论会不会变。书里 7.2 节（接口重复何时可以接受）回答了这一点，作者在这里没有重复。

## 挂到站点哪里

- 第 7 章：与已有内容重复，不需要新段落。可在 7.1 小节或已有讨论组块里加一句作者的数法："C 依赖的功能在两种做法下一样多，透传只是多造了接口。"
- 训练场：适合出一道选择题（原创 C++ 场景，例如 `ReportService` 同时需要 `OrderStore` 和它底下的 `Clock`）。选项：A. 让上层只依赖一个模块，由它转交；B. 直接依赖两个；C. 把两者合并；D. 引入一个 facade。解析用作者的数法，并说明什么时候 D 才成立——facade 提供了不同的、更简单的抽象，而不是原样转交（对应 7.2、7.3）。
- 第 2 章：不需要。
