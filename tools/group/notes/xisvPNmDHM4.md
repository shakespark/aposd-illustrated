# Note on Wrappers and Pass-Through Methods

- 原帖：https://groups.google.com/g/software-design-book/c/xisvPNmDHM4
- 精读：2026-10-03，读到第 4 条（2019-06-13 ～ 2019-06-14）
- 主题：读者指出书里批评透传方法和包装类时漏了两种合理的情况（包第三方类、把多个第三方部件粘成一个整体）；作者同意，并说这本书取的是理想化的视角。
- 对应：第 7 章 7.1（透传方法）、7.3（装饰器 / 包装类）；次要：第 3 章（不可能事事战略）、第 21～22 章（规则怎么用）
- 性质：勘误或澄清（作者承认有例外）
- 优先级：B。作者的两句话很短，但有一句是对全书定位的自述（"理想化视角，现实里规则有时得弯一弯"），站点上没有；另外第二版 7.3 节末尾恰好有一段"包装类偶尔合理"的话，例子正是外部类，可以把这一串和那段话对上。第 7 章已有三块讨论组内容，这条应当并进去而不是再开一块。

## 读者说了什么（转述）

1. **两种合理的包装**（Will Duquette，[1]）：
   - 要扩展一个第三方库的类：既不能改它，继承又不明智或根本做不到。这时只有两条路——原样使用，把不便转嫁给所有使用者；或者包一层做成需要的样子，并接受一定数量的透传方法。
   - 把若干第三方部件粘成一个连贯的整体，例子是 Tk 的 megawidget（由多个基础控件拼成的复合控件）。这也免不了一些透传。
   - 同时说明：书里的例子是学生包自己写的类，那确实有问题；对 Java 流库的批评这位读者也不反对。
2. **语言的限制**（Peter Ludemann，[3]）：Java 和 C++ 里"什么都包一层"的啰嗦写法，是语言本身的限制或缺少好的重构工具造成的。Python 里属性用普通的点号访问，类的定义可以事后用 `@property` 把属性换成方法调用，使用处不用改；Common Lisp 也可以，印象中 Smalltalk 也行。Python 里有少量运行时开销，静态类型语言可以做到零开销。
3. **建议**（Will Duquette，[4]）：本来就没指望作者不同意；但认为如果出第二版，这两种情况值得写上一两句。

## 作者的回应

作者只有 [2] 一条（整段回复，已对照 full.txt）。

**让步**

- 任何设计规则都有例外。读者举的两种情况，作者都同意：不包的替代方案比包更糟。

**对全书定位的自述（书里没有这么直说）**

> "APOSD takes a somewhat idealistic view, describing what would make sense in a perfect world."（John Ousterhout，[2]）

- 作者接着说：现实世界有约束，所以有时规则得弯一弯；并顺手举了另一个例子——不可能总是做到完全战略式。

作者没有回应 Peter Ludemann 关于语言特性的说法，也没有回应 [4] 里"第二版加一两句"的建议。

## 挂到站点哪里

- 第 7 章"边界与反方"：已有"讨论组 · 作者补充：透传方法有时是别处的问题"等三块。把这一条并进那一块或紧跟其后，两三句即可：
  - 作者 2019 年同意的两种例外：包不能改也不便继承的第三方类；把几个第三方部件组合成一个整体。共同点是**你改不了被包的那一方**。书里学生项目的例子之所以是红旗，是因为两边的类都是自己的，本可以重新划分职责。
  - 这给了一个好用的判别问法：透传方法出现时，先问"两边的代码我都能改吗"。能改，就按 7.1 节处理；不能改，包装是较小的代价。
- 第二版 7.3 节末尾有一段说包装类偶尔合理，例子是接口不能修改的外部类需要适配成应用里的另一种接口，并说这种情况很少见。这与 Will Duquette 的第一种情况基本一致，可以在站点上并排指出。**但不能写成"作者因为这一串而加了这段话"**——没有第一版文本可对照（见待核实）。megawidget 那种"组合多个部件"的情况，第二版没有写。
- 第 22 章或第 21 章（**目前都没有讨论组材料**）：作者那句"理想化视角"的自述很适合放在全书收尾处，提醒读者把书里的规则当成方向而不是判据。第 3 章（"不可能事事战略"）也可交叉引用。这是这一串对空白章节的贡献，篇幅一句话。
- 训练场：可出一道判断题。两段都含透传方法的代码（原创 C++）：一段是自己写的两个类之间的转发，一段是包一个不能改的第三方类并补上线程安全或错误翻译。问哪一段是红旗、哪一段可以接受，为什么。
