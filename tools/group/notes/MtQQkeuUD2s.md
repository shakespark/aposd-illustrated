# Process to arrive a good design that separates general & special purpose code

- 原帖：https://groups.google.com/g/software-design-book/c/MtQQkeuUD2s
- 精读：2026-10-03，读到第 14 条（2023-04-26 ～ 2025-01-11）
- 主题：怎样的过程才能把通用代码和专用代码分对——先设计还是先写乱再重划边界；作者答"先想、别卡住、做两个差别很大的方案、准备好迭代两三轮"，提问者一年半后回来写了实践心得。
- 对应：第 11 章（设计两次）；第 6 章（6.1 适度通用、6.6 把专用代码往上推）与第 9 章 9.4；第 3 章（持续的小投资）；次要涉及第 15 章（先写注释 / 先写用法）、第 16 章；中途跑题到 DSL、代码生成、GUI 工具箱历史
- 性质：仅作背景 · 真正的分歧（很轻：提问者的"先做出来再抽取"与 6.1 的倾向不完全一致）
- 优先级：B，作者只有一条回复，但给了书里没有的具体数字（一个 API 通常要两到三轮）和停止前期设计的判据；提问者 [13] 的回访是不错的读者实践材料。中间一半篇幅是跑题和自我推介，没有可用内容。

## 读者说了什么（转述）

1. **提问**（Venkat Dinavahi，[1]）：常遇到九成通用、一成专用的代码，比如一个文档查看器，大部分通用，少部分只为自家的专有文档格式服务。道理上知道该把通用部分分出去，实际上总是分错；想预先把 API 定好，又陷入分析瘫痪。问：是接受第一版必然错、先写乱再重划边界，还是走预先设计的流程，或者介于两者之间？
2. **先问"怎么事先知道是九比一"**（Daniel T.，[3]）：如果事先就知道哪些是通用的，定 API 并不难；不知道的话只能边写边模块化。这位读者的两条规则：把副作用与逻辑分开；把功能与功能分开。[5] 用写作类比：功能跑通只是初稿，之后至少再过一稿、评审、再一稿。
3. **业务逻辑层与基础层的变化节奏不同**（Simon Frankau，[7]）：业务逻辑需求变得快，底层变得慢而且每次动作大；所以让日常业务改动不需要动底层，是很大的效率收益。底层一旦掺进业务特有的假设，就成了隐蔽的耦合。这位读者的做法是先问"假如有任何趁手的工具可选，我会怎么解这个业务问题"，再去造或选那套工具；经验是大项目最后几乎都长成了 DSL。
4. **提问者的回访**（Venkat Dinavahi，[13]，实践约半年后）：
   - 通用代码抽取出来比预先写出来容易：先画个粗略架构，把东西做出来，知道了真实需求再抽通用层；凡是试图预判通用设计的，通常都做成一团乱。
   - "先写你希望有的那段代码"：先写下这个库要怎么被使用，反复推敲这个用法（这位读者提到"README 驱动开发"）。自认以前在设计上投入不足，尤其是没花足够时间把接口做深、把复杂性推进实现里。
   - 可以反复问自己的几个问题：真的需要这个吗？作为使用者为什么要操心这件事？怎样会让用起来更省事？有没有现成的设计可借鉴？
   - 设想这个库在应用的其他部分或另一个应用里会怎么被用，以此看清通用与专用的边界。
5. **对回访的补充**（Paul Becker，[14]）：同样可能卡在设计阶段迟迟进不了实现；便宜的原型可以在低风险下暴露那些"其实行不通"的想法。还引了丰田生产方式里"先彻底手工做一遍，再上机器"的说法来类比"先做再抽取"。
6. **跑题部分**：Ciaran McHale [2][10] 介绍基类/框架回调等常规手段，然后用很大篇幅讲自己的 Config4* 配置库、代码生成工具和未完成的书稿，[10] 再讲 curl 式的字符串指令接口、用配置文件描述对象如何创建和接线（X Toolkit、Spring）；Gregg Irwin [6][8][9] 用剧本结构和叙事打比方；Brent Welch [11] 回忆从 SunTools 到 Motif 手册越来越厚、而 Tcl/Tk 把样板代码压进 C 层之后写界面快了很多。[12] 已删除。这些与书的关系很弱。

## 作者的回应

只有 [4] 一条，简短但具体。

- **坦白（书里没有这么直白）：** 做出模块划分得当的系统很难，作者说自己这么多年了也几乎从来没有一次做对。
- **三条建议：**
  1. 尽量事先想清楚，但别陷进分析瘫痪。**停止的判据（新说法）：** 当不再冒出会影响设计的新想法时，就该动手实现了。
  2. 实现过程中一定会发现问题，没人能在动手前看清一个设计的全部后果，要准备好重新设计。**具体数字（新说法）：** 作者自己通常要迭代两到三轮——一轮大改，再加一两轮小改——才能把一个 API 调到合适。
  3. 初始设计时拿出两个差别很大的方案，比较各自的利弊能学到很多。（这就是第 11 章，没有新内容。）
- **补充：** 迭代是关键；照这样做仍然可能很吃力，但反复做下去经验会长，到达满意状态会越来越快。原话："It typically takes me 2-3 iterations (one major, plus 1-2 more minor ones) to get to a sweet spot for an API."（John Ousterhout，[4]）

作者没有回应提问者 2025 年的回访，也没有评论 DSL、代码生成等跑题内容。没有让步或争论——这条是经验分享。

## 挂到站点哪里

- 第 11 章页：补"作者在讨论组里说的实际节奏"——设计两次只是起点，之后通常还要两三轮迭代；以及"什么时候停止前期设计"的判据。正好回应读者常有的疑问"设计两次会不会变成分析瘫痪"。
- 第 6 章页"边界与反方"：Venkat 的实践结论"通用层是抽取出来的，不是预判出来的"，与 6.1 的"一开始就做得适度通用"放在一起对照。注意两者未必冲突（6.1 说的是接口适度通用、功能只满足当前需要），页面上要把这层区别讲清，别写成读者推翻了书。

- 第 3 章页（可选）：作者"几乎从没一次做对"这句自白，作为"战略式编程不等于一次设计到位"的旁证。
