# What purpose do factories serve?

- 原帖：https://groups.google.com/g/software-design-book/c/46heiunvGug
- 精读：2026-10-03，读到第 12 条（2021-12-21 ～ 2022-11-14）
- 主题：这一串是作者自己发问——重回 Java 后在 gRPC 代码里看到大量工厂、builder，不明白比构造函数好在哪；读者给出若干理由，作者接受了其中一个（运行时才能确定具体类型），否定了两个。
- 对应：第 4 章（浅模块、classitis、接口数量本身是成本）；第 8 章（把复杂性往下拉：宁可类的实现复杂些，也别让使用者复杂）；第 7 章（多一层要多一份抽象；7.5 的透传在 [2][6] 被顺带提到）；专题 clean-code（仅因设计模式文化，关系较远）
- 性质：真正的分歧 · 可改编成训练题的例子 · 仅作背景
- 优先级：B，书里没有讨论工厂模式，这一串能看到作者怎样用自己的标准当场检验一个流行模式，并且有一处明确的"被说服"；但讨论的是 Java 生态的习惯，对本站 C++ 读者是间接材料。

## 读者说了什么（转述）

**结构说明：** 发帖人就是作者，所以下面"读者说了什么"是读者对作者提问的回答，"作者的回应"包括开帖和三条跟帖。

1. **配合依赖注入、少传单例**（Hunter Herman，[2]）：唯一想用工厂的场合是——构造某类对象时，一部分参数是全系统共用的单例，一部分是每个实例各不相同的；工厂可以让构造点只填后者，不必把单例一路传到构造点。这位读者说自己最后嫌麻烦没用，并说明这只是猜测。
2. **构造函数的三个麻烦**（Marko Ristin-Kaufmann，[3]）：(a) 构造函数抛异常时对象状态让人糊涂；(b) 构造函数太重容易出现"半初始化"的 bug——在对象没初始化完时调用了要求完全初始化的方法；(c) 为测试而注入依赖，是书本上最常见的理由。
3. **工厂要和别的设施配合才有价值**（Ciaran McHale，[4]）：单纯给构造函数包一层薄工厂没有任何好处。这位读者的用法是：启动时建一张"类型名 → 工厂函数"的哈希表，再解析运行时配置文件，按其中的"类型.标识"逐项找到工厂、把配置交给它去构造对象。作用类似 Spring 式的依赖注入，但不需要反射，所以在 C++ 里也能用；代价是工厂函数要手写。
4. **《Effective Java》第 1 条**（Andrey Satarin，[5]）：静态工厂方法相对构造函数的好处——有名字；不必每次都新建对象；可以返回任意子类型；返回类型可以随代码演化和入参不同而变化。这位读者也认为作者描述的 gRPC 情况确实复杂。
5. **gRPC 的具体原因：Java SPI**（Akshay Shekher，[8]）：gRPC 想通过 Java 的 SPI 机制自动发现 NameResolver 之类接口的实现，而 SPI 只支持无参构造函数的实现类。让 DnsNameResolver 本身只有无参构造函数会把它搞复杂，于是库里引入一个通过 SPI 暴露、带无参构造函数的抽象工厂（Provider），由它来创建真正的实例。结果是每个实现都要配一个 Provider。这位读者的总结：这套元对象设计是 Java 生态的工具限制一路演化出来的；并说明"目标是让真正的对象好用、系统可配置，没说达到了"。
6. **不可变性文化与 DI 习惯**（kristjan，[9]，自称在 Google 写过 Java 后转到 C++ 团队）：Google 的 Java 圈子很执着于不可变性和《Effective Java》里的做法；Java 没有 C++ 的 `const` 那样的支持，于是每个类变成两个版本——可变的 `Foo.Builder` 和字段全是 final 的 `Foo`，protobuf 的 Java API 是典型，字段有几十个时构造函数会很难用。另外 DI 框架在 Java 界无处不在，鼓励把"怎么创建对象"与对象本身分开；凡是看到 `FooProvider` 基本就是 DI 的习惯。这位读者说换到 C++ 之后回头看，对自己当年造的那些 provider、注解、绑定和 builder 感到抱歉。
7. **为多态做准备**（Björn Jürgens，[10]）：Fowler《重构》里"以多态取代条件表达式"的例子——父类 Bird 和几个子类，工厂方法 `createBird` 读一个 JSON 对象后返回具体子类的实例，此后代码只用父类型。没有工厂方法，这类重构会麻烦得多。
8. **多步创建**（Dimitar Dimitrov，[12]）：工厂/builder 可以封装多步创建，避免半成品对象被应用代码看到；需要获取多个资源、任何一步失败都要全部释放时也适用。作者没有再回复。

## 作者的回应

四条：[1]（开帖）、[6]、[7]、[11]。

- **[1] 提出问题，同时亮明标准：** 作者说离开 Java 去写了近十年 C++，现在在 gRPC 的 Java 实现里工作，到处是工厂却看不出用处：它们增加了额外的接口，让系统更复杂，好处不明显。gRPC 里还有专门创建工厂的 builder，以及创建 builder 的对象；作者估计有上千行代码，唯一的工作就是最后构造出某个底层类型的对象。原话："What does a factory do that can't be done more simply with a constructor for the underlying class?"（John Ousterhout，[1]）
- **[6] 追问 Hunter：** 引入工厂之后，不是还得把工厂传到构造点吗？是不是说传一个工厂比传一堆参数简单？（没有得到回答。）
- **[7] 逐条回应 Marko：**
  - 对 (a)：**不接受。** 构造函数抛了异常，就没人拿得到那个半成品对象，它内部是否一致不成问题。
  - 对 (b)：**不接受，并给出替代做法（书里没有这个例子）。** 如果是指构造函数只做基本初始化、其余选项靠后续方法设置，那么有比工厂更简单的办法：让任何要求初始化完成的方法置一个内部标志，此后再调初始化方法就抛异常；或者更好——把类设计成选项随时可改而无害。两种做法都让类的实现复杂一点，但对使用者比引入工厂简单。这是"把复杂性往下拉"的一次现场应用。
  - 对 (c)：**原则上接受，但认为不适用于眼前的代码。** 为测试而注入说得通，可 gRPC 的工厂结构复杂到很难想象能在测试里插进去替换。
- **[11] 被 Björn 的例子说服（明确的让步）：** 作者说没读过《重构》，但理解这个场景——"构造"不仅要造出对象，还要根据数据（JSON 内容）决定它的具体类型；真正的构造函数做不到，因为调用构造函数之前就得知道类型。作者认可工厂方法在这里合理，并且是唯一可行的选择，还感谢了这个例子。原话："I see how a factory method makes sense in this situation, and is really the only viable alternative."（John Ousterhout，[11]）

作者没有回应 Ciaran 的"哈希表 + 配置文件"、Andrey 引的《Effective Java》四点、Akshay 的 SPI 解释、kristjan 的文化解释和 Dimitar 的多步创建。所以**不能说作者接受了这些理由**，只能说作者明确接受的是"运行时选择具体类型"这一种。

## 挂到站点哪里

- 第 4 章页，"classitis / 浅模块"小节：加一个旁注"工厂是不是浅模块？"——作者的检验方法（它做了什么构造函数做不到的事）加上作者认可的唯一场景（类型要到运行时由数据决定）。再列出读者给的其他理由，标明"作者未表态"。
- 第 8 章页：作者在 [7] 的替代做法是"把复杂性往下拉"的好例子——宁可在类里加一个标志或把选项做成随时可改，也不让每个使用者多学一个工厂。
- 专题 clean-code / 设计模式相关的反方材料：kristjan [9] 的亲历（从 Google Java 转到 C++ 后的反思）可以转述为一条读者证词；Akshay [8] 的 SPI 说明则提醒读者，有些"过度设计"是平台限制逼出来的，不全是品味问题。
- 训练场：一道 C++ 判断题（原创代码）：给三段代码——(1) 只是转调构造函数的 `WidgetFactory::create()`；(2) 根据配置字符串返回不同子类的 `makeShape(const Config&)`；(3) 分两步初始化、靠工厂保证顺序的类——问哪个工厂是浅模块、哪个有存在理由、(3) 有没有不用工厂的改法。
