## 读者说了什么（转述）

Mohammad Razavi（[1]）代表小组提的六条，说明自己未必准确转述了别人的意见：

1. **4.7 节"几乎每个文件 I/O 的使用者都要缓冲"缺证据**：Java 有数百万开发者、用途各异，这个断言并不显然，建议给出更具体的依据。
2. **与开闭原则的张力**：书里建议给 FileInputStream 加一个构造函数或方法来关闭/替换缓冲，这位读者觉得和开闭原则相左，想知道作者怎么看 SOLID。
3. **7.5 透传变量**：书里说 context 远非理想、也没找到更好的办法。读者问是不是语言限制了解法，Common Lisp 的动态作用域特殊变量会不会更好。
4. **5.6 节的 getParameter / getIntParameter**：同意"返回内部 Map 的引用"不好，但替代方案也别扭——难道每种类型写一个方法？这些方法不是太浅了吗？能不能返回内部结构的只读视图（像 Python 字典的 `.keys()`）？
5. **对 Clean Code 的批评是否公允**：组里有人认为书里没有准确反映 Martin 的意思，或两人其实没有分歧。例证是 12.6 节引的那句话带着两个"如果"，说明 Martin 并不认为注释一概是坏的。
6. **圈复杂度**：书是否认为圈复杂度很高的长函数仍可以是合理的深方法？组里有人特别担心这种函数难测。

其他读者：

- Peter Ludemann（[3]）：C 标准库默认带缓冲（按文件类型有两种，另有不缓冲），允许覆盖；自己听过对 C 的很多抱怨，但没听过抱怨它的缓冲选择。
- Steven Rose（[4]）：Java 标准库面对"合理默认值"时几乎总选"做得少"，动机是保持依赖干净（读文件的类不该依赖缓冲）。这个目标本身不坏，后来 JDK 能拆成模块可能也靠它；问题出在把这条依赖纪律用到了包以下的层次，同一个包里的类永远在一起，分那么细没有收益。这位读者把它归为执行问题，不是原则有错。
- Steven Rose（[5]）：对作者点名 DIP 表示意外，称 DIP 是让超大代码库可以忍受的主要原则；但它不是纯技术原则，要管理层配合，按架构来划分团队（康威定律）。自述只在一家公司见过它真正发挥作用。

## 作者的回应

作者 1 条：[2]，按读者的编号逐条作答（不是插话式，已对照 full.txt）。

**让步**

- 第 1 条：承认最好能有数据支撑"几乎所有 Java I/O 使用者都要缓冲"，但手头没有，也看不出怎么去拿。同时仍然坚持这个判断，理由是：如果错得离谱，早该有不用缓冲的 Java 开发者来反驳了，至今没有。
- 第 4 条：承认一堆返回不同类型的 get 方法"相当浅"，说读者提的问题有意思。

**坚持**

- 第 4 条：看不到好的替代——没有这些方法，使用者就得自己写转换。对"返回只读视图"没有正面评价。
- 第 5 条：与 Martin 在注释上的看法"非常不同"。依据是 Martin 自己写的代码几乎没有注释，而那句话里的前提条件（语言表达力足够）在今天的语言里并不成立。
- 第 6 条：不太熟悉圈复杂度，但没发现任何复杂度的数值指标特别有用。方法实现让人觉得复杂、又能找到干净的拆法（拆出的子方法深、能分开理解），就拆。至于测试：长方法也许难测一点点，但自己很少在写干净的单元测试上遇到困难，不管方法长短。

**书里没有的新说法**

- 第 2 条（SOLID）：直说没发现 SOLID 很有用。有的看起来相当随意（点名 DIP），看不出和管理复杂性有什么关系；有的可能有用但容易做过头，以 SRP 为例——有的 SRP 拥护者会主张一个方法里只能有一个控制语句。原话："SRP only captures one half of the tradeoff"（John Ousterhout），即只说了变小的好处、没说代价，所以更愿意用"深度"，因为它把取舍包含在内。
- 第 4 条：**C++ 里可以用按返回类型模板化的 get 方法**。使用者只需学一个接口，却得到转换成很多类型的功能。书里 5.6 节给的是 `getParameter` + `getIntParameter`。
- 第 5 条：以 Clean Code 第 145 页的 `isLeastRelevantMultipleOfLargerPrimeFactor` 为例批评"用长名字代替注释"，两条理由：名字几乎读不懂（"relevant"指什么？"larger"是大多少？），不如写一两句清楚的英文；以及"You have to retype the entire documentation for the method every time you invoke it!"（John Ousterhout）。

**没有回答的**

- 第 3 条：说自己不熟悉 Common Lisp 的动态作用域变量，无法回答。
- 第 2 条里开闭原则与"加一个关缓冲的构造函数"是否冲突，没有正面回答。
- Steven Rose 对 DIP 的辩护（[5]）和 Java 库设计动机的解释（[4]）。
