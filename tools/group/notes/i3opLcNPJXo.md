# Some thoughts about "Classitis"

- 原帖：https://groups.google.com/g/software-design-book/c/i3opLcNPJXo
- 精读：2026-10-03，读到第 3 条（2019-02-19 ～ 2019-02-19）
- 主题：读者同意模块要深，但认为深模块的内部仍应拆成短小的方法和子类，改代码时才不必读完几千行；作者表示同意，条件是拆出来的东西各自独立、各自够深。
- 对应：第 4 章 4.6（类过多症）；第 9 章 9.7（拆分与合并方法）；专题 clean-code
- 性质：勘误或澄清
- 优先级：C。与已有内容重复：作者"不偏爱长方法、先做深再拆、拆出来的要独立"的立场，第 9 章页和 clean-code 专题页已经从另外几串整理过。新的只有两句话（见"挂到站点哪里"）。

## 读者说了什么（转述）

1. **深模块内部也该短**（Silas，[1]）：设想一个几千行、对外只有一个简单方法的深模块。接口是抽象，内部结构对使用者无所谓；但要改它内部时，是愿意读一个只有几个方法的 3000 行的类，还是先读公开方法的 5 行实现——它告诉你主功能分三步，各由一个私有方法实现，这些方法再去协调各自的子模块（类）——然后只钻进与改动有关的那一步？这位读者明确偏好后者。
2. **代码总量变多，但要读的变少**（[1]）：承认这种结构总代码更多，可改动时需要读、需要记在脑子里的更少；多层抽象把人引到要改的地方。样板代码可以靠语言减少（举 Kotlin 对 Java）。并认为这不增加系统的整体复杂性，因为全在主模块这个黑盒里面。
3. **对 Java I/O 例子的看法**（[1]）：问题在于那些类全都暴露在 API 上，而不在于功能在内部被拆成了多个类。
4. **收尾**（Silas Graffy，[3]，同一位读者换了邮箱）：完全同意作者的回复。拆成三个小方法的唯一理由，是读者只需读调用方法和其中一个；如果还得读另外两个，就是越拆越糟；如果读一个方法的接口和读它的实现差不多费劲，那它就不算抽象。承认自己是把"类过多症"那段误读成了"偏爱大类"，而原意是：宁要较大的类，也不要一堆互相依赖、单独看不懂、单独没价值的小类。

## 作者的回应

作者 1 条：[2]（整段回复，已对照 full.txt）。

**同意的**

- 保持短小有价值，前提是短的东西也足够深。顺序是：先做出深的类，让使用者省事；然后在合理范围内尽量分解它的实现。读者把一个大方法分成三个小方法的例子，作者说多半是个好主意。

**加的条件**

- 小方法要相对独立，每个都能单独读懂。如果依赖多到不看其他方法的实现就看不懂其中任何一个，拆开多半更糟：相互依赖的东西被放到了不同的地方，没法一眼看全，只能来回翻。
- 短方法如果是浅的（接口和实现一样复杂），就没有增加任何价值。

**这一串里特有的两句**

- **算"要读多少代码"时，接口注释也得算进去**：使用一个方法就得读它的接口，所以接口注释是要读的"代码"的一部分。这是对读者"拆了以后要读的更少"的直接修正。
- 口号式的总结："As short as possible while staying deep"（John Ousterhout），并补充方法可以既相当短又仍然深；"不惜代价求短"则不是好主意。

## 挂到站点哪里

- **与已有内容重复**：第 9 章"边界与反方"的讨论组块已写"Ousterhout 至少三次否认偏爱长方法"、"先做出深的接口，实现太长时再找拆法，拆出来的也要深、彼此独立"；clean-code 专题页"关于方法长度"一节有 2019-01、2019-04、2023-01 等出处。这一串（2019-02）是同一立场的又一次表述，可以作为出处补进那一节的括号里。
- 值得新增的只有两点，各一句话即可：
  - 第 9 章或专题页：算阅读量要把接口注释算上——拆出一个方法，读者省下的是方法体，多读的是它的接口说明；两者差不多时就没赚。
  - 第 4 章 4.6：读者最后那句对"类过多症"的复述很准确，可以用来澄清常见误读（书不是说类越大越好）。这是读者的话，作者只是在前一条里表达了同样的意思。
- 读者关于 Java I/O 的看法（毛病在暴露、不在内部拆分）与作者后来（2022 年）给出的"缓冲做成内部复用的模块"是同一个方向，第 4、9 章页里已经有后者，不必再挂。
