# Determinism and immutability as a way of reducing complexity

- 原帖：https://groups.google.com/g/software-design-book/c/TW3Uy0Ro8qQ
- 精读：2026-10-03，读到第 5 条（2022-05-16 ～ 2022-06-08）
- 主题：把代码从"有状态、可变"挪到"纯函数、不可变"为什么会显得更简单；两位读者借 Yourdon 与 Constantine《Structured Design》里"信息的可获得性"来解释。
- 对应：第 2 章（2.2 认知负担、2.3 隐晦）；次要：第 18 章（代码应该一目了然）
- 性质：仅作背景
- 优先级：C。作者没有发言；两位读者的讨论有条理，但没有落到书里任何具体例子上，也没找到反例。只有一个小对比（`game.roll()` 与返回三个骰子值）勉强可用。

## 读者说了什么（转述）

1. **Venkat Dinavahi（[1]）**：把能抽的逻辑抽成纯函数后代码更好懂；理由是确定性——同样输入得同样输出，不必去想系统当前处于什么状态，出了问题把同样的输入再喂一遍即可。这位读者把代码想成两个世界：有状态可变的（更复杂）和不可变确定的（更简单），从前者往后者挪通常会变简单。
2. **Paweł Badeński（[2][3]）**：同感，但说不出第一性原理，于是搬出《Structured Design》（[3] 更正：作者是 Yourdon 和 Constantine 两人）。那本书认为影响语句复杂度的有三项：信息的量、信息的可获得性、信息的结构。这位读者的看法是：可变与不可变两种写法信息量差不多，不可变的可获得性更好。又提醒那本书说的"信息"包括注释、外部文档、约定俗成，所以有时可变写法反而更简单——比如不可变方案要把大量数据传来传去，而面向对象可以把数据收在一个带可变状态的类里。
3. **Venkat（[4]）**：接受"可获得性"的说法，但不认同那个例子：自己所在团队后端用函数式语言，常见做法是让一个数据结构流过一长串函数，写起来费事些，但每一步都能把状态打出来看。希望有人给出"可变写法确实更简单"的例子。
4. **Paweł（[5]）**：承认举不出这样的例子。补充《Structured Design》把可获得性分成四项（直接/间接、本地/远处、标准/出人意料、明显/隐晦），并做了两组对比：
   - `counter.increase()` 与 `newCounter = increase(counter)`：信息量相同，后者输出就在调用处，略胜。
   - `game.roll()` 与 `[d1, d2, d3] = roll(game)`：前者要记的东西少，但什么都不返回，读者得进去看它到底改了什么；后者信息多却都在眼前。这位读者判后者胜。
   - 还注意到：自己一向只从"读代码不运行"的角度讲复杂度，Venkat 则从"能重跑、能打日志"的角度讲，两者都算可获得性。

## 挂到站点哪里

- 第 2 章：最多加一句旁注——读者用"信息离使用处有多远"解释纯函数为什么好懂，这与 2.3 节"隐晦"（重要信息不明显）是同一件事的另一种说法。不值得单独成段。
- 第 18 章（目前没有讨论组材料）：能补的只有 `game.roll()` 那个"返回 void 的方法让人不知道它改了什么"的小例子，可改写成原创 C++ 例子放进"让代码不显然的写法"里。分量很轻。
- 训练场：可出一道小题——同一操作的"原地修改、返回 void"与"返回新值"两种签名，问各自把什么信息留在了调用处、什么藏进了实现。属于可有可无。
