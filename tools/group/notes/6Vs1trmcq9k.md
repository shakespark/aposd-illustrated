# Eliminating pass-through variables by creating objects up front

- 原帖：https://groups.google.com/g/software-design-book/c/6Vs1trmcq9k
- 精读：2026-10-03，读到第 10 条（2022-09-24 ～ 2022-10-03）
- 主题：7.5 的透传变量除了 context 对象还有没有更好的解法：一位读者提出"在 main 里预先把对象一层层构造好"，被作者否定；另一位读者提出"绑定在调用栈上的作用域式 context"，作者称之为接近最优。
- 对应：第 7 章（7.5 透传变量、图 7.2）；次要涉及第 5 章（信息隐藏：main 不该知道调用链）、第 2 章（不明显的依赖）
- 性质：真正的分歧 · 可改编成训练题的例子
- 优先级：A，作者在这里明确称赞了一个书里没有的方案，又给出了否定"构造函数注入"的具体理由，两点都能直接补进第 7 章页。

## 读者说了什么（转述）

1. **方案一：预先构造对象链**（Filip Lange，[1]）：开头先说这本书改变了自己多年按 Clean Code 写小方法的习惯。然后引 Misko Hevery 2008 年的一篇文章，提议把书里的 m1/m2/m3 各包进一个类：C3 的构造函数拿 `cert`，C2 的构造函数拿 c3，C1 的构造函数拿 c2，`main` 里依次构造 c3、c2、c1 再调用 `c1.m1()`。代价是代码变多，好处是每个类只拿到直接依赖，`cert` 不再穿过中间层。这位读者还提到 2018 年那场讨论只谈了 DI 框架，没谈"把依赖传给构造函数"这个一般做法（见 xYzAzHcB630，其中 Tomasz Masternak 在 [13][14] 给过几乎相同的代码）。
2. **方案二：作用域式 context**（Paul Becker，[2]，Python）：一个 `CertContext` 类，用类级别的私有变量保存当前证书；进入 `with CertContext(cert):` 时把旧值存起来、换成新值，退出时恢复；最底层的 m3 调 `CertContext.getCert()` 取值，不在任何 context 内就抛异常。中间的 m2 完全不知道证书的存在；内层还可以再套一个 `with` 临时覆盖。这位读者称之为"半个单例"——全局变量与 context 对象的混合体，生命周期绑定在调用栈上。
   - 这位读者自己指出的代价：必须记住哪些函数要求"在 context 内被调用"。如果把这个要求写进每个函数的接口（比如声明"可能抛 NoCertContextError"），调用者也得跟着声明，透传只是从参数挪到了接口的另一处。
3. **对方案二的质疑**（Gregg Irwin，[6]）：(a) m3 及以下的任何代码都能往上"够到"这个 context，建 context 的人不知道谁在用，时间久了容易共享过度；构造函数注入在这一点上更能防住。(b) 它造成跨层的隐式耦合，日后更难看清。结论是 7.5 列的几种办法都成立，选哪个要看场合。**作者没有回复这一条。**
4. **同类先例**（David Hess，[7]）：Flask 的 application/request context 就是这个模式——一个全局引用，运行时按线程解析到各自的 context，线程内可以用上下文管理器临时压入新的 context。这位读者说自己商用多年，很稳。
5. **方案三：内部函数**（Paul Becker，[8]，C#）：把 m2、m3 写成 m1 内部的局部函数，直接捕获 m1 的 `cert` 参数，顺带把 m2、m3 藏了起来。同一条里这位读者也坦白：方案二的主要弱点是自己其实从没在实际项目里用过。Gregg Irwin [9] 补充：有的语言没有内部函数；相关代码都住在一起时这招很好，分散在各处时就不适用。
6. **收尾的直觉**（Paul Becker，[10]）：透传变量多半说明设计时漏掉了一条必要的依赖，或者想把一条跨很远的依赖伪装成局部的；更好的办法是直接连上，或者改抽象把问题消掉——有时就意味着本来分开的东西不该分开。

## 作者的回应

两条，[4] 和 [5]。

- **[4] 否定方案一，理由具体：** `main` 里那几行构造代码破坏了抽象——主程序现在必须知道 c1 调 c2、c2 调 c3。只要 c1 或 c2 的内部结构变了（比如 c2 改成先调 c4、再由 c4 调 c3），主程序就得跟着改；调用链越深，主程序要知道的依赖越多。其他办法虽然各有毛病（包括透传参数本身），但至少 c1 的内部对 `main` 是完全隐藏的。作者的总判断：这个问题大概没有完美解，每种办法都有缺点。
  - 这是书里没有的论证：7.5 没讨论构造函数注入。它同时也回答了 2018 年那一串里 Tomasz 的同款代码。
- **[5] 称赞方案二：** 原话："I like your approach! ... it seems to me that it provides a near-optimal solution to the problem"（John Ousterhout，[5]）。作者给的理由：只有真正关心这份信息的两方——顶层的提供者和底层的使用者——需要知道它；中间层还能临时覆盖 context，这对测试很有用。作者说第一反应是这就是这个问题的正解，并认为别的语言也能实现，比如 C++，大概只需要构造函数、析构函数、静态变量和静态方法。
  - **保留：** 作者说自己还在消化，需要再想想有没有弱点，并请大家来挑毛病。之后 Gregg 挑了（见上第 3 条），作者没有再发言，所以这个称赞停留在"第一反应"。

没有明确说书会因此修改。

## 挂到站点哪里

- 第 7 章页，7.5 小节：这是本串的主要落点。在图 7.2 的四种办法之后加"讨论组里的第五、第六种"：
  - 构造函数注入（预先接线）——附作者的否定理由：接线代码把调用链泄漏给了 `main`。
  - 作用域式 context——附作者的称赞、Gregg Irwin 的两条质疑、Flask 的先例，并写明作者只给了初步意见。
- 第 7 章"边界与反方"：Paul Becker [10] 的观点——透传变量可能是"不该拆开的东西被拆开了"的症状，和第 9 章接得上。
- 训练场：一道 C++ 多选对比题（原创代码）：同一个 `cert` 透传问题给出四种写法——逐层传参、全局变量、RAII 作用域守卫（构造时换入、析构时恢复）、main 里预先接线——让读者指出每种写法"谁被迫知道了不该知道的事"。RAII 版本要用 `thread_local`，并在解析里说明原因。
- 项目 / 专题 ostep（可选）：如果重构项目里有全局配置或日志句柄的透传，可以拿作用域守卫做一次对照。

## 待核实

- 作者说 C++ 版只需要静态变量即可。静态变量在多线程下是所有线程共用的；书里 7.5 自己也提醒 context 有线程安全问题，David Hess 描述的 Flask 做法是按线程解析的。训练题里若写 C++ 版，需要自己验证 `thread_local` 的写法，以及异步/协程场景下"绑定调用栈"是否还成立——这些串里没人讨论。
- Paul Becker 的 Python 代码用的是类变量（[2]），同样不是线程安全的；这位读者也承认没在实际项目中用过（[8]）。"接近最优"目前只是作者的第一印象加一个未经实战的示例。
- David Hess 对 Flask 实现的描述（[7]）是读者的说法，引用前对照 Flask 文档。
- Filip Lange 提到 Jannik Spiering 在 2018-12-08 发过类似建议而没人回（[1]）——不在我负责的串里，未核对。
