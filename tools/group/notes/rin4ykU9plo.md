# 4.7 Examples: Java and Unix I/O (p. 26) feedback.

- 原帖：https://groups.google.com/g/software-design-book/c/rin4ykU9plo
- 精读：2026-10-03，读到第 7 条（2019-05-31 ～ 2022-11-14）
- 主题：4.7 节 Java I/O 的例子（打开文件读序列化对象要建三个对象）批评得对不对——缓冲该不该默认、ObjectInputStream 独立成类有没有道理、装饰器分层的替代方案是什么。
- 对应：第 4 章 4.7；次要：第 7 章（装饰器，7.3）、第 6 章（通用性）、第 20 章（性能）
- 性质：真正的分歧 + 勘误或澄清 + 可改编成训练题的例子
- 优先级：A。作者明确承认例子里有一半"更有争议"，并在 2022 年给出了书里没有的替代设计（把缓冲放到流来源的下面）。这是书里被引用最多的例子之一，值得把这次修正写上站点。

## 读者说了什么（转述）

1. **代码写法不典型**（Artem Shevchenko，[1]）：书里把三个对象各自赋给变量，实际写法通常是嵌套构造、不留中间变量；这样书里"前两个对象打开后再也不用"那句话就不成立了。
2. **ObjectInputStream 独立是合理的**（Artem，[1][3]）：同意缓冲应当默认开启；但 FileInputStream 不会读序列化对象没什么不对。ObjectInputStream 是在任意 InputStream 之上加序列化能力，底下可以是压缩流、内存流、网络流，正是书里说的"较通用"的模块。
3. **两组数字**（Artem，[3]）：自己测了创建 100 万个对象、带与不带 BufferedInputStream 各 10 次，平均差约 5%，认为是噪声，短命小对象的 GC 开销可忽略。又称在 Google 代码库里，构造 FileInputStream 的地方大约是构造 ObjectInputStream 的 20 倍，而 ObjectInputStream 只有约 20% 建在 FileInputStream 之上。据此认为两个类各有独立价值、都算深，建议 4.7 节只保留缓冲那一点。
4. **对象总是要存在的**（Peter Ludemann，[4]）：换一种实现，这些对象照样存在，只是可见性不同；C 的 `setvbuf()` 也未必是更好的 API。还提醒：操作系统自己也缓冲，用户态缓冲主要是为了少做系统调用；不该把缓冲当成提升性能的万能粉到处撒。
5. **替装饰器分层辩护**（Dimitar Dimitrov，[6]，2022）：三层各管一件事——来源可以换成管道、网络、生成器；缓冲策略可以换；最上层可以换成 zip 或 JSON 反序列化。java.io 的根是 InputStream，根应当保持简单。若在 InputStream 里默认缓冲，会给管道流、以及假定有背压的自定义实现带来麻烦；做成默认关闭的可选功能，复杂度又和现在的装饰器方案一样。

## 作者的回应

作者共 3 条：[2][5][7]。

**让步**

- [2] 同意中间变量可以省掉，说明自己用变量只是为了把发生的事写清楚。
- [5] 明确承认："I agree that my complaint about ObjectInputStream is more controversial."（John Ousterhout）即 4.7 节里"FileInputStream 不能读序列化对象"这半句批评，作者自己认为站得没那么稳；缓冲才是更大的问题（[2] 已这么说）。
- [7] 同意 Dimitar 的前提：缓冲与数据来源基本正交，逼每种来源各自实现一遍缓冲是坏主意。

**坚持**

- [2] 省掉变量不解决根本问题：仍然创建了三个对象，仍然得构造一堆浅对象；代码短了一点，不会更快。
- [2] 看不出把 ObjectInputStream 从 FileInputStream 分出去的好处：它重复了后者的许多 API，而且用户更不容易发现这项功能。作者反问分开的好处是什么。（之后在 [5] 承认此点有争议，但没有撤回。）
- [5] 关注点主要不是执行效率，而是**对使用者的复杂性**；同时仍认为多余的对象确实有性能代价（比如增加 GC 开销）。

**书里没有的新设计**

- [7] **把缓冲放到流来源的下面，而不是上面**："I'd suggest layering the buffering *under* the stream sources"（John Ousterhout）。做法是单独写一个缓冲类，供每一种流来源在内部直接使用。这样既保留了 Dimitar 要的灵活性（缓冲实现只有一份，与来源正交），又不要求绝大多数用户知道缓冲的存在。作者说相信这能做得干净且高效，但没有给出代码。

书里 4.7 节原来给的方案是"默认带缓冲，另给一个构造函数或方法来关闭/替换"，只说了接口长什么样；[7] 第一次说了实现上怎么组织才不至于让每个来源重复造缓冲。

作者没有回应的：Artem 的两组数字；Peter Ludemann 关于 OS 缓冲和 `setvbuf` 的话；Dimitar 提到的管道流/背压问题（[7] 的方案是否解决它，作者没展开）。

## 挂到站点哪里

- 第 4 章 4.7 对应的小节："边界与反方"里加一段——
  - 这个例子其实是两条批评：缓冲不默认（作者坚持，读者也大多同意）；序列化单独成类（作者承认更有争议）。读书时只取前一条即可。
  - 装饰器方的最好论据（Dimitar：三层各自可替换；Artem：ObjectInputStream 是通用模块）。
  - 作者的折中设计：缓冲作为内部部件放在来源之下。配一张"上面叠一层 vs 下面垫一层"的对比图。
- 第 7 章装饰器一节：同一个例子可以交叉引用，说明"装饰器让使用者自己组装"与"把组装做进模块内部"的取舍。
- 训练场：很适合出一道设计题。用原创的 C++ 场景（比如文件、管道、内存三种字节来源 + 缓冲），给出"调用方自己套缓冲装饰器"的版本，要求改成"缓冲对调用方不可见、但实现只有一份"，并讨论什么情况下需要留一个关闭缓冲的口子（交互式管道、背压）。
- 第 20 章可顺带一句：作者在这里把"复杂性"放在"对象创建开销"之前。
