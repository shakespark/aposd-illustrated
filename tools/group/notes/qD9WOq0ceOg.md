# Single Responsibility Principal

- 原帖：https://groups.google.com/g/software-design-book/c/qD9WOq0ceOg
- 精读：2026-10-03，读到第 7 条（2020-07-17 ～ 2022-02-07）
- 主题：第 4 章批评的 Java I/O（读一个文件要建三个对象）是不是单一职责原则（SRP）的产物；作者怎么看 SRP。
- 对应：第 4 章 4.6（类过多症）、4.7（Java 与 Unix I/O）/ 专题 clean-code / 第 9 章（9.7、9.8）/ 第 19 章 19.3（单元测试）
- 性质：真正的分歧 · 勘误或澄清
- 优先级：A。书里完全没提 SRP 和 SOLID，而这是读者最常拿来对照的原则；作者在这里先后两次表态，第二次比第一次温和，两次合起来就是一份可以直接引用的"APOSD 对 SRP 的立场"。

## 读者说了什么（转述）

1. **提出解释**（匿名，署名 Articulate Source Code，[1]）：猜测 Java 那套"三个类各建一个实例"的设计背后是 SRP。认为"接口简单"和"单一职责"在不同场合各有道理（比如简单的方法更好测）；想两者兼得可以加一个外观（Facade）——例如一个"给文件名、返回对象集合"的函数；代价是多一层间接。
2. **测试角度的反方**（Chris Jerdonek，[3]）：复杂函数即使好测，也很难靠目测确认重要的边界情况都测到了；测试用例一多，也难以组织得让后来的人对覆盖情况有整体把握。所以这位读者常把复杂函数在内部拆成小函数，对小函数测边界，这样不必都经由大函数去测。
3. **推到极限**（Brent Welch，[4]）：SRP 推到极限是行不通的——总得有东西把功能组合成有用的整体。每种组合都算一个新"职责"、一个新类吗？一个类把 5 个类组装起来算不算违反？难道要为各种组合再造 5! 个类？如果被组装的某个部件对系统别处毫无用处、又很琐碎，它该不该单独成类？这位读者自己说这是极端化的说法，但造一堆做不了多少事的小类并不能隐藏复杂性。
4. **SOLID 弊大于利**（Jeff Doolittle，[5]）：完全赞同作者 [2] 的话，认为 SOLID 给了教条者打压别人的弹药，增加的含糊多于清晰；引 Dan North 的 CUPID 文章（称 SOLID 每一条都是错的）。
5. **替 SRP 辩护**（Robin Winslow，[6]）：那篇文章是先有耸动标题再找理由，最后其实承认其中三条原则没问题。SRP 仍然是好原则，前提是"单一职责"要**从使用者的角度**来理解：一个函数、类或模块在使用它的人看来应当是一个内聚的目的；如果它让人困惑，就想想它是不是在处理属于不同领域的事。SOLID 都该当作带着分寸去考虑的事项；有人拿它当棍子打新人，问题在那个人。并说作者那句"任何原则都不该走极端"其实就够了。

## 作者的回应

作者发了两条，相隔一年半，**口气有明显变化**，要一起看。

**[2]（2020-07）：否定性较强。**
- Java 的类过多症很可能就是过分热心地遵循 SRP 的结果；在作者看来，这正说明 SRP 大概不是一条好的设计原则。原话：
  > "to me, that is evidence that the SRP probably isn't a good software design principle"（John Ousterhout，[2]）
- 关于"简单方法更好测"：当然，但你会得到多得多的要测的方法，所以可测性上是不是净赚并不清楚；作者自己没觉得给相当复杂的方法写测试有什么困难。
- 一般性论证：所有强调"把单个东西做小/做简单/做短"的设计方法，问题都在于会产生**大量**这样的东西，每个都有自己的接口；所有接口累积起来的复杂性让系统变复杂，哪怕每个个体都简单。思考复杂性要在系统层面（什么让整个系统最简单），而不是单个实体层面。

**[7]（2022-02）：同意 Robin Winslow，立场收窄。**
- 如果用得合理，作者对 SRP 没有意见。比如类的方法和特性之间有内聚性通常是好事，这听起来和"单一职责"差不多。
- 但用得太狂热或太微观就会失效：比如把"单一职责"理解成一个类只增加一个特性、或一个方法只做一个决定——作者认为这两种理解都是错的。
- 总的定位：不会把 SRP 放在自己设计原则清单的靠前位置，理由两条——(a) 它没有触及应对复杂性的核心（用了 SRP，为什么我的系统整体上更简单、更好管理？）；(b) 它容易被误读、误用。原话：
  > "I think there are better ways of thinking about software design that address complexity more directly (such as having simple interfaces)."（John Ousterhout，[7]）

**变化在哪**：[2] 说的是"SRP 大概不是好原则"；[7] 改成"合理使用没问题，只是不重要且易被滥用"。作者没有明说自己在收回 [2]，但 [7] 以"我同意 Robin"开头，实际上是把批评对象从 SRP 本身缩小到了对 SRP 的微观解读。

**书里没有的**：整段都是。原书文本里检索不到 SRP、SOLID、Single Responsibility。4.6 批评的是"类应该小"的流行观点，没有点名 SRP；这里作者亲口把两者连了起来（用词是"很可能"，不是断言）。"为什么遵循它我的系统就更简单？"这个反问，可以当成检验任何设计原则的通用问题。

**作者没有回应的**：Chris Jerdonek 关于"复杂函数的边界覆盖难以目测确认"的具体论点（[3]）——作者只在 [2] 里泛泛说过测复杂方法不难，之后没接；Brent Welch 的极限论证（[4]）；Facade 方案（[1]）。

## 挂到站点哪里

- 专题 clean-code：新增一小节"APOSD 怎么看 SRP / SOLID"。站点目前没有任何地方提到 SRP。内容：作者的两次表态（标明年份和口气变化）；Robin Winslow 的"从使用者角度看的单一职责 = 内聚"；Brent Welch 的极限论证；Chris Jerdonek 的测试角度反方。写的时候不要只引 [2] 那句否定，否则会把作者的立场说得比实际更极端。
- 第 4 章 4.6 / 4.7：在 Java I/O 例子旁加一条旁注——读者猜这是 SRP 的产物，作者说"很可能"；并引"每个都简单、但接口总量让系统复杂；要在系统层面看"这段话，它是 4.6 论证的一个更明白的说法。读者 [1] 提的 Facade 也可以带一句：书里 4.7 对 Java I/O 的批评其实就是"缓冲应当是默认的"，与加 Facade 的想法方向一致，但作者未评论 Facade。
- 第 19 章 19.3：一组小的正反方——作者"方法小则要测的方法多，可测性未必净赚" vs Chris Jerdonek"大函数的边界覆盖难以检查，所以内部拆小函数来测"。
