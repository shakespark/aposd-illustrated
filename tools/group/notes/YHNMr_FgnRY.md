## 读者说了什么（转述）

1. **提问**（Steven Newton，[1]）：如果物理块号和逻辑块号是不同类型，编译器不让互相赋值，那个 bug 还可能出现吗？这对应"基本类型偏执"（Primitive Obsession）这个坏味道和 Ward Cunningham 的 Whole Value 模式。这位读者认为这等于把一类错误定义掉，也减轻了注释负担。但也承认会走过头——类型泛滥——而且没有现成的判据；举了自己团队的争论：年龄该建 `Age` 类型还是用整数（系统需要算某人在未来某天的年龄）。
2. **"实现起来简单" vs "用起来简单"**（Ciaran McHale，[3]）：程序员倾向选前者。例子：配置文件里 `timeout = 1209600`，要拿计算器才看出是两周的秒数；解析器若支持 `timeout = 2 weeks` 就友好得多。这位读者在自己的配置解析库里做了"数字 + 单位"的支持。同样的取舍在粗粒度上也有（给 DSL 设计专门语法，还是硬塞进 XML/JSON）。建议是：有意识地做这个设计选择，别默认选"好实现"。
3. **Parse, Don't Validate**（Dan Cross，[4]）：引 Alexis King 的文章——用类型把不变式固定下来，值能被构造出来本身就证明约束成立。举自己的例子：一个引导加载器的虚存实现里，虚拟页地址和物理页帧地址是不同类型，且带页大小对齐约束，映射函数只接受配对的类型，于是"把 2M 大页映到 4K 页""虚拟地址映到虚拟地址"之类的错写不出来。也说这是需要经验和品味的地方，线不好划。
4. **用注释代替类型**（Paul Becker，[5]）：魔数就加注释写明"两周，单位秒"；`block` 也可以在声明处、方法说明里注明是物理块还是逻辑块，不必建硬类型。
5. **整数的接口太宽**（Steven Newton，[6]）：整数带着加减乘除乘方全套运算，块号的平方有什么意义？类型的接口应该由"对块号有意义的操作"来定义。[7] 又讲了一个项目经历：日期时间以多种格式的字符串在系统里到处传，到处解析和校验，大量精力花在修这些地方。
6. **单位放进名字，或者干脆用 Duration**（Steven Rose，[8]）：反对 [5] 的"注释里写单位"——变量出现的每一处都需要知道单位，而注释只在声明处，所以应叫 `timeoutSecs`；更好的是用库算（Java 的 `Duration.ofDays(14)`），最好直接让变量就是 `Duration`，由用的人去取秒或毫秒。同一条还指出 Parse-Don't-Validate 的边界：有些约束是对象自身的（出生日期不能在未来），有些取决于它所处的环境（不能比父母年长）；后者理论上可以再造一个 `FamilyTree` 类型来承载，但真实系统里给每条规则都找一个"家"并不现实，硬套会增加而不是减少复杂性。
7. **回应**（Dan Cross，[9]）：既然有 `Duration` 这样的类型，把单位编进名字就是浪费了类型系统；单位只在值产生和被消费的边缘有意义，中间的代码把它当不透明值即可，这样表示法和大部分逻辑解耦。又说 [8] 对 Parse-Don't-Validate 的批评纠结在面向对象里"校验放哪个类"，没抓住要点：要点是把校验的复杂性集中在"解析器"一处，之后不必再校验；解析本身可以很复杂。同意过度使用会造成无用的复杂性，何时用靠判断。

## 作者的回应

作者只发了一条（[2]），两句话：

- 同意：如果两个变量类型不同，那个 bug 会好找得多。
- 保留：和提问者一样担心造出一大堆"本质上都只是整数"的类型；并且认为**事先很难预料哪些整数该单独成类型、哪些不该**。原话：
  > "it might be difficult to predict ahead of time which integers should be separate types and which shouldn't"（John Ousterhout，[2]）

**注意，这不是让步**：现有的书（第 2 版）14.1 末尾本来就写着"更好的做法是给两种块定义不同的类型，使其不可能互换"。提问者像是没注意到这一句（或读的是没有这句的版本，见待核实）。所以这一条里书上没有的只有那句保留意见——"类型泛滥"和"难以事先判断"——书里讲到这个例子时没有提这个代价。

之后关于 Parse-Don't-Validate、单位命名、`Duration` 的讨论，作者都没有参与。

## 挂到站点哪里

- 第 14 章 14.1 的讲解处加一条"读者问答"：名字 → 类型是书里已经给出的升级路径；作者在讨论组补充的代价是类型泛滥、且难以事先判断。再列三种手段的对比（都是读者提的）：注释写明（Paul Becker）、单位/含义写进名字（Steven Rose）、单独类型（Steven Newton、Dan Cross），以及 Dan Cross 的"单位只在边缘有意义"。
- 第 10 章：把"用类型让错误写不出来"作为"把错误定义掉"的近亲手法提一句，并附 Steven Rose 的边界——依赖上下文的约束不一定能找到合适的类型来承载。
- 训练场：两道题的素材。
  - `timeout = 1209600`：给四个版本（裸数字 / 加注释 / `timeoutSecs` / `std::chrono::seconds` 或 `std::chrono::weeks`），问各自在"声明处""使用处""跨函数传递时"能不能看出单位。C++ 有 `std::chrono`，正好对口。
  - 物理块号 / 逻辑块号：用 C++ 写两个强类型包装（原创），让读者体会"编译器替你拦住"与"类型数量增加"的取舍；可接 Steven Newton 的"块号需要哪些运算"。
