# Surface of a class

- 原帖：https://groups.google.com/g/software-design-book/c/TQABoaV0rQA
- 精读：2026-10-03，读到第 3 条（2021-05-20 ～ 2021-05-22）
- 主题：一个类公开接口很简单、内部却有许多短小的私有方法，它算不算深；作者回答算，并说公开接口简单比内部接口简单更重要，但两样可以都要。
- 对应：第 4 章 4.4～4.5（深模块、浅模块）；次要：第 9 章 9.7～9.8；专题 clean-code
- 性质：勘误或澄清
- 优先级：B。只有三句话，但把一个常见的误读讲清楚了（"深"看的是类的公开接口，不是里面每个方法的长短），而且作者明确给了公开接口与内部接口的优先顺序；站点第 4 章和专题 clean-code 的讨论组材料里都还没有"公开接口与内部方法谁优先"这一条（专题页已有的是"我并不偏爱长方法""每多一个方法就多一个接口"等，角度不同）。

## 读者说了什么（转述）

Khaja Minhajuddin，[1]：

- 觉得"表面积"不好理解。书主张类要深不要浅；那么一个类如果公开 API 很简单（也许只有两三个方法），但有很多私有方法，而且这些私有方法都很短（5～10 行），它是不是仍然算深？
- 自己的理解：公开 API 是类的表面，分布在所有公开和私有方法里的全部代码是类的深度。问这样理解对不对。

[3]：表示这个回答讲得通，并感谢作者建了这个讨论组。

## 作者的回应

作者只有 1 条：[2]，整段回复，三层意思：

- **同意**：一个类即使有一堆浅的私有方法，只要公开 API 简单、实现的功能多，仍然可以算深。
- **排了优先级**：让类的公开 API 简单，比让类内部的 API 简单更重要。
- **但不必二选一**："But, why not have both?"（John Ousterhout，[2]）建议的顺序是：先定义一个好的、深的公开 API；实现它的时候，再尽量避免不必要的浅的内部方法。

作者没有直接评价读者那个"公开 API 是表面、全部代码是深度"的说法是否准确，只是在同意的那句里换了一个表述：深度取决于"实现了多少功能"，而不是代码量。这与作者在别的串里说过的"实现更长不等于更深"（站点第 4 章已用）一致。

## 挂到站点哪里

- 第 4 章讲深／浅模块的小节：在已有的"讨论组 · 作者补充：深度是用来讨论的，不是用来测量的"一块里加一条——深度先看类的公开接口；内部满是小私有方法的类仍然可以是深的；但作者认为内部也值得做深，顺序是先公开接口、后内部方法。
- 专题 clean-code：这一条正好落在两本书的分歧线上。把方法拆得很小，如果拆出来的都是私有方法，类对外的深度不受影响，受影响的是读这个类实现的人——所以作者把它排在第二位，而不是说它无所谓。可以在专题页"讨论组里的补充 · 关于方法长度"一节加一句。另一串（yHsxTAAqP9g）的笔记里有读者 Artie Shevchenko 的同向概括（接口简单比实现短小重要），目前没有用到站点上；要用的话以作者这一句为主。
- 第 9 章 9.7：可交叉引用一句，不必展开。
- 训练场（可有可无）：一道判断题——同一个公开接口的两个实现，一个内部是 3 个较长的私有方法，一个是 20 个三五行的私有方法；问对调用者而言哪个更深（一样），对维护者而言差别在哪。
