# How to design Components in modern web apps?

- 原帖：https://groups.google.com/g/software-design-book/c/XuXnFQSG7Vo
- 精读：2026-10-03，读到第 3 条（2023-07-06 ～ 2023-07-11）
- 主题：在 Store/State 架构的前端应用（Angular，类似 Redux）里，组件既订阅全局状态又接收父组件传入的属性，"组件的接口到底是什么"说不清；作者把它归为发布-订阅，评价是灵活但管不住复杂性。
- 对应：第 18 章 18.2（事件驱动让代码不显然）；第 4 章 4.2（接口包含什么）；第 2 章（不明显的依赖）；次要：第 5 章
- 性质：仅作背景 + 少量作者补充
- 优先级：B。作者坦言没有好答案，实质内容只有一段；但这段话对发布-订阅给了一个书里没有的概括（灵活、却不收容复杂性），而且正好落在没有任何讨论组材料的第 18 章（目前为空，这一串能补）。

## 读者说了什么（转述）

1. **提问**（Torbjörn Lundquist，[1]）：赞同深模块、小接口，但在一个大型企业级 Angular 应用里犯难。应用里有 Store（状态）发出值的变化，组件订阅它们；某种意义上这些订阅就是组件的接口。同时组件还有初始化时设置、父组件随时可改的属性。代码难以跟读，和同事讨论"组件的接口"时，连什么算接口都有争议。问有没有设计建议或推荐读物。
2. **"接口"先说清指哪个**（Justin "J.R." Hill，[3]）：这里有很多层接口——给终端用户的图形界面、与服务器的请求/响应、模块导出的对象和函数、方法签名或类型。和人讨论时宁可多定义一句"我说的接口是指……"。不了解更多背景，很难分清复杂性有多少来自框架、多少来自问题本身、多少来自现有实现。同意作者对发布-订阅的看法。
3. **框架鼓励的混合**（J.R.，[3]）：这类框架里有三样东西：呈现/布局、状态、动作（逻辑）。框架把状态分出去了，但呈现和动作仍然混在一起；"一切皆组件"和 Java 的"一切皆对象"后果相似，会把逻辑硬塞进不合适的载体。建议尽量把动作从呈现里分出去，抽成更纯的函数，像分离状态那样分离逻辑。

## 作者的回应

作者 1 条：[2]（整段回复，已对照 full.txt）。

- **先承认没有好答案**：对"怎么设计基于组件的 Web 应用"没有好的建议。
- **把读者的架构归为发布-订阅，并给出评价**（书里没有这个说法）：发布-订阅很灵活、很有力，系统任何部分都能轻易对别处的变化做出反应；但它"don't contain complexity very well"（John Ousterhout）——很难预测一次状态变更的后果，因为系统里任何别的部分都可能订阅了它。
- 同意读者的感受：这样的系统里代码确实难以跟读。
- **建议只有一句**：发布-订阅在某些场合有用，但要有节制地用。

作者没有回答"什么算组件的接口"，也没有回应 J.R. 关于分离呈现与动作的建议。

## 挂到站点哪里

- **第 18 章"边界与反方"（新开"讨论组"块，本章目前为空）**：18.2 节把事件驱动列为"让代码不显然"的做法，理由是很难跟踪控制流（处理函数由事件模块间接调用）。作者在这里从另一头说了同一件事：发布方不知道谁订阅了，所以一次状态变更会波及哪里无法预测。两句合起来正好是一对：订阅方看不到谁会调用自己，发布方看不到自己会触发谁。再接上书里给的补救（在处理函数的接口注释里写明何时被调用），并提醒这只补了前一半。
- 第 4 章 4.2 可带一句读者的问题作为思考题："组件订阅了哪些状态"算不算它的接口？按 4.2 的定义（使用者必须知道的一切，含非形式部分），答案是算——这是本站的推论，作者没有回答，写的时候要标明。
- 第 5 章已有的 Eventz 一段（-3R1G0sU3zI：所有函数通过共享的事件记录通信 = 全是全局变量）与这一串是同一类担忧，可以互相指一下；那一段更尖锐，这一串更温和（"有节制地用"）。
- J.R. 的"把动作从呈现里分出去"是读者建议，与本书没有直接对应，不挂。
