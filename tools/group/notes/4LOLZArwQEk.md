# More example on error prone design

- 原帖：https://groups.google.com/g/software-design-book/c/4LOLZArwQEk
- 精读：2026-10-03，读到第 2 条（2023-06-16 ～ 2023-06-20）
- 主题：HTTP 客户端库默认不设超时（读者举 Python 的 requests）算不算容易出错的设计；库作者不知道合适的超时值、下载大文件又不能超时，这个两难怎么解。
- 对应：第 10 章（10.3 把错误定义掉——通过改定义让特殊情况消失）；第 8 章（8.2 配置参数：能自己定的默认值就别推给使用者）；次要：第 4 章 4.7（让常见用法默认做对）、第 6 章；训练场
- 性质：可改编成训练题的例子 + 勘误或澄清
- 优先级：A。作者给了一个书里没有的、很干净的设计动作：把"超时"的定义从"N 秒内没完成"改成"N 秒内没有可见进展"，大文件这个特殊情况就不存在了，默认值也就立得住。第 10 章目前没有任何讨论组材料，这一条正好补上，而且直接能改编成训练题。篇幅虽短（作者只有两段），但含金量高。

## 读者说了什么（转述）

Ivan Chernov（[1]）：

1. 想给书补一个"容易出错的设计"的例子：网络库，尤其是 HTTP。用 Python 的 requests 发一个最普通的 GET，默认没有超时。
2. 这位读者称几乎所有 HTTP 库都这样，并给了 requests 项目的一个讨论链接（帖子里同一个链接贴了两次）。
3. 转述库作者一方的主要理由：库不知道典型的响应时间，没法替使用者定超时。这位读者补了另一面：下载很大的文件是特殊情况，那时需要能无限期地关掉超时。
4. 问作者怎么看、多经常遇到超时错误。

## 作者的回应

作者只有 [2] 一条，两段。

- **默认值**：按作者的经验，任何分布式系统里超时都少不了。如果由作者来写 HTTP 库，大概会提供一个默认超时，并允许调用方覆盖。
- **重新定义"超时"（书里没有的例子）**：不要把超时定义成"操作在 N 秒内没有完成"，而是定义成"过了 N 秒却没有任何可见的进展"。原话："define timeouts to happen if N seconds elapse with no visible progress"（John Ousterhout）。这样传大文件时，只要一直在稳定地收到字节，文件再大也不会超时。
- 效果：作者预计这会减少人们覆盖默认值的需要。

这两段话把书里两章的做法连了起来：

- 第 8 章 8.2：库作者"不知道合适的值"不是把决定推给每个使用者的理由；给一个合理默认值、留覆盖口。
- 第 10 章 10.3：读者提的两难（要默认超时，又不能打断大文件下载）不是靠加一个"关闭超时"的选项解决的，而是靠改语义让冲突消失——和书里把 `unset`、文件删除、`substring` 的错误情况"定义掉"是同一手法，只是这里被定义掉的是一个特殊情况及其配置项，不是一个异常。

没有回应的：读者问的"多经常遇到超时错误"；requests 那场讨论本身。作者也没有给出具体的默认值，没有讨论"有进展但极慢"（比如对方每隔几秒才吐一个字节）的情况。

## 挂到站点哪里

- **第 10 章"边界与反方"（目前没有讨论组材料，优先补这里）**：新增"讨论组 · 作者补充"块。写法建议：先摆读者的两难，再给作者的改定义，最后点出它与 10.3 的关系——"把错误定义掉"不只用于异常，也用于消掉特殊情况和为它准备的开关。配一张小图：两条时间线，一条按总时长计时（大文件被误杀），一条按"距上次收到数据多久"计时。
- **第 8 章**：已有讨论组块（配置参数）。加一句交叉引用：默认值立不住时，先看能不能改语义让默认值适用于更多情况，再考虑暴露参数。
- **训练场**：很适合出一道设计题，原创 C++ 场景：`HttpClient::get(url)`。给三个版本——A 无超时；B 有总时长超时加一个 `no_timeout` 选项；C 空闲超时（每收到数据就重置计时）。问：哪一版让"最常见的调用"默认是安全的；B 的选项把什么决定推给了调用方；C 还剩什么情况没覆盖（慢速滴流；这一点是本站补充，可再加一个很宽的总时限作兜底），以及此时接口注释必须写明什么（超时指的是空闲时间而非总时间）。
- 第 4 章 4.7："常见情况应当默认做对"已有材料，交叉引用即可，不必重复。
