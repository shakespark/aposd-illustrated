# Is interface informal information a bad thing?

- 原帖：https://groups.google.com/g/software-design-book/c/lqWkasBh5jA
- 精读：2026-10-03，读到第 2 条（2023-12-28 ～ 2024-01-12）
- 主题：接口里的非形式信息算不算一种"隐晦"；读者用 AWS SQS 接收消息接口的等待时间参数举例——一个参数既是等待秒数，又暗中决定是只查一部分服务器还是全部查。
- 对应：第 4 章 4.2（接口的形式与非形式部分）；次要：第 2 章 2.3（隐晦）、第 13 章 13.5（接口注释）、第 8 章（配置参数）
- 性质：勘误或澄清 + 可改编成训练题的例子
- 优先级：C。作者的回答只是把 4.2 节重说了一遍（非形式信息不是坏事，而且必不可少），没有碰读者真正的问题（那个一身二任的参数该怎么设计）。读者的例子本身不错，可以改编成题，但站点第 4、12 章已有"非形式部分"的讨论组材料。

## 读者说了什么（转述）

Renan Roggia（[1]），刚读完第 4 章：

1. 问：非形式信息是不是都算隐晦？
2. 例子：SQS 接收消息的接口有一个以秒计的等待时间参数。从名字看只是"等多久"；实际上它还决定走短轮询（立刻返回，只问一部分服务器）还是长轮询（等待，并查遍所有服务器）。
3. "查一部分还是全部"听起来是实现细节，使用者本不关心；但每次调用都计费，短轮询可能因为那一部分服务器恰好没有消息而返回空，导致多花钱。所以这个看似简单的参数背后有不少非形式信息，其中有的对使用者重要（成本），有的不重要（怎么存、怎么取）。
4. 这位读者试着把这些信息变成形式化的接口（比如加参数），每次都觉得反而更复杂；最后倒觉得让一个参数兼做"开关 + 等待时长"还不错。请大家给别的设计。

## 作者的回应

作者只有 [2] 一条，只回答了第 1 问。

- 不确定读者说的"隐晦"具体指什么，但听起来是贬义；而作者**不认为接口里的非形式信息是坏事**：有些东西在接口的代码里写不出来（前置条件、副作用、单位等），必须靠它来描述。
- 另一层作用：非形式信息可以从实现和接口的所有细节里抽身出来，给出这个东西背后的直觉。原话："informal information makes it possible to abstract away from all of the details of the implementation and interface to provide an intuition behind the entity"（John Ousterhout）
- 结论：用得恰当，非形式信息在接口里有重要而有益的作用。

没有回应的：SQS 的例子；"一个参数兼两种含义"好不好；有没有更好的设计。

与书对照：前半句就是 4.2 节的内容；后半句（非形式描述提供直觉）是 13.4 节"高层注释增强直觉"的意思用到了接口上，不算新论点。

## 挂到站点哪里

- 第 4 章：已有关于 4.2 的讨论组内容（"接口简单是否等于规约简单"等）。本串作者的话与书重复，不必新增；至多在解释"非形式部分"时加半句"作者明确说过它不是缺点"。
- 训练场（本串真正可用的部分）：把读者的例子改编成原创题。场景换成自己的：一个消息队列客户端的 `receive(wait_seconds)`，`wait_seconds == 0` 时只查一个分片并立刻返回，大于 0 时查全部分片并最多等这么久。问：(1) 哪些信息属于接口的非形式部分、必须写进接口注释（空结果不代表队列为空；计费或开销含义）；(2) 哪些是实现细节不该写；(3) 把"0 表示另一种模式"这种用特殊值切换行为的做法和拆成两个方法、加一个枚举参数相比，各自的接口成本。对应第 4 章 4.2、第 13 章 13.5，也可挂第 8 章。
- 第 2 章 2.3：读者的直觉（接口的含义得靠文档才知道，就是隐晦）有一半是对的——隐晦指的是重要信息不明显；写清楚了的非形式信息不算隐晦，没写的才算。这句是本站的归纳，不是作者说的。
