# Composable decorators -- does that make sense?

- 原帖：https://groups.google.com/g/software-design-book/c/XF1ApRr0h9Y
- 精读：2026-10-03，读到第 4 条（2019-01-11 ～ 2019-01-18）
- 主题：一篇博客主张"可组合的装饰器"——把 String 的 trim、toUpperCase、split 等二十来个方法各改成一个装饰器类，层层嵌套着用；读者问这是不是 7.3 节说的浅类，作者说是，并说明为什么更喜欢现有的 String。
- 对应：第 7 章 7.3（装饰器）；第 4 章（4.5 浅模块、4.6 类过多症）；训练场
- 性质：可改编成训练题的例子 + 仅作背景（没有人替对方辩护，算不上真正的分歧）
- 优先级：B。作者的结论在意料之中，但给了三条具体理由，例子（二十个方法 vs 二十个装饰器类）非常适合改成训练题；第 7 章现有讨论组块讲的是透传变量和 Tell-Don't-Ask，装饰器一节还没有讨论组材料。

## 读者说了什么（转述）

1. **提问**（Kim，[1]）：7.3 节说装饰器类往往很浅。读到一篇博客（yegor256，2015 年的 "Composable Decorators"），里面的示例是从文件读文本，再依次套上"去掉不可打印字符""去首尾空白""全部大写"三个装饰器类，嵌套构造后调用一次读取。问这是不是书里说的浅类，以及装饰器什么时候才合理、怎样才算用得好。
2. **补充**（Kim，[2]）：同一篇博客还说 Java 的 String 是坏设计的典型，它那二十多个工具方法都应当做成装饰器；现在的链式调用是"命令式、过程式"的，改成嵌套构造装饰器对象才是"面向对象、声明式"的，并称这样更灵活、更可复用。（以上是这位读者转贴的博客观点，不是读者自己的观点。）
3. **收尾**（KimSia Sim，[4]，同一位读者）：倾向同意作者，也想不通博客作者为什么那样想。遗憾的是自己说不出更硬的理由，尤其想知道某种手法"什么时候"合理；承认自己同意作者却说不清为什么。

## 作者的回应

作者 1 条：[3]（整段回复，已对照 full.txt）。

**立场**

- 不喜欢这些装饰器例子。作者的感觉是：博客作者把好好的深类拆成了一堆浅类，给使用者增加了复杂性和工作量。照作者的理解，博客是在建议写二十个装饰器类来代替 String 上的二十个工具方法。
- 对博客的论证不满意：只有"更灵活、更可复用"这类含糊的话。作者表示如果有支持这种做法的论据，愿意听。

**喜欢现有 String 的三条理由（书里没有用这个例子）**

1. 所有功能集中在一处，使用者更容易看到有哪些功能。
2. 不管做什么操作，用到的类型始终只有一个 String。
3. "invoking a method on an existing class is generally simpler than creating a new class"（John Ousterhout）。

作者没有回答读者真正想问的后半句——装饰器什么时候合理、怎样用好。这部分书里 7.3 节有（四个"先考虑别的办法"的问题，以及"外部类接口改不了时用包装类做转换"这一种合理情形），但作者在这一串里没有重复，也没有补充。

## 挂到站点哪里

- **第 7 章 7.3 对应的小节 / "边界与反方"讨论组块**：加一小段"把方法改成装饰器类"。书里 7.3 的例子是 Java I/O 和可滚动窗口，都是"功能该不该并进被装饰的类"；这一串的例子更极端也更好懂：对一个字符串做三步变换，是三次方法调用，还是三层对象嵌套。作者的三条理由可以直接对应到书里的概念：可发现性（第 4 章：接口成本）、类型数量（每多一个类多一个要学的接口）、调用 vs 构造。
- **训练场**：很适合出一道 A/B 题（原创 C++）。A：`trim(toUpper(s))` 或成员函数链；B：`UpperCased(Trimmed(TextInFile(path)))` 这样的嵌套对象，每个类只有一个 `read()`。问：B 版每个类的接口与实现相比有多深？使用者要认识几个类型？再加一问把题目拉回平衡——"数据来源可替换（文件、内存、网络）"这一层用多态是否合理，从而区分"来源的多态"和"每个小变换一个类"。
- 第 4 章 4.6（类过多症）可交叉引用一句。
- 读者没得到回答的"什么时候合理"，站点可以用 7.3 节原有的四个问题来回答，并注明那是书里的话、不是这一串里的。
