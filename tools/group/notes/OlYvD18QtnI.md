## 读者说了什么（转述）

1. **原始异议**（Eric Wilson，[1]）：书读下来几乎全部同意，唯独不同意对小方法、小类的态度。书似乎暗示"写小方法就得不到简单接口"，但完全可以写一个小类，把协作的别的类藏在后面，合起来提供深的功能。Eric 的经验是：共事过的所有程序员（含自己）都倾向于把方法和类写得太长，而不是太短。最讨厌长方法的地方是多层嵌套的 if。还问作者：Robert Martin 这类人都提倡小方法，怎么看？
2. **真正的规则是"可理解"**（John Faucett，[3]）：50 行能看懂就不必拆成 10 个；5 行看不懂，拆成 5 个也没用，多半是缺注释。大师们推荐短，是因为见多了看不懂的长模块。
3. **大方法难测**（Chris Jerdonek，[4]）：分支多的方法难以确认所有路径都测到了。赞成作者说的"把深类切成外部不可见的小方法"，并指出这种切分可以一次抽一个、渐进地做。
4. **相关不是因果**（Evan Jones，[6]）：把一团乱的大函数拆开往往能改善理解，于是大家学到"拆大函数会让代码变好"；但函数长度只是与好设计相关，不是原因。函数长度是弱信号，函数签名的数量和复杂度是更好的警报。
5. **混杂因素清单**（Peter Ludemann，[7]）：Java 的 getter/setter 是为日后留余地；有些代码天生是"一件事接一件事"（业务规则），抗拒拆分；拆的时候如果发现要传一大堆参数、或者得发明许多私有字段在方法间传信息，就说明它是这类代码；Berkeley socket 的初始化是坏 API 逼人写长函数的例子；完整的异常处理会把主逻辑埋掉。
6. **箭头形代码与提前返回**（Brooks Moses，[8]；rj，[10]；Eric，[11][13]）：深层嵌套可以用提前返回（卫语句）压平，不缩短方法却好读得多。"只许一个 return"是过时的规矩。Eric 补充：多个 return 放在方法开头或结尾，中间的 return 不容易被注意到。
7. **反小函数的材料**（rj，[9]）：称有一项（"好像是 IBM 的"）研究认为理想函数长度在 65～200 行；不同意"能把注释变成小函数就变"的思路。
8. **为测试而拆会拖累重构**（Peter O'Connor，[15]）：大量小方法被测试直接调用，改代码时就会碰坏一片测试，反而让人不敢改；更好的做法是在模块接口处测高层行为。亲历过一个把 Clean Code 和 TDD 当圣经的代码库，设计被测试和 mock 扭曲，多出许多只为测试而设的间接层。
9. **Eric 的长篇自述**（[17]）：服务器端方法平均 10～12 行，客户端 5～6 行，是平均值不是上限。短的原因包括：把复杂布尔表达式包成命名良好的方法、把晦涩代码（哪怕一行）包起来、几乎不容忍重复、用包装类简化并收窄 API。也承认方法可能太小，两个紧密配合的小方法应当合并；长方法如果只是嵌套很少的一串步骤，也可以接受。附了一段约 15 行的 TypeScript 示例（两个方法：刷新数据后恢复表格选中行）。
10. **自动补全不解决问题**（Rafael Anschau，[20]）：转述 Martin 的说法——方法多不是问题，因为 IDE 有自动补全；Rafael 反驳：签名只是接口的一部分，另一部分更复杂，方法多照样增加认知负担。
11. **十个月后的回访**（Eric，[21]）：立场没变，但承认：很小又配合紧密的方法有时该合并（最近在自己代码里就发现了）；嵌套很少的长方法有时可以；从书里新学到"让错误不存在"的思路（认同 substring 的例子，但认为数据库错误之类不该被掩盖）；同意书里对继承的保留态度。

## 作者的回应

作者共 3 条：[2][5][19]。

**让步 / 认同**

- [2] 小方法本身不是坏事；别的条件相同时，短方法大概比长方法好，理由就是 Eric 说的那些。
- [2] 如果能把一个深类切成许多小方法，其中大多数对外不可见，而且各自干净、互相独立，作者说这很好。关键只在于：从外面看，这个类只呈现为少数几个简单方法。

**坚持**

- [2] 问题在于"别的条件"通常不相同：方法小就得多，每个都有自己的接口，这些接口的复杂度会累加；小方法隐藏的信息也少，对抗复杂性的杠杆小。
- [2] 小方法可能把相互依赖的东西拆散；这种情况下应该把相关的部分放在一处，才能看全、才能推理。

**书里没有的新说法 / 新例子**

- [2] **局部优化 vs 全局优化**："Making a method smaller is a local optimization"（John Ousterhout）——它让那一个方法好懂，但设计应该问的是什么结构让整个系统好懂。这句话比书里任何一处都更直接。
- [2] **点名《Clean Code》Listing 10-8**：作者说那段代码被切得太碎，任何一个方法单独都看不懂，必须全部读完；合成一个方法反而更简单。并透露："in my software design class, we use this code as the \"before\"!"（John Ousterhout）——Martin 把它当重构之后的成品，作者的课把它当重构之前的起点。
- [5] **中断处理函数的例子**：作者说自己有时会为了方便测试而拆方法——通常把中断处理的主体抽成单独的方法，顶层处理函数只留接中断、返回的管道代码；这样不必真的触发中断就能单测主体。这类拆分在模块外完全不可见，不给系统其余部分增加复杂性。这是作者亲口给出的"为测试而拆是正当的"的条件。
- [19] 有读者请作者公开课上的重写结果，作者拒绝并解释原因：写这本书时把当时所有课程项目的例子都用掉了，等于"报废"了那些项目，不得不全部重做；Martin 那段代码现在是课堂练习（学生先读、再批评、再重写），答案公开了就没法再用。

## 挂到站点哪里

- 第 9 章"边界与反方"：
  - 正文补"局部优化 vs 全局优化"这一句概括，以及作者认可的拆法（对外不可见、干净、独立）。
  - 反方用 Eric 的经验（实际见到的问题几乎都是太长）和 Evan Jones 的"相关不是因果"——后者既解释了为什么"拆小"这条建议流行，也没否定它在一团乱的代码上有效。
  - Peter Ludemann 的检验法（拆的时候要传一堆参数或发明私有字段，说明不该拆）可以直接当一条实用判据，和书里"浅方法"的红旗信号呼应。
