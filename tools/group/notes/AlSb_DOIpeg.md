# Question about 9.4 and 9.2

- 原帖：https://groups.google.com/g/software-design-book/c/AlSb_DOIpeg
- 精读：2026-10-03，读到第 9 条（2022-10-19 ～ 2022-10-25）
- 主题：9.2 说 FileInputStream 和 BufferedInputStream 应该合并，9.4 又说通用机制要单独成模块，两条是否矛盾；作者给出了书里没有写明的解法——缓冲做成内部复用的模块，而不是暴露给用户的一层。
- 对应：第 9 章（9.2、9.4）；第 4 章（Java I/O 例子的出处，"让常见用法尽可能简单"）；第 2 章（复杂性是一点点累积的）；次要涉及第 7 章（装饰器式的分层）
- 性质：勘误或澄清 · 真正的分歧 · 可改编成训练题的例子
- 优先级：A，读者问的正是读第 9 章时最容易卡住的地方，作者的回答补上了书里缺的一步，而且串里留有一个作者没接的反例。

## 读者说了什么（转述）

1. **提问**（Mitchell Johnson，[1]，自称入行不久）：9.2 主张把两个流类合并以简化接口；9.4 却说一个模块如果包含可用于多种用途的机制，就只该提供这一个通用机制。放在 Java I/O 上两条看起来相互打架。这位读者想知道作者会怎么做：把缓冲和文件读取放进同一个类，还是另建一个类把这几个类藏起来。
2. **"文件"和"缓冲"不是同一层的概念**（Gregg Irwin，[2]）：文件是输入来源的一种，缓冲只是任何来源都可能有的一个选项；`BufferedInputStream` 这个名字没说它是什么来源，`FileInputStream` 说了，两者不对称。另一种组织方式是"动词在前"：`read source`，由各种来源自己实现 open/close/read，选项和默认值放在通用接口里，各来源的默认值可以不同。
3. **替 Java 的分法辩护**（Peter Ludemann，[3]）：分开的好处是缓冲可以套在任何"像文件的东西"上，复用性更好；合并成一个类只是比嵌套两个构造函数少敲几个字。同时承认 Unix/C 那套（`open` 的 `O_SYNC` 加上 `setbuf` 一族）对大多数程序员也很难用对。
4. **对"0.01%"的反例**（Peter Ludemann，[5]）：至少有两类场景不要标准缓冲——逐字符响应的交互式输入（文本编辑器），和按行缓冲的交互式输入（要支持退格）。Unix/C 库覆盖了这两类但仍不够用，所以才有 ncurses 和 readline。**作者没有回复这一条。**
5. **"交给操作系统"其实做不到**（Gregg Irwin [6] 提出除嵌入式外不该让程序员看到缓冲选项；Peter Ludemann [7] 反驳）：内核里有一层缓冲、用户态又有一层，再加上磁盘缓存；不检查 `close()` 的返回值通常没事，出事时要很久才发现数据丢了。多层缓冲叠加后错误处理非常难。Peter 特别说明这不等于说 Java 的流设计是好的。
6. [8][9] 转去推荐 ACM Queue 的几篇文章（Poul-Henning Kamp 讲 Varnish 的 "You're Doing It Wrong" 等），与书无直接关系。

## 作者的回应

只有 [4] 一条，但内容很实。作者没有点名回答提问者，而是分别回应 Gregg 和 Peter，实际上把 9.2 与 9.4 的"矛盾"解开了：

- **坚持：为常见情况设计。** 作者把问题归结为"系统是围绕常见情况设计，还是围绕少见情况设计"。给文件以外的东西加缓冲是可以想象的，但少见；Java 把两个类分开，等于让几乎每个开发者多付出一份力气，却几乎没给谁省事。
- **新说法（书里没有）：缓冲可以是可复用的模块，但应当是内部模块。** 作者同意"有一个可复用的缓冲机制"是合理的，但主张把它做成 FileInputStream 内部使用、对用户基本不可见的模块，而不是叠在它上面、暴露给用户的一层；这个模块完全可以设计成能服务多种 I/O。书里（第 4 章、9.2）只说到"合并，并提供关闭或替换缓冲的办法"，没有说"通用机制照样独立存在，只是藏到下面去"。这正是 9.4 与 9.2 同时成立的方式：通用与专用仍然分开，分的是实现，不是用户看到的接口。
- **反驳"只省了几个字"。** 两点：其一，复杂性正是这样来的——一大堆每个都"看起来没那么糟"的决定加在一起。原话："That's exactly how complexity arises, as a whole bunch of decisions, each of which 'doesn't seem that bad'."（John Ousterhout，[4]）其二，这是额外的认知负担：要多学一个接口，还得记得用它；忘了的话程序看上去能跑，只是很慢。
- **更进一步的主张：** 常见情况下连"缓冲"这个概念都不必露出来，自动做对就行。
- **一个修辞性的数字：** 作者反问，创建 FileInputStream 却不想要标准缓冲的情况，会不会连万分之一都不到。这是反问，不是数据。

没有让步的地方；对 Peter 在 [5] 举出的交互式 I/O 反例没有回应。

## 挂到站点哪里

- 第 9 章页：在 9.2/9.4 之间加一个"这两条矛盾吗？"的问答框，用作者的解法收束——"通用机制独立成模块"和"对用户合并成一个接口"说的是两个层面。这是本串最该用的内容。
- 第 4 章页的 Java I/O 小节：补一句"作者后来在讨论组里的补充"，并在"边界与反方"里放 Peter Ludemann 的两类反例（逐字符、按行缓冲），注明作者未回应、书里的说法是"提供关闭缓冲的途径即可"。
- 第 2 章页：作者那句"复杂性就是这么来的"可以作为"复杂性是累积的"一条现成的例证（转述，或用上面那一处引用）。
- 训练场：改编成一道 C++ 的 A/B 对比题（原创代码）：A 是 `BufferedReader(FileReader(path))` 两层都暴露；B 是 `FileReader(path)` 内部持有一个可复用的 `Buffer` 组件，另给一个少用的构造参数关闭缓冲。问：哪一个违反了 9.4？（答案：都没有；B 的通用机制依然独立，只是不在接口上。）
