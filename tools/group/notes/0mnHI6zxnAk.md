# Confusing example in the book APOSD

- 原帖：https://groups.google.com/g/software-design-book/c/0mnHI6zxnAk
- 精读：2026-10-03，读到第 3 条（2026-08-29 ～ 2026-09-21）
- 主题：读者问 4.7 节的 Java I/O 例子——三个装饰器对象共用同一个接口，而书里说成本来自接口不来自类，那用三个对象的成本为什么不等于用一个？
- 对应：第 4 章 4.7（Java I/O 例子）、4.2（接口包含什么）；次要：第 7 章（装饰器）
- 性质：勘误或澄清
- 优先级：B。只有 3 条，但问题问得准（是初读者很容易产生的误解），作者的回答短而完整，适合做成章节页里的一条答疑；内容与 rin4ykU9plo 那一串互补，应合并使用。

## 读者说了什么（转述）

1. **疑问**（Santi machin，[1]）：附了书里例子的截图（图片不在本文件里，从上下文看是 4.7 节建三个流对象的那段）。推理是：这些对象都是装饰器，接口必然相同；既然书里说给使用者带来负担的是接口而不是类本身，那么三个同接口的对象和一个对象的成本应该一样。
2. **补充**（Tristan Ludowyk，[3]）：接口不只是其中的数据或名字，还包括它承载的全部语义和含义。

## 作者的回应

作者 1 条：[2]。没有让步，直接说明三个对象带来的额外成本：

- **要知道三个类**。接口相同确实比各不相同好，但使用者仍然得了解三个类而不是一个。
- **要实例化三个对象**，代码本身多了一层复杂度。
- **忘了建 BufferedInputStream，程序照样正确运行，只是极慢**。这是一个不报错的陷阱。

然后是原则性的一句："most programmers should never need to have any awareness that file I/O is buffered"（John Ousterhout）——缓冲应当自动发生，不必开口要。

与书对照：第三点书里 4.7 节已经说过（忘了建就没有缓冲、I/O 会慢）。前两点是书里没有明说的澄清：**"接口相同"并不等于"认知成本为零"，每多一个需要知道其存在、知道何时该用的类，本身就是成本**。这实际上把"接口"的含义从"方法签名"扩到了"使用者必须知道的一切"，与 4.2 节对非形式接口的定义一致，Tristan 在 [3] 说的也是这个意思。

作者没有新例子。
