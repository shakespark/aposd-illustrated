## 读者说了什么（转述）

全部出自 Benoît Fleury（[1]）。先说感想：接口越少越好，每写一个新模块、每引入一个新库或工具，系统里就多一些接口，应当问这份复杂性值不值。然后是三个例子：

1. **只有 getter/setter 的类**：Java 代码里常见，尤其是处理信息记录的业务系统。这位读者认为用通用抽象（映射）表示记录往往更好，Clojure 把这种抽象做进了语法。
2. **薄包装库**：很多 Clojure 库只是把函数调用转给 Java 方法。在已经有文档、有讨论的 Java 接口之外又多了一套接口。如果包装简化了接口或加了功能，才值得。
3. **Web API 的 SDK**：很多只是 HTTP 客户端外面的一层薄壳，还把 HTTP 客户端藏起来不让配置；系统连几个服务，就有几个要各自理解和配置的 HTTP 客户端；它们还为领域对象造一批浅类。这位读者宁可全系统只用一个自己熟悉的 HTTP 客户端，再用通用的解析器把响应体解析成映射。

## 作者的回应

作者 1 条：[2]。**这一条是插在引文之间回复的**，对照 full.txt：第一段答的是读者的第 1 点，第二段答的是第 2 点，第 3 点（SDK）之后没有回复。

**对第 1 点（getter/setter 类）**

- 如果唯一的方法就是 getter 和 setter，作者几乎不把它们当成类，"they are really just data structures"（John Ousterhout）。
- 遇到这样的类，作者会问：能不能实现一个更高层的接口，做的事不止读写结构里的字段？这样会得到更深的类。
- 注意作者没有接读者"改用通用映射"的建议，给的是另一个方向：不是换一种更通用的浅表示，而是把行为加进去。

**对第 2 点（包装库）**

- 包装几乎总是浅的，但仍然可能有用。两个例子：让一种语言实现的设施能被另一种语言使用；RPC 包装，把函数调用通过网络转给另一台机器。
- 结论：不认为有可能彻底消灭浅类。

**没有回应的**

- 第 3 点：SDK 把 HTTP 客户端藏起来反而增加配置负担。这其实是"隐藏了使用者需要的东西"的例子，作者没有评论。

## 挂到站点哪里

- **与已有内容部分重复**：第 4 章"边界与反方"已有"有用的抽象不一定深"（栈的例子，2018-10）和"浅模块有时无法避免"。这一串可以给那一段补两个更日常的例子：跨语言绑定、RPC 存根——它们浅，但换来的是"能用"，不是"藏复杂性"。一句话即可。
- **第 19 章 19.6**：书里说 getter/setter 是浅方法、应尽量避免暴露实例变量。作者在这里说得更直接：只有 getter/setter 的类不算类，是数据结构；该问的是能不能提供更高层的操作。可作为 19.6 的一句补充（第 19 章现有块没有涉及 19.6）。
- 第 7 章 7.3：书里说包装类"偶尔合理"，举的是接口转换；这里多了两种合理情形（跨语言、跨机器）。与 7.3 的口径一致，一句话。
