# Thoughts on Chapter 13.5 Interface documentation

- 原帖：https://groups.google.com/g/software-design-book/c/SPVi2Ib3Vhg
- 精读：2026-10-03，读到第 7 条（2021-06-23 ～ 2021-06-26）
- 主题：13.5 节 IndexLookup 例子里"循环调用 getNext，返回 NULL 表示结束"这个接口，是否不如 hasNext/getNext 配对的写法安全；后半串转到逐条取数据的接口在 RPC 下的性能，作者说明实现里可以把批量和并发全藏起来。
- 对应：第 10 章（10.3 把错误定义掉：用特殊返回值表示"取完了"算不算）；第 20 章（简单接口下面藏批量与并发）；第 4 章（深模块）、第 8 章（把复杂性往下拉）；第 13 章 13.5 只是例子的出处；训练场
- 性质：真正的分歧 + 可改编成训练题的例子
- 优先级：A。作者给了两条书里没有的论证（NULL 结束标记的线程安全优势；RAMCloud 的实现在简单接口下面做批量和并发 RPC），而且正好落在两个还没有任何讨论组材料的章节上（第 10、20 章目前为空，这一串两章都能补）。

## 读者说了什么（转述）

1. **返回 NULL 像是"把错误定义掉"的反例**（Geovani de Souza，[1]）：13.5 节的示例循环是先 `getNext()`、再判断是否为 NULL。这位读者认为这把检查的责任推给了使用者，容易漏；主张加一个 `hasNext()`，让 `getNext()` 永远返回有效对象，并举 Go 标准库 `database/sql` 的 `Rows.Next` 为同类设计。[2] 补充说后来发现这个类取自真实项目，但仍认为值得讨论。
2. **用可选类型比两种写法都好**（Simon Frankau，[3]）：把问题重述为"用'取不到东西'换来了'忘了查空值'"。在 Rust 里 `next()` 返回 `Option`，配合 `while let` 就漏不掉；而 hasNext/getNext 这种接口，类型系统拦不住误用，例如循环体里连取两个对象却只查了一次 hasNext。Rust 的迭代器接口正是只有一个 `next`。
3. **不要把预取绑在 hasNext 上**（Simon，[3]）：hasNext 和 getNext 通常紧挨着调用，预取没有收益；若为了性能把 hasNext 提前调用，代码既复杂又不显然。朴素的 RPC 实现里，hasNext/getNext 是两次往返，getNext 只要一次。这位读者自己偏好"基础实现保持直白，另做一个后台预取的适配器，再用工厂包成看起来像一个深模块的东西"，同时猜作者会选"一个深类全包"；翻书后看到 `isReady` 的注释，认为作者确实是后一种做法。
4. **RPC 下逐条取很慢**（Ciaran McHale，[5]）：往返延迟主导开销，应该提供一次返回一批的操作。给了一组伦敦到纽约的估算，并顺带批评 getter/setter 式的细粒度接口被照搬到 RPC 上（应当一次返回一个结构体）。
5. **不同领域的"好设计"不一样**（Ciaran，[7]）：看了作者的回复后，同意"把复杂性藏在门面后面"是好的；但指出自己熟悉的 RPC 系统里，IDL 生成的代理类不会做任何聪明事，调一次就是一次远程调用。RPC 让远程调用看起来和本地调用一样，这是双刃剑：开销差几个数量级；客户端与服务器互相递归调用可能死锁或耗尽线程。最后问书里有没有谈"好设计因领域而异"，无人回答。

## 作者的回应

作者共 2 条：[4][6]，都是整段回复，不是逐段插话。

**坚持**

- [4] 两种写法在作者看来差不多：都有一个循环、都有一处判断是否取完。作者反问：担心的是有人不检查 getNext 的返回值吗？这比有人忘了调 hasNext 更可能发生吗？
- [4] hasNext 方案并没有省掉接口上的复杂度：对象已经全部返回之后再调 getNext 会怎样，照样得定义。原话："won't it have interface complexity just as large as the getNext from the first approach?"（John Ousterhout）

**书里没有的新论证**

- [4] **线程安全**：只有一个 getNext 的写法可以让多个线程同时取对象来处理；hasNext/getNext 配对则不行，一个线程从 hasNext 得到"还有"（恰好是最后一个），另一个线程抢先把它取走，前一个线程再调 getNext 就没东西可拿。作者自己称这是一条"小"论据。
- [6] **一次方法调用不必对应一次 RPC**：这个接口在 RAMCloud 里是真实实现过的，实现做了两件事来减少 RPC：(a) 只要可能，一次 RPC 取回多个对象（相当于 Ciaran 说的批量操作）；(b) 同时向不同的索引服务器和存储服务器发 RPC 以提高吞吐。作者承认这套机制有些复杂，但对接口的使用者完全不可见。
- [6] 类比带缓冲的 I/O：应用调用 `getc` 时，很少真的引发一次内核调用。

**没有回应的**

- Simon 的可选类型方案（把"有没有"和"取值"合成一次调用、由类型强制检查）——这其实和作者的 getNext 是同一个形状，只是多了类型保障；作者没有评论。
- Ciaran [7] 的两点：远程调用伪装成本地调用的风险；好设计是否因领域而异。

## 挂到站点哪里

- **第 10 章"边界与反方"（新开"讨论组"块，本章目前为空）**：用这一串讲"用特殊返回值表示结束，算不算把错误定义掉"。要点三条：作者认为"先问再取"和"取了再查"的接口复杂度相当，因为前者仍要定义"取完之后再取"的行为；作者的线程安全论据（检查与取值分成两次调用，中间会被别的线程插入）；读者的可选类型方案作为第三种设计。可以和 3hgHk9NhZL4（异常还是特殊返回值）放在同一块。
- **第 20 章"边界与反方"（新开"讨论组"块，本章目前为空）**：简单接口不等于慢。逐条取的接口，下面可以批量取、并发取；`getc` 是同一回事。配上读者的反面提醒：自动生成的 RPC 代理不会替你做这些，接口细粒度就真的是一次调用一次往返。
- 第 8 章可交叉引用一句：这是"把复杂性往下拉"的实例（批量和并发由实现承担）。
- 第 13 章 13.5：只需一句提示"这个例子的接口本身在讨论组里被质疑过，见第 10 章"。
- 训练场：出一道 C++ 的 A/B 题（原创代码）。A 版 `hasNext()/next()`，B 版 `std::optional<T> next()`，问哪一版在两个线程共用一个游标时会出错、错在哪；再加一问"hasNext 方案里，取完后再调 next 的行为要不要写进接口注释"。

## 待核实

- Ciaran 的估算（往返约 60 毫秒、逐条取比批量取慢约 877 倍）是读者自己按假设算的，不是测量；"二十年前在 RPC 厂商工作时见过多起"是自述。
- Simon 说 Rust 的迭代器接口只需实现一个 `next`、返回 `Option`：与常识相符，但本站未对照 Rust 文档。Geovani 提到的 Go `Rows.Next` 实际是"先 Next 再 Scan"的配对式接口，正好是这位读者主张的形状，同样未核对文档。
- 作者说 RAMCloud 的实现做了批量与并发：是作者对自己系统的陈述，本站没有去读 RAMCloud 源码。书里 13.5 节的 `isReady` 注释（"getNext 可能阻塞 / 不阻塞"）与此一致，已对照本地原书文本。
