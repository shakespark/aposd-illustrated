# An alternative implementation to the undoable delete

- 原帖：https://groups.google.com/g/software-design-book/c/RFJ7q9wdke4
- 精读：2026-10-03，读到第 2 条（2020-05-30 ～ 2020-06-02）
- 主题：编辑器撤销机制的例子里，文本类直接调用 `History`；读者提议改成让 `delete` 返回一个"撤销函数"，由调用者交给 `History`，这样文本类就不依赖 `History`。作者逐点说明这样既不会让 API 更简单，也不会让知道这个 API 的地方更少。
- 对应：第 6 章 6.7（第二版的小节号；撤销机制例子）；次要：第 9 章 9.7（读者引用的图 9.3(c)）、第 8 章（复杂性上推还是下沉）、第 2 章 2.3（依赖）；训练场
- 性质：真正的分歧 · 可改编成训练题的例子
- 优先级：A。作者对书里一个核心例子的替代设计做了完整分析，给出了一套书里没有明说的判断办法（两个问题 + 数调用点）；站点第 6 章讲了 `History` 但没有这场讨论，而且很适合直接改成训练题。

## 读者说了什么（转述）

Hilary Hacksel，[1]：

- 书里的做法让每一个支持撤销的类都依赖 `History`，`History` 的接口一变，这些类全要改；这位读者认为这个依赖也许没有必要。
- 替代方案：去掉"可撤销的删除"这种专门的东西，让 `delete` 方法返回一个（或几个）函数引用，执行它就能把这次删除撤销掉。这样只有调用者需要知道 `History` 和 `Action` 的形状，文本类的方法也少了。
- 自己承认这是把复杂性往上拉给了调用者，属于图 9.3 里的 (c) 那种拆法（调用者要分别面对拆出来的两部分）；但问：比起让每个类都绑在 `History` 的 API 上，这是否更可取？调用者因此能自己往历史记录里加东西，也许还是好处。

## 作者的回应

作者只有 1 条：[2]，整段回复（没有逐段插在引文里），分四层。

**让步**

- 同意书里的机制确实把每个可撤销的类都绑到了 `History` 的 API 上，`History` 的 API 一改，这些类都受影响。

**坚持：这种绑定在一定程度上躲不掉**

- 只要一个类要支持撤销/重做，而且是作为一套支持多种可撤销类的通用机制的一部分，就必然存在一个用来协调各个类的撤销与重做的 API。
- 于是关键问题变成两个："(a) what is the simplest possible API, and (b) how many parties have to be aware of it?"（John Ousterhout，[2]）

**对 (a)：读者的方案里 API 并没有消失**

- 每个可撤销的类仍然要知道一个 API——`delete` 返回的那个函数的签名。
- 接着是一串追问：重做怎么办，`delete` 要返回两个函数吗？撤销/重做所需的信息（比如被删掉的那段文本）存在哪里？这正是 `History.Action` 的用途，新方案里难道不需要等价的东西？
- 作者的判断：把这个方案补全之后，现有 `History` API 的几乎所有成分最终都会回到新 API 里。

**对 (b)：知道这个 API 的地方反而更多**

- `delete` 返回函数引用之后，调用者拿它做什么？只能是交给 `History`。于是调用者暴露在 `History` 的 API 之下，API 一变调用者就受影响。
- 调用 `delete` 的地方几乎肯定不止一处，每一处都会受影响。所以受 `History` API 影响的代码片段比书里的做法更多，而且可能多得多：一个应用里调用 `delete` 的地方可以有几十处；如果文本类是通用的，还会被多个应用使用，所有这些应用里的每一次 `delete` 调用都得带上与撤销有关的代码。

**结论与姿态**

- 看不出这个方案简化了 API 或减少了受影响的地方；最后反问一句是不是自己漏了什么。读者没有再回。

**书里没有的新东西**

- 书 6.7 节只说了这个设计"好在哪里"（通用机制、具体动作、分组策略三者互不知情），没有讨论"可撤销的类依赖 `History`"这个代价。这里作者第一次承认这个代价，并给出评估它的办法：既然某个协调 API 必然存在，就比较"它最简能有多简"和"有多少方必须知道它"。
- "数调用点"的论证：把依赖从被调用的类挪到调用者，受影响的是所有调用点（乘以使用这个类的应用数），而类只有一个。这是"把复杂性往下沉"（第 8 章）在依赖问题上的一个具体算例。
