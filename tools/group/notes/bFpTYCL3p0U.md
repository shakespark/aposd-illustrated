# Context Objects

- 主题：一位读者分享在实际项目里大量使用 context 对象的经验——让每个类只通过一个"收窄的接口"看到 context 里自己需要的那几项服务，以缓解书里承认的"context 变成大杂烩"问题。作者只道了谢。

## 读者说了什么（转述）

Bogdan Bălan，[1]（自述是 Google 的高级工程师，系统是一个用 Objective-C 写的 iPhone 应用，设计时还没读过这本书）：

1. **两个 context**：起初很多类在构造函数里接收一个 `AppContext`；后来又加了一个 `UserContext`，把与用户相关的服务和共享服务分开，从而支持多账号并把用户数据隔离干净。
2. **每个类只看到一个子集**：完整的 context 是一个实现了几十个"Provider"协议的类；每个使用者拿到的不是完整类型，而是只含自己需要的那几个协议的组合类型，于是只能调用那几个取值方法。Objective-C 可以在使用处临时把几个协议组合成一个类型，几乎没有样板代码；Java 里要为每个使用者另外声明一个继承这几个 Provider 的接口，样板多一点，这位读者认为仍可接受。
3. **不追求防得住**：拿到 context 的类技术上可以强制转型去访问不该访问的方法，但严防死守是过度设计，"限制可见性"已经够用。
4. **效果**：自述这套做法很稳健，对测试很友好；当时是在"用现成的依赖注入框架"和"自己这样做"之间选了后者，样板代码的代价不大。
5. **后续改进**：服务越来越多之后，把相关的服务归到一个"伞"服务下面（例如一个主题服务统一提供颜色、字体、主题），而不是让它们都成为 context 的顶层成员；理由是凡是需要颜色的界面类，本来也该能访问其他外观设置。日志、统计、数据类服务同样处理。

## 挂到站点哪里

- 第 7 章 7.5 对应的小节：在已有的 context 讨论组材料后面加一小段"读者经验"（标题不要写成"作者补充"）——
  - 书里的原话是 context 缺乏约束就会变成一个制造隐蔽依赖的大杂烩，并承认没有更好的办法。
  - 这位读者的做法：context 本身还是一个大对象，但每个使用者声明自己需要的那个窄接口，依赖因此重新写在了类型上。这正好回应了书对透传变量替代方案的担忧（依赖不显眼）。
  - 代价也要写：每个使用者多一个接口声明；不防恶意转型；"伞服务"是在粒度上做的妥协。
  - 明确标注：作者未置评。
- 训练场：可以出一道 C++ 题（原创）。给一个持有十几项服务的 `AppContext`，以及一个只用到其中两项的类；A 版构造函数收 `AppContext&`，B 版收一个只含两个取值方法的抽象基类（或用模板约束）。问：读 B 版的类声明能知道什么、A 版不能；给这个类写单元测试时各要准备什么；什么时候应该把若干服务合成一个"伞"。出题前对照第 7 章现有的透传变量题和"取材于讨论组"的那道，避免撞题。
- 与已有笔记的关系：Dependency injection for eliminating pass-through variables、Eliminating pass-through variables by creating objects up front 两串都谈 7.5；这一串是其中唯一来自大规模实践的经验，但也是唯一没有作者意见的。
