# Omission of fsync in APoSD and RAMCloud

- 原帖：https://groups.google.com/g/software-design-book/c/OCSMlVYmQTE
- 精读：2026-10-03，读到第 9 条（2025-03-18 ～ 2025-04-05）
- 主题：书里把 Unix 文件 I/O 的五个调用当作深模块的典范，却没提 fsync；读者问：算上持久性之后这个接口还"简单"吗？后半串转到 RAMCloud 不调用 fsync 是否安全。
- 对应：第 4 章（4.4 深模块的 Unix I/O 例子，4.7 Java 与 Unix I/O 的默认行为）；第 2 章（2.1 复杂性按"开发者花在上面的时间"加权）；专题 ostep（文件系统持久性、fsync、崩溃一致性）
- 性质：真正的分歧 + 勘误或澄清（作者说明为什么省略 fsync）+ 可改编成训练题的例子
- 优先级：A。这是对书里最著名例子的一次有力质疑，作者正面回答并把"复杂性取决于多少人需要知道"讲得比书里更明确；同时和 ostep 专题直接相连。

## 读者说了什么（转述）

1. **质疑**（Varun Gandhi，[1]）：同意那五个调用（open/read/write/lseek/close）按书里的定义是"深"的，但问它是否算"好"。没有 fsync，这五个调用对持久性没有足够保证；而 fsync 出名地难懂，连做数据库和文件系统的人都容易用错（附了几篇外部文章）。这位读者还搜了 RAMCloud 源码，说没有找到任何 fsync / aio_fsync 调用，对一个声称保证持久性的系统来说有点意外。问题是：fsync 的存在和复杂度是否影响对那五个调用的评价？还是因为普通开发者很少操心它，就不该算太重？
2. **再加几层**（Peter Ludemann，[2][5]）：C 标准库在 POSIX 之上又加了一层缓冲（setvbuf、fflush）；磁盘固件的缓存也未必可信。"多数人不受影响"——直到受影响为止：程序崩溃后不能指望最后一次写已经落盘。还有：close 的返回值常没人检查；写管道或网络时要处理短写、EAGAIN、EINTR。
3. **"成功之坑"**（Varun Gandhi，[4]）：不用 fsync 的应用更容易出 bug。例子：云上的抢占式实例随时可能被终止，如果程序先写文件、再做不可逆的动作（比如发出网络请求），可能请求发出去了而文件没落盘；桌面程序把数据存成普通文件再和网络交互也一样。这位读者拿书里第 4 章对 Java 缓冲流的批评（常用情形应当是默认行为）反过来问：POSIX 把持久性做成"要自己选择打开"而不是默认，是不是没有满足同一条准则？
4. **Redpanda 的文章**（Varun Gandhi，[4]）：一篇 2023 年的博客论证即使有多副本复制，不 fsync 仍可能全局丢数据；RAMCloud 论文假设 fail-stop 模型，看起来符合那篇文章的前提。这位读者说明自己没有仔细分析过该论证。
5. **替作者辩护**（Dan Cross，[6]）：要不要持久性取决于程序的语义。Dan Cross 称 FreeBSD 的 bin/ 源码树里只有 dd 用到 fsync，而且要给特定选项才用。POSIX 并不规定 write 之后必须 fsync 才落盘，那是实现的事；open 还可以带 O_SYNC / O_DSYNC 得到同步语义。需要的程序用 fsync，大多数不需要——而且默认同步的性能代价很大。数据库（SQLite、BerkeleyDB 等）替应用做了这套动作。
6. **收尾**（Varun Gandhi，[9]）：接受作者的解释。并推测 Redpanda 的文章隐含"系统自己负责持久性"的假设，而 RAMCloud 的协调器元数据放在外部的容错键值存储里，等于把一部分持久性外包出去了，所以两者情形不同。

## 作者的回应

作者回了两次（[3]，[7]/[8]）。第 7、8 条是同一回复的两个版本，措辞略有改动，下面合并处理。

**关于为什么省略 fsync（[3]）**
- 承认除了那五个还有别的文件相关系统调用：fsync，还有 sendmsg 这类网络专用的，等等。省略的理由是它们**很少需要**；只用那五个就能做极多的事。
- 承认要构建高可靠系统时事情会更复杂。但只有少数人需要这样做，所以这部分额外的复杂性不影响绝大多数使用 POSIX I/O 的人。作者明确确认了读者的理解：开发者不需要知道的东西，就不给这位开发者制造复杂性。

**把这条原则说得更细（[7]/[8]，书里没有这么明确的表述）**
- 一切取决于**多常需要**。如果多数开发者确实都该用 fsync，那评估 I/O 接口的复杂度时就必须把它算进去。
- 承认读者举的例子（抢占式实例等）确实需要 fsync，但认为是离群情形：对几乎所有程序，崩溃时丢一点数据不值得为之同步。作者的个人数据点：写过上千个程序，只有少数几个觉得需要 fsync。
- **复杂度因人而异**——这是全串最有用的一句：

  > "if you use fsync in most or all of your code, then fsync becomes a fundamental part of the I/O interface for you"（John Ousterhout，[8]）

  也就是说，对那样的开发者，把 fsync 的复杂度算进 I/O 接口是恰当的。

**关于 RAMCloud（[3] 和 [7]/[8]）**
- 作者先声明记忆有些模糊。不需要 fsync 的原因是：写到磁盘的内容都在多台机器上有副本，系统本来就必须承受整台机器丢失，所以恢复不取决于是否 fsync。唯一有影响的是整个数据中心断电；当时的假设是生产节点有足够的后备电池，断电后能把内存数据刷到磁盘。
- 对 Redpanda 的论证：作者读了，认为那里描述的行为是一个 **bug**——一个节点带着未同步的数据崩溃，重启后像从没收到过那些数据一样重新加入集群，这是不安全的。作者的规则：节点如果崩溃后无法恢复它已确认过的数据，就必须被视为永久死亡，不得再参与集群；承诺了持久就必须真的持久。
- RAMCloud 的做法：节点不管因为什么崩溃，都不复用崩溃后残留的数据，整个节点从其他副本恢复；只有干净关机（其中包含 fsync）的节点启动时才可以复用已有数据。作者据此认为不 fsync 是安全的（用词是"我相信"）。

**没有让步的**：作者没有承认书里省略 fsync 是疏漏，也没有说会改。
**没有回应的**：读者用第 4 章 Java 缓冲流的"默认值"准则反问 POSIX 的那一点，作者没有直接接；只是用"多数程序不需要"间接回答。Peter Ludemann 提的短写、EINTR、close 返回值等也没有回应。

## 挂到站点哪里

- 第 4 章"边界与反方"：加一条"五个调用够吗？——fsync 之问"。写清读者的质疑、作者的回答（复杂度按需要知道它的人加权；对数据库作者而言 fsync 就是接口的一部分），以及本站可以点明的一层：这其实是 2.1 节那个"按开发者花的时间加权"的定义在起作用。
- 第 2 章：在讲复杂性定义的地方加一个指向这里的例子——同一个接口，对不同的使用者复杂度不同。
- `topics/ostep.html`：这是把 APOSD 的"深模块"与 OSTEP 的持久性部分（fsync、崩溃一致性、缓冲写）接起来的现成桥梁；Peter Ludemann 列的那串"藏在简单接口下的坑"（短写、EINTR、close 的返回值、stdio 缓冲）可以作为清单。
- 训练场 / 项目（minikv）：
  - 一道题：给一段"写文件→发网络请求"的 C++ 代码，问它在崩溃时的行为，以及持久性应该由哪一层负责（调用方每次 fsync，还是封装成一个带持久性语义的模块，把复杂性往下拉——第 8 章）。
  - 项目 minikv 若有写盘路径，可加一个思考题："你的接口把持久性做成默认还是可选？为什么？"
- 作者关于"已确认的数据若丢失，节点必须视为永久死亡"的规则是分布式系统设计的内容，放 ostep 专题做延伸阅读即可，不必进章节页。
