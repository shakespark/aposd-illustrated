# On unit testing, mocks, and classitis

- 原帖：https://groups.google.com/g/software-design-book/c/CZ-gs8MPqvA
- 精读：2026-10-03，读到第 5 条（2018-07-23 ～ 2018-07-25）
- 主题：为了能用 mock 做单元测试而把功能拆成多个类，算不算类过多症；可测试性该不该影响类的划分。
- 对应：第 19 章 19.3（单元测试）；次要：第 4 章 4.6～4.7（类过多症、Java I/O）、第 9 章
- 性质：真正的分歧（很浅）· 勘误或澄清
- 优先级：C。作者的立场（为测试做小改动常见，为测试改整体类划分没遇到过）与站点第 19 章已收录的 2020 年说法、第 9 章已收录的"拆中断处理函数"例子基本一致，**与已有内容大体重复**；新增的只有"把系统调用放到可替换的接口后面以模拟难以制造的错误"这个具体例子，和一句对读者例子的点评。

## 读者说了什么（转述）

1. **开帖**（Mike Marty，[1]）：自己的经验是单元测试的考虑确实会影响怎么分类，部分原因是 gMock 这类 C++ 测试框架通常靠虚函数分派来替换依赖。完全同意书里对 Java"读文件要建三个对象"的批评；但即使对外只给一个顶层 API，内部实现可能还是会拆成三个类，好各自单测和 mock。所以提议区分两种类过多症：为实现/可测试性而生的，和暴露在顶层接口上的。
2. **应作者要求举例**（Mike，[3]）：从 Go 官方博客一篇讲云端可移植编程的文章里取了一个函数 `setupBucket`：先用写死的区域名取 AWS 凭证，再用写死的桶名打开 S3 桶并返回。测试包含这段代码的模块时不能真去连 S3，而那个 S3 包只暴露一个打开桶的函数，所以要测就得自己新建一个可 mock 的接口，外加一个只做转发的真实实现。
3. **不认为这是"纯为测试而改"**（Brooks Moses，[4]）：这个函数藏着两个写死的字符串，出于可配置性和健壮性本来就该改；改了之后，传入这些值的那套机制顺便也能传入"给我一个假桶"。另一种 Go 惯用法是把 `setupBucket` 定义为某个接口的实现，生产代码链接真实版本、测试链接返回假桶的版本。同意核心观察：要可测试，就不能把写死的字符串和无条件的 S3 调用与想测的代码放在同一个模块里；但这样做的理由不止测试，替换桶的来源还有很多别的用处。

## 作者的回应

作者共 2 条：[2]、[5]。都是整段回复。

- [2] **常见的是小改动**：为可测试性做几处小的设计调整并不少见，例如让系统调用经过一个可以替换的接口，测试时换掉它来模拟平时很难制造的错误。（这个例子站点上没有。）
- [2] **没遇到过大改动**：记不起有哪次仅仅为了可测试性而改变整体的类划分。如果确实对测试帮助很大，并不一定反对，只是至今没碰到这种需要。以 Java I/O 为例，看不出拆成三个类对可测试性有什么帮助。向读者要一个好例子。
- [5] 喜欢 Brooks 提的两种办法。另外点评读者举的那个函数本身就很浅：功能不多，而且怀疑调用方最后还是得知道那两个写死的常量是什么。

作者没有评价"两种类过多症"的区分本身。
