# Review of APoSD and comments on prior discussions

- 原帖：https://groups.google.com/g/software-design-book/c/GDglsxrKIgo
- 精读：2026-10-03，读到第 2 条（2025-02-09 ～ 2025-02-10）
- 主题：一位读者讲自己边读边按章改写一个 G-code 前端项目的经历，顺带对讨论组里旧帖发几句感想（文学式编程、图形化表达代码），并提到用表格枚举来给模块起名。
- 对应：无；勉强相关的是第 14 章（起名字）和"怎么读这本书"的学习方法
- 性质：仅作背景
- 优先级：C。没有作者回应，没有质疑也没有成形的例子；而且帖子里引用的原话都被去掉了，几处关键句读不出原意。只有"每读一章就拿自己的项目过一遍"这个读法值得一提。

## 读者说了什么（转述）

全部来自 William Adams。

1. **读法**（[1]）：每读完一章就停下来，把当前项目整个按这一章的教训过一遍，该改的改、该重写的重写。读到大约一半时改动越来越小、越来越少，到书末已经没有可改的了。项目本身比较特别：给一门现有语言（控制数控机床的 G-code）的一个小子集做前端。由此问：这种"重新实现"是不是典型的问题空间？
2. **文学式编程**（[1]）：翻过讨论组旧帖后，意外于 Literate Programming 很少被提到。
3. **图形化表达**（[1]）：对作者 2018 年 8 月的一句话感到沮丧（那句话在文件里被去掉了，从上下文看是关于图形/可视化表达代码的局限）。这位读者自称是视觉型的人，希望有一种机制把问题分解到每个元素都能放进一屏，并有清楚的层级和导航；但承认自己写了近百页代码和文档，只有一张图真正表达了代码（一个画圆弧的简单循环）。另外提到作者在 SE Radio 第 520 期访谈里的一个例子（内容被去掉）和 folklore.org 上"计算器构造套件"的故事作为对照。
4. **用表格起名**（[2]）：给模块起名时，先列一张表穷举各种组合——形状（线 / 弧）× 输出方式（切削 / DXF / G-code）——得到 `cutline`、`dxfline`、`linegc`、`cutlinedxfgc` 这样一组成体系的名字，认为这个办法值得一提。（表后面的说明文字被去掉了。）

## 挂到站点哪里

- 基本不用。
- 如果站点首页或"怎么用本站"有学习建议，可以加一句读者经验："每读一章，拿手头的项目过一遍"，不必注明出处细节。
- 第 14 章：第 4 条可以当作"一致性命名"的一个小旁证，但那组名字（`cutlinedxfgc` 这类把多个维度拼进名字的做法）本身更像一个值得讨论的反例——组合爆炸进了名字，可能说明该用参数而不是多个函数。这是本站的判断，不是帖子里的结论；要用的话得自己另写例子。
