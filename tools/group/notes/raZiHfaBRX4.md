# Another approach to complexity reduction: interface elimination

- 原帖：https://groups.google.com/g/software-design-book/c/raZiHfaBRX4
- 精读：2026-10-03，读到第 8 条（2018-08-20 ～ 2018-08-30）
- 主题：一位读者主张用"广播消息、不写显式接口"来降低改结构的成本，并给出一个 C++ 小游戏的两种写法；作者反驳说依赖和接口并没有消失，只是被藏了起来，认知负荷反而更重。
- 对应：第 18 章 18.2（事件驱动让代码不显然）；第 21 章（"什么重要"）；第 2 章（认知负荷 ≠ 打字量，2.2/2.3）；第 5 章（已有相近材料）；训练场
- 性质：真正的分歧 · 可改编成训练题的例子
- 优先级：A。作者用六点逐条拆了一个具体的 C++ 例子，并给出两句书里没有的概括；能补到目前没有任何讨论组材料的第 18 章和第 21 章。与第 5 章已有的"没有接口和接口不明显是两回事"一块论点相近，用的时候要避免重复（见"挂到站点哪里"）。

## 读者说了什么（转述）

1. **开帖的主张**（James L / James Leibert，[1]）：书里说降低复杂性靠两条路（把代码写简单、模块化），这位读者认为漏了第三条——取消刚性的接口。起因是自己的 C++ 大项目想加脚本接口时，发现模块划分本身几乎改不动；而孩子用 Scratch 写程序可以随意挪代码，因为组件之间只靠广播消息通信。提出的做法：模块之间只传不可变的、序列化成标准形式的数据，不返回值，要数据就发请求、通过回调或"黑板"拿回；需要引用对方的对象时只给不透明的句柄。自己承认两个缺点：编译器查不了消息格式和有没有人响应；序列化比直接调用慢。
2. **服务化就是给传统语言接上消息传递**（Evan Jones，[3]）：大型互联网公司的系统由独立服务组成，接口用跨语言 IDL 描述。主要好处是各服务可以分开开发和部署，只要消息按兼容的方式演进；而且除了消息没有别的共享途径，能挡住一些"意外的耦合"。
3. **历史渊源**（Andrew Simmons，[4]）：联想到 Hoare 的 CSP、occam、Go 的 channel，以及 Plan 9 的 9P 协议。
4. **具体例子**（James，[5]）：先承认作者说的"功能上等价"基本是对的，把主张收窄为"探索式开发阶段，改结构更便宜"。例子是一个飞船躲导弹的小游戏：
   - 普通写法：`Sprite` 类有 `touching/move/show/explode`，`Game` 拿着一组 `Sprite*`，在循环里做碰撞检测、更新、渲染。
   - 消息写法：一个全局 `Notifier`（`observe/broadcast/send`），`Sprite` 和 `Game` 都继承 `Notified`，在 `receive(msg, info)` 里用字符串比较分发；`Game::run` 里只广播 "check touching"、"move"、"show"；碰撞检测被拆成两步（导弹广播自己的位置，玩家收到后比较并广播 "hit"）。
   - 然后假设要把一个个 `Sprite` 对象换成按数组存放的 `SpriteStore`（为了缓存友好）：普通写法里 `Game` 要换依赖、迭代代码要搬家；消息写法里 `Game` 一行不用改。
   - 由此提出六条启发式：用调用方的领域语言声明式地表达通信；信息一次只朝一个方向传（方法不返回值）；跨模块的数据不可变且序列化；协议只针对一对模块的一次交互（不设正式"接口"）；需要引用对方对象时给不透明句柄；模块内把通信层和实现逻辑分开。
5. **读者的让步与坚持**（James Leibert，[7]）：大体同意作者的批评——什么都广播、谁都能处理的大系统会是噩梦；写得差的消息传递程序可能比写得差的 OOP 程序更糟。补充三点：一旦确定由谁处理，就把广播换成定向 `send`，依赖重新变得显式；普通 OOP 有对称的负担——想把某个请求的处理者从 `Sprite` 换成别的模块时，不知道自己模块里有多少处用到了 `Sprite` 的哪些行为；广播值得保留的场合是"通知"（只发信息、不要求服务）。并把主张重新表述为"结构上的承诺越少越好"：先按领域语言写清自己需要什么，等把握大了再把连接逐步变显式。还指出书似乎把"结构难改"当成既定事实，问为什么不研究怎样让结构选择更容易改。
6. **收尾**（James，[8]）：见作者没再回，表示就此打住；附带一个观察：敏捷最早出自 Smalltalk 圈子，而没有自发出现在 C++ 圈子，猜测与"结构改动的难易"有关。

## 作者的回应

作者共 2 条：[2][6]，都是整段回复，没有逐段插在引文里。[7][8] 之后作者没有再回。

**[2] 第一反应：消息和函数调用差别不大**

- 先声明自己在消息式系统里写的代码不多，可能漏了什么。
- 消息式系统照样有 API：接收方只能处理含有特定信息的消息，发送方只能请求接收方支持的功能；请求消息的内容和方法参数的结构、含义基本一样；唯一标识符与内存地址在程序结构上也没多大区别。所以猜测消息式 API 最后会和方法式 API 一样刚性。
- 给了一篇书里没有引用的文献：1979 年的 "On the Duality of Operating System Structures"，论点是消息式系统和过程调用式系统互为对偶，一种写法的程序可以很容易改写成另一种。
- 请有消息式系统经验的读者来谈它是否真让大系统更好建、更好维护。

**[6] 看了 C++ 例子之后的六点（坚持，没有让步）**

- 总评：这个例子正好说明"打字量"和"认知负荷"的区别。消息写法少打了一点字，但认知负荷更重；总体上比 OOP 写法复杂得多。
- 依赖还在，只是不显式。`Game` 仍然依赖 `Sprite` 提供的那些功能：写 `Game` 时必须确切知道 `Sprite` 能做什么，改了 `Sprite` 可能就得改 `Game`。
- 依赖被藏了。`Game` 里没有任何迹象表明它依赖 `Sprite`。设想几百个类都在处理各种消息：读 `Game` 的人想知道谁实现了 "move"、它到底做了什么，只能把所有响应消息的类搜一遍——而且找到第一个实现还不能停，因为可能有多处实现，它们都会被调用。
- API 也被藏了。OOP 写法里看公开方法的签名和注释就知道 `Sprite` 支持什么；消息写法里得读实现代码，找每种消息在哪里处理。接口没有一个明显的地方可以写文档，所以多半就没有文档。
- 省下的代码很少：基本上只省了 `Sprite` 对象的那一行声明。换掉 `Sprite` 时确实要改这一行，但与重写 `Sprite` 本身相比微不足道；而这一行声明的作用正是把依赖写明，值得多打这点字。
- 小例子里看不出来，几百个类的大系统里这份复杂性会非常大。
- 换一个角度，用"什么重要"来说：理想的设计是尽量减少"重要的东西"（某一时刻人需要意识到的信息）；但一件事既然重要，就必须把它讲清楚、摆在明处。"If something matters and you hide it, you have made life worse for developers"（John Ousterhout，[6]）。消息写法做的正是这件事。
- 结句："Complexity isn't as much about what you have to type as about what you have to know."（John Ousterhout，[6]）

**书里没有的新东西**

- "多处实现都会被调用，所以找到第一个不能停"这条针对广播的具体论据。
- 对偶性论文的引用。
- 2018 年 8 月就用"what matters"来论证（"尽量减少重要的东西；重要的就必须显眼"）。本地原书文本是第二版，第 21 章"Decide What Matters"讲的正是这件事；这条回复可以当作第 21 章思路的一个早期、更短的版本。

## 挂到站点哪里

- **第 18 章（目前没有讨论组材料）**："边界与反方"加一块"讨论组 · 作者补充"。18.2 把事件驱动列为让代码不显然的做法，理由是控制流难追踪；这一串给了更完整的论证和一个可以对照的例子：广播式写法里依赖和接口都还在，只是从声明里搬到了字符串比较里。用作者的六点，重点是"找到第一个处理者还不能停"和"接口没有地方写文档"。同时把读者一方最站得住的两点写进去：确定处理者之后可以把广播换成定向发送；"通知"是广播的合理用途。
- **第 21 章（目前没有讨论组材料）**：加一小块——"重要的东西要少，但重要的必须显眼"；把重要的东西藏起来和把不重要的东西摆出来是同一类错误的两个方向。引那句 "If something matters…"。
- **第 2 章**：2.2 认知负荷处可加一句"复杂性看的是要知道多少，不是要打多少字"。第 2 章已有三块讨论组材料，只加一句即可，不必单独成块。
- **第 5 章**：已有"没有接口和接口不明显是两回事"（取自 2023 年的另一串），论点与本串重复。不要再加一块，最多在那一块末尾加半句"2018 年对广播消息的做法也说过同样的话，见第 18 章"。
- **训练场**：很适合出一道 C++ 对比题（原创代码，不照搬）。给出一个"全局通知器 + 字符串消息"的小模块和等价的直接调用版本，问：(a) `Game` 类到底依赖谁、依赖什么；(b) 把某个消息名拼错会发生什么；(c) 哪一处适合保留广播（纯通知）、哪一处应改成直接调用。也可以出一道"看起来解耦了，其实没有"的判断题。
