# Good example of a bad interface (shaaaaallow)

- 原帖：https://groups.google.com/g/software-design-book/c/uHWl_gbtmW8
- 精读：2026-10-03，读到第 13 条（2023-04-02 ～ 2023-04-11）。**其中 [4]～[9]、[11] 共 7 条在本地两个文件里正文都是空的**；[9]、[11] 的内容能从后一条的引用里看到，[4]～[8] 完全缺失。
- 主题：pandas 的 `read_csv` 有几十个参数，它是"浅"接口的典型，还是一个可选参数很多的深接口？
- 对应：第 4 章（深度的定义、4.7 Java I/O 的对照）；次要：第 6 章（通用与专用）、第 8 章（配置参数）、第 9 章（合还是分）、训练场

- 优先级：B。作者没有发言，所以不能当"作者补充"；但这是一场质量不错的读者争论，案例人人都见过，正反两边都用书里的词在论证，很适合改成训练场的设计题，也可给第 4 章加一条"读者质疑"。

## 读者说了什么（转述）

1. **起因**（Oliver，[1]）：举 `pandas.read_csv` 当坏接口的例子（自己也不确定该叫"浅"还是"臃肿"）。理由：选项太多；许多选项和"把 TSV/CSV 切成列"无关，是在解析列里的内容，应当放到后面的步骤；按 IANA 对 TSV 的原始定义根本没有引号机制，接口做的事超出了函数名所说的任务。这位读者说明自己只是翻了翻书，没读完。
2. **辩护**（Simon Frankau，[2]）：数据科学里读 CSV 的目标不是解析理想格式，而是把现实里乱七八糟的数据装进来。遇到一种怪格式，多传一个参数就解决了，这按"接口代价比功能"算几乎是最深的做法，仅次于自动检测。关键在于这些参数都是**可选的**：不用就没有代价（文档难看除外），像 Unix 命令行工具那些冷门选项。反过来问替代方案是什么——让使用者自己拼后处理管道，那就很像 4.7 节批评的 Java 三层流。
3. **世界本来就乱**（Peter Ludemann，[3]）：接口复杂是因为 CSV 的变体本来就多，虽然未必用了最好的方式反映。设想的简化办法：提供一组过滤函数（分隔符、引号风格、日期格式……），让使用者传一个列表，或者提供回调，这样还能处理库作者没想到的情况。反面教材是 Excel：自作聪明地猜，猜错了就悄悄损坏数据。Unix 的 sort、find 和 IBM 大型机的 DFSORT 也是接口复杂的例子。
4. **仍然认为是坏设计**（Oliver，[9]，内容见 [10] 的引用）：接受"可选参数"的说法，也承认可以说它"臃肿但未必浅"，因为参数多、覆盖的功能也多。但坚持应该分两步：第一步只按分隔符切列，接口就是数据加分隔符；第二步再解析列内容。理由是把引号等处理强行绑进来，非典型用法反而更难做。
5. **也许只是文档问题**（Paul Becker，[10]）：文档里最简单的用法 `pd.read_csv('data.csv')` 排在页面最底下；主要问题可能是文档没有把简单的常见情况摆在前面。
6. **超出了"反映现实"的范围**（Gregg Irwin，[11]，内容见 [12] 的引用）：分块、压缩、内存、类型转换这些和 CSV 无关；有些选项很专，有些本可以用通用机制；最要紧的是**看不出哪些开关会相互影响**，在调用处不读文档无从知道。问：CSV 加载器的职责到底是什么？怎么区分"通用到值得收进来"和"只是我自己需要"（这位读者称后者为"轶事式设计"）？建议把选项做成数据（一个可以分组、合并、复用的配置结构），调用处会简单很多。
7. **换成 Rust 会怎样**（Simon Frankau，[12]）：先声明每一列的类型，告诉解析器"解析成这个类型的迭代器"；非标准的字段解析用类型上的标注表达。结果是一份紧凑的声明式定义，背后的解析器做大量工作，仍然是深接口。还提出把选项分成"表级属性"和"字段级属性"能理清那一锅"选项沙拉"；并拿 Rust 的命令行库 clap 自问：接口巨大，但每个使用者只用一个子集，也许应当看成"多个深接口"。
8. **收尾**（Gregg Irwin，[13]）：赞成用包装来隐藏细节。自己团队的做法是：一个全能但吓人的通用 `parse`，外加一个只管常见情况的 `split`。加载 CSV 时不做值转换，只提供几个关键选项和结果形状的选择，其余留给后处理。

## 挂到站点哪里

- 第 4 章"边界与反方"：可加一块"讨论组 · 读者质疑：几十个可选参数，是深还是浅"。要点三条——
  - 可选参数的代价不是零：不用的人不必学（Simon），但参数之间会不会相互影响，在调用处看不出来（Gregg）。这正是书里"接口 = 使用者必须知道的一切"的定义在起作用。
  - "深度"是比值，"臃肿"是另一回事：Oliver 自己最后也承认它可能臃肿而不浅。
  - 文档把最简单的用法放在最后，会让一个其实好用的接口看起来很吓人（Paul Becker）。
  必须写明这是读者之间的争论，作者没有表态。站点第 4 章已有 4 块讨论组内容，这一块如果加，篇幅要短，或者只放进训练场。
- 第 8 章（配置参数）：书里第 8 章反对把决定以配置参数的形式推给使用者，但也说有合理默认值时可以。`read_csv` 是"每个参数都有默认值"的极端情况，可以作为一句边界例子。
- **训练场（最合适）**：出一道设计题。原创 C++ 场景，例如一个 `loadTable(path, options...)`，有二十来个带默认值的参数。给三种方案：(A) 保持一个函数加大量可选参数；(B) 拆成"切列"和"解析列"两步让调用方自己串；(C) 一个声明式的配置对象或列类型描述。让学生用书里的词评估：常见情况要写多少、调用方需要知道什么、选项相互影响时谁负责、遇到库没想到的格式怎么办。答案解析说明没有唯一正解，并指出 (B) 在什么条件下会退化成 4.7 节的 Java I/O。
- 第 9 章：Oliver 的"分两步"与 Simon 的"合在一起"是 9 章"合还是分"的现成例子，可交叉引用训练题。
