# Dependency injection for eliminating pass-through variables

- 原帖：https://groups.google.com/g/software-design-book/c/xYzAzHcB630
- 精读：2026-10-03，读到第 18 条（2018-08-22 ～ 2018-09-24）
- 主题：读者认为依赖注入（DI）框架已经解决了透传变量问题；作者坦言不懂 DI，追问"显式写出这类依赖到底有什么价值"，最后没弄明白、搁置；读者之间对 DI 是什么也没有共识。
- 对应：第 7 章（7.5 透传变量与 context 对象；第 1 版第 50～53 页）；第 2 章（依赖、不明显）；次要涉及第 14 章（"context"这个名字是否含糊）、专题 clean-code（依赖倒置 / SOLID 只是顺带提到）
- 性质：真正的分歧 · 仅作背景
- 优先级：B，作者提出了一个书里没有的区分（"有意思的依赖"与"没意思的依赖"），读者对 context 的批评也值得放进反方；但作者自己承认没搞懂 DI，整串没有结论，不能当定论用。后续见 6Vs1trmcq9k，那里作者给了更明确的态度。

## 读者说了什么（转述）

1. **开题**（Kevin Wu Won，[1][3][9]）：DI 框架（由 Guice 带火）基本解决了透传变量。以 Angular 为例：把一个类标成可注入，系统就把它登记进一张全局单例表；谁需要，就在构造函数参数里写上，系统递归地把它造出来塞进去，不用从应用根部一路传下来。[9] 进一步澄清：框架本身就提供了那个"全局桶"，只是应用代码看不见它；配置里只需要说"谁要 LoggerService 就给这个对象"，并不需要逐条写"X 从 S 传到 T"。FormController 的构造函数只写它直接依赖的 FormValidator，看不到 Logger 或 Context。条件是这些类必须交给框架来实例化，不能自己 new。
2. **DI 是原则不是工具；context 容易变成垃圾堆**（andrew，[4]）：这位读者从 Spring XML 时代用到 Guice，说 XML 配置已经过时，现在的 Java 配置方式有编译期检查和模块化。对 context 的批评有两点：(a) 需要很强的纪律，否则很容易滑向"什么依赖都往里扔"，因为把系统结构理顺比往 context 里塞东西难得多；(b) 接口变得不透明——函数收一个 SSL 证书，一看就知道它依赖什么；收一个 context，就不知道了。
3. **DI 解决不了透传，只会把问题藏起来**（Indrit Selimi，[5][8][16]）：DI 这个"原则"很基本，就是用构造函数（而不是浅的 setter）传依赖。[8] 认为 DI 只管"接线"那部分代码，不用框架也能做；并指出书里把 context 经构造函数传给需要它的对象，本身就是 DI。真正的问题在别处："context"不是一个精确的名字——按书自己的标准这该算红旗。[16] 更进一步，说透传变量和 context 的例子违反迪米特法则，是缺了合适的抽象，质问为什么要造一个什么都装的桶。
4. **DI 与 context 是两回事**（Tomasz Masternak，[11][13][14]）：DI 框架做的是把"实例化对象并接线"的样板代码自动化；在 C# 社区有人认为 DI 框架有害——为一件简单的事引入太多魔法。它和依赖倒置（Dependency Inversion）经常被混为一谈，后者是另一回事。[13] 应作者要求不用那两个词来描述问题：依赖关系一变，所有接线代码都要改，这是维护成本；DI 框架省掉的就是这部分。这位读者自己的看法是 DI 多数时候并不降低复杂性，省掉的只是样板。对透传变量有用的不是 DI 而是"接线方式"本身：在 main 里先 `new M3(certificate)`，再把 m3 交给 M2、m2 交给 M1，调用 `m1.m1()` 时就不用再传证书了。代价是可能产生很多短命的对象结构。
5. **连读者自己也说不清**（Andrew Simmons，[7][15]）：推荐 James Shore 的一篇解释文章；后来发现串里各人说的"DI"并不是同一个东西——有人指"不用 new 和工厂来创建实例"，有人指"把变量送到调用链深处的办法"。这位读者说面试常被问到 DI，自己答不上来。
6. **三种做法的优缺点清单**（James Leibert，[17]）：把问题定义成"运行时才知道用接口的哪个实现"（例：开发时写本地日志，生产时发回公司）。构造函数传入——每加一个依赖就要改所有相关构造函数，复杂系统里未必存在满足所有依赖的构造顺序；setter——暴露实现、可能忘记调用、要处理"还没设置"的状态；依赖管理器对象（这位读者理解 Guice 等框架就是这样）——等于一个巨大的全局单例，全局状态的毛病全都有，而且看不清什么代码何时被调用。还提到动态语言和消息传递式语言里这个问题轻得多。
7. **历史与术语**（Paul Hammant，[18]，自称 PicoContainer 共同作者）：应该叫"DI 容器"而不是"框架"；能被全局访问到的容器不算真正的 DI（点名 Angular 和 Spring）；容器应分 application/session/request 作用域，短作用域可依赖长作用域，反之不行；DI 源自 90 年代的控制反转。属于背景。

## 作者的回应

四条：[2][6][10][12]。作者从头到尾都声明自己没有 DI 框架的实际经验，说的话要打折扣。

- **[2] 没有银弹：** 根本问题是信息在一处产生、在很远的另一处使用，任何把信息送过去的办法大概都免不了别扭。作者花半小时上网了解 DI，没看明白，觉得几种做法都增加了不小的复杂性，判断不了比 context 更复杂还是更简单；对 Spring 的 XML 配置印象很差——一个描述所有类所有配置项的巨型文件，看不出模块化。
- **[6] 是全串最有价值的一条：**
  - 把 context 描述成"全局的桶"：信息源往里放，使用方从里拿。**让步**：接受 andrew 的批评，桶会被滥用、变得很乱，必须克制着用（书里 7.5 本来也这么说）。
  - 按当时的理解，作者以为 DI 是由调用链之外的第三方显式列出"信息 X 从源 S 送到目标 T"。由此提出核心疑问：把这类依赖显式化有什么价值？看起来只是多干活。
  - **为 context 辩护的新论据（书里没有）：** 想知道谁在用某个值，用 IDE 查 context 里那个成员变量的所有引用即可；而且全程有类型检查——从 context 里删掉或改掉一个变量，编译器会指出所有要改的地方。
  - **新区分（书里没有）：有意思的依赖 vs 没意思的依赖。** 方法 A 调用方法 B，这条依赖很重要：不知道它就看不懂 A 的实现，所以它应当是显式的（事实上也是，就写在 A 的代码里）。透传变量的那条依赖不一样：不知道它，照样能看懂源头和目标各自在做什么。作者认为，既然这条依赖要靠源头和目标之外的东西来声明，本身就说明它无助于理解系统的结构和行为，因此没必要显式。原话："for pass-through variables, the dependency isn't actually interesting: you don't need to know about the dependency to understand either the source or the target."（John Ousterhout，[6]）
  - 末尾问大家自己是不是漏了什么。Kevin 在 [9] 指出作者对 DI 的理解有误（并不需要逐条列出关系）。
- **[10] 搁置：** 承认自己还是没懂 DI，贴出来的链接帮助不大（Angular 那篇假设了太多背景知识），眼下太忙，先放一放；希望有人能贴一个简单、真正看得懂的解释，尤其要说明它解决什么问题、怎样改进设计。
- **[12] 对"解释"提出要求：** 多数 DI 的定义在定义里反复使用这两个词，成了循环定义。作者要求换一种问法——如果禁止使用 DI，会发生什么坏事？能不能不用"dependency"和"injection"这两个词把问题讲出来？最好给个具体例子。原话："what bad thing will happen if I forbid you from using dependency injection in your system?"（John Ousterhout，[12]）
  - Tomasz 在 [13] 按这个要求作答后，作者没有再回复。

**让步了什么：** context 会被滥用；自己不懂 DI。**坚持了什么：** 没有银弹；看不出把透传类依赖显式化的好处。**没有回应的：** Indrit 关于"context 这个名字不精确"的批评；Tomasz 的"在 main 里预先接线"（四年后在 6Vs1trmcq9k [4] 里作者才给出否定理由：这样 main 必须知道整条调用链）。
