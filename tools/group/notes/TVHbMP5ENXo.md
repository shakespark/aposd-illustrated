# a small worked example

- 原帖：https://groups.google.com/g/software-design-book/c/TVHbMP5ENXo
- 精读：2026-10-03，读到第 8 条（2026-02-26 ～ 2026-03-13）
- 主题：同一个小程序（给 Markdown 标题行加章节编号）的"一个函数写完"与"拆成两个类"两种实现，哪个更简单；作者逐条点评了拆类版本的毛病。
- 对应：第 4 章（4.4 深模块、4.5 浅模块）/ 第 9 章 9.7（方法的拆与合）/ 第 5 章（信息泄漏、时序耦合）/ 第 6 章（通用模块，仅读者提到）/ 第 13 章 13.5（接口注释）/ 训练场 / 专题 clean-code
- 性质：可改编成训练题的例子 · 真正的分歧
- 优先级：A。完整的"小例子 + 作者两轮具体点评 + 读者反驳 + 加需求后的对比"，是这批里最适合直接改编成训练题的一串。

## 读者说了什么（转述）

1. **出题**（Paul Becker，[1]）：给出两份 Python 实现，都不带任何注释，问哪份更简单。实现 1 是一个约 18 行的函数：循环读行，用正则认出标题行，维护一个"各级计数器"列表（比当前级别深的弹掉、不够深的补 0、当前级加 1），拼出 `1.2.3` 这样的前缀插回行里。实现 2 把同样的逻辑拆成主函数 + `MarkdownHeader`（解析、加前缀）+ `NumberedSections`（计数），主循环缩到约 10 行。
2. **"只看主函数短不短"是错的量法**（Shreevatsa R，[2]）：这位读者认为 Clean Code 一派会选实现 2，因为主函数短，却没算维护者要多理解三个接口的代价。把两个类挪进函数内部（2a）后主函数变成 39 行，可读性优势就不见了。又给出 1a：实现 1 加上函数头注释（带输入输出示例）、计数器变量的注释和更清楚的变量名。排序是 1a > 1 >> 2a > 2。
3. **出题人的自我检讨与第 3 版**（Paul Becker，[4]）：转述一位朋友的反问——以后要加链接检查、风格检查之类的预处理，你愿意从哪一版开始改？并承认实现 2 的抽象不好：`MarkdownHeader` 不够通用，`NumberedSections` 应该把"级别"藏在内部；当时只顾"分离关注点"，没想过主函数单独读起来难不难、类到底该隐藏什么。还说这些毛病是给别人看了代码之后才看出来的。第 3 版让 `NumberedSections` 对外只提供"是不是标题行""给标题行加编号"两个方法，`HeaderLine` 变成（级别，文本）的数据类。实现 1 里文件处理、编号、标题行格式三件事缠在一起，是这位读者想拆的原因。
4. **另一个方向的重写**（Ivan Yordanov，[5]）：批评第 3 版三点——解析失败返回 `None` 逼调用方判空（引书里"消除特殊情况"）、违反 Tell, Don't Ask、标题行被解析两次。给了两版改写，第二版把调用层次反过来（`HeaderLine` 持有 `NumberedSection`），主循环只剩一行调用。这位读者自己也承认第一版改写里那一行嵌套调用很难看。
5. **出题人对作者点评的回应**（Paul Becker，[7]）：
   - 不接受把 `parse` 拆成"判断"和"构造"两个函数，理由是 "parse, don't validate"：拆开会让判断逻辑和错误处理各写一遍。
   - 接受"必须按顺序调用"的批评，但认为加一句接口注释说明"这是流式处理器，必须按顺序对每个标题行调用"就够了。
   - `HeaderLine` 的 `level`、`text` 本来就是它的接口，它是个数据类。
   - 实际做了一次扩展对比：在实现 1 和实现 3 上各加"目录（TOC）+ 锚点"功能，贴出两份代码（这次带了注释和 docstring）。
   - 感想：接口占地方（代码里和脑子里），但也划出边界。原话：
     > "interfaces take up space, both in the code and in the mind. But they also *create* space."（Paul Becker，[7]）
   - 提出"熟悉度"问题：同样的接口，熟悉这种风格的人读起来就轻松；所以认知负荷这类复杂性症状，可能因人而异。
6. **只抽计数器的折中方案**（Felix Leipold，[8]）：实现 1 里 `numbers` 列表的"接口"太宽（谁都能随便增删改），实现 2 的 `NumberedSections` 想解决的正是这个，但名字没说清它是什么——它不是"章节"，而是一个多级计数器。建议只抽出一个 `MultiLevelCounter`（"在某级加一""取当前字符串"两个方法，带文档），标题行处理留在主函数里；`MarkdownHeader` 只是多了些词汇，不值得。这位读者把它联系到第 6 章：把子问题推广一下（版本号 major/minor/patch 也是这种计数），不只为了复用，还会逼出更干净的实现。给了两个判断"该不该抽出来"的问题：假想有什么通用库能让这段脚本好写？抽出来的东西我想不想给它单独写单元测试？

## 作者的回应

作者发了两条（[3]、[6]），都很具体。

**[3] 对实现 1 与实现 2：**
- 选实现 1，说即使没有注释也比较容易懂。
- 实现 2 让作者看得头晕，没完全看懂就放弃了：代码多了很多，类的用途不明显。至少需要文档说明这两个类提供什么抽象；但作者认为这些"抽象"本身让代码更难懂而不是更易懂。
- 核心论证（针对主循环里调 `next_at_level` 和 `with_prefix` 的两行）：光看这两行不知道这两个方法做什么，只能去读方法体；既然还是得读方法体，把代码抽出去就没有好处，全放在一处反而好懂。作者补了一句：如果方法有文档，也许文档能让这一点变明显——但按现状不行。
- 结论：问题本身很简单，实现 2 把它弄复杂了。

**[6] 对实现 3，逐条：**
- 总体仍比实现 1 长、难懂。是否更易扩展，作者说看不出来，而且**不知道扩展是什么就没法判断**；所以会选实现 1，等将来的扩展真的需要时再重构。原话：
  > "I'd probably go with implementation 1 and be prepared to refactor in the future if extensions require it."（John Ousterhout，[6]）
- `HeaderLine.parse` 实际上是两个函数揉成一个：一个判断"是不是标题行"，一个根据行构造对象；两种用法各只出现一处，为什么不拆成一个"检查函数"加一个构造函数？
- `add_section_number_to_header` 有名字里看不出的**隐藏副作用**：它不只是给这一行加编号，还在累积用来算编号的表。所以它只有在"对每个标题行、按顺序、恰好调用一次"时才正确；漏掉一行、或拿文件中间随便一行来调用，就不对。结果是这个方法和主函数的循环**纠缠**在一起，只能按那个循环的方式用。
- 这个方法伸手进 `HeaderLine` 取 `text`、`level` 字段，还改了 `text`，于是两个类也纠缠在一起。
- 总评：要看懂只能把主函数和两个类同时装进脑子，这说明这些类没提供多少抽象或模块化。

**作者没有回应的**：Paul Becker 在 [7] 的三点反驳和 TOC 扩展对比、Felix Leipold 在 [8] 的 `MultiLevelCounter` 方案，作者都未再回复。所以"实现 1 加了 TOC 之后还是不是更好""只抽计数器算不算深模块"这两个问题，串里没有作者的答案。

**书里没有的新说法**：
- "方法没文档 → 调用处读不懂 → 只能读方法体 → 那抽出来图什么"这条推理链，是对 9.7（拆方法的条件）的一个很短的实操版判据。
- "隐藏的调用顺序约束使方法和调用者的循环纠缠"——书里讲时序分解导致信息泄漏（5.3）和 conjoined methods（9.7），但没有"有状态的方法名字像无状态的"这个角度的例子。
- "看不出扩展是什么，就别为扩展预先拆"——比书里 6.1 "somewhat general-purpose" 的表述更偏保守。

## 挂到站点哪里

- **训练场（首选）**：改编成一道"三选一 + 说理由"的题，再加一道追问题。原创一段 C++（或保持 Python 思路但自己写）：给文本的标题行加层级编号，A = 单函数，B = 拆两个类，C = 只抽多级计数器。先让读者选，再给出作者对 B 的四条批评（隐藏副作用/顺序约束、两个类互相伸手、一个函数两件事、必须全部装进脑子），最后摆出串里**未决**的两点：加 TOC 需求后怎么看；C 方案算不算"通用模块更深"。不照搬原帖代码。
- 第 9 章 9.7：加一个"边界与反方"小框——作者的判据"如果读调用处还得去读方法体，拆分就没带来好处"，配上 Paul Becker 的反方（接口占地方，但也划边界；为将来长大做准备）。
- 第 5 章：`add_section_number_to_header` 作为"名字看不出的状态与顺序依赖"的例子；并列 Paul Becker 的回应"在接口注释里写明必须顺序调用"（这正好接 13.5：接口注释要写副作用和调用前提）。
- 第 4 章：Shreevatsa R 的"主函数从 18 行变 10 行，但要多懂三个接口"作为"浅模块的总成本"的一句话例子。
- 专题 clean-code：可引用 Shreevatsa R 的 1a > 1 >> 2a > 2 排序，说明"加注释的不拆版"是 APOSD 式的答案。注意"Clean Code 一派会选 2"是这位读者的推测，不是 Martin 说的。
- 第 6 章：Felix Leipold 的两个自问（"假想什么通用库能让这段脚本好写""抽出来的东西值不值得单独写测试"）可作为读者补充，标明不是作者说的。

## 待核实

- Felix Leipold 的 `MultiLevelCounter` 里，`increment_at` 的文档写级别"从 0 开始"，但代码用的是 `level - 1`（实际从 1 开始）；另外这版在 `#` 后多插了一个空格，输出和实现 1 不完全一样。这是我读代码看到的，没有实际运行。
- Ivan Yordanov 两版改写是否与实现 1 输出一致，没有验证（第二版对非标题行做了 `strip()` 再补换行，看起来会改变原文的行首行尾空白）。
- Paul Becker 的"实现 1 + TOC"与"实现 3 + TOC"两份代码没有运行过；若训练题要用"加需求后对比"的结论，需要自己写一遍再下结论。
- 所有实现用的正则只匹配行首连续的 `#`，代码块里的 `#` 注释行也会被当成标题——串里没人提，改编时自己注意。
