# Note on Implementation Comments

- 原帖：https://groups.google.com/g/software-design-book/c/TTPivcnXqd4
- 精读：2026-10-03，读到第 4 条（2019-06-13 ～ 2019-06-13）
- 主题：13.2 节把"// Add a horizontal scroll bar"这类注释当作重复代码的反例；读者指出实现注释还有"导航"的用途，短短的分段标题式注释是有用的。随后争论：与其加这种注释，要不要把那段代码抽成一个函数。
- 对应：第 13 章 13.2（不要重复代码）、13.6（实现注释）；次要：第 9 章 9.7～9.8（要不要拆方法）、专题 clean-code
- 性质：勘误或澄清 · 真正的分歧
- 优先级：B。作者接受了读者的补充（导航用的短注释"听起来很好"），不过对照本地第 2 版，13.6 节正文已经写着分段注释能帮读者在代码里导航，所以"导航"这一点书里其实有（是否为 2019 年之后才加，未核对）。真正的新东西是一句很干脆的判据——缺的是注释就加注释，别为此新建函数——正对着《Clean Code》"用函数名代替注释"的做法，而且早于那场书面辩论；站点第 13 章块和 clean-code 专题都还没有这一句。

## 读者说了什么（转述）

1. **开帖**（William Duquette，[1]）：实现注释有两个用途，理解和导航，书里的讨论忽略了后者。它帮新来的人看懂代码，也帮熟悉代码的人快速定位；在会把注释显示成另一种颜色的编辑器里，注释自然地把一个长函数分成几块，不必读全部代码就能找到要的那段。就书里的例子而言，这位读者会写一个很短的"// Scroll Bars"，作为创建和配置滚动条那五六行代码的小标题。
2. **换成函数**（Peter Ludemann，[2]）：既然是五六行，为什么不抽成一个名字起得有意义的函数（比如"设置滚动条"）？代码更清爽，文档也有了。
3. **对作者的反驳**（Peter，[4]）：一件接一件往下做的代码（搭界面时常见），除了函数太长，还会让局部变量越来越多。可以用花括号把每段包起来限制作用域，但仍然难以追踪函数级的局部变量在哪些地方被用到；抽成函数能把"变量在哪里用"这一信息封装起来。还指出 Python 里花括号这招用不了，局部变量的作用域总是整个函数。作者没有再回。

## 作者的回应

作者只有 1 条：[3]，两段，整段回复（对照 full 文件，引文都在正文之后）。

**让步 / 澄清**

- 认为 William 提的短小导航注释很好。关键是注释要有实际用处；能让浏览代码更容易，就是有用。
- 这与书并不矛盾，但书里两处读起来有张力：13.2 说那几条滚动条注释毫无价值（第 2 版原文未改）；13.6 又建议在长方法的每个主要代码块前加一条较抽象的注释，并说这类注释帮助读者在代码里导航、找到关心的部分。合起来的读法是：**一行代码配一行同义注释是重复；一条短注释盖住一段代码、起小标题作用，是 13.6 认可的做法。** William 说书"忽略了导航"，就第 2 版的 13.6 而言并不成立。

**坚持 / 新说法**

- 对"抽成函数"不太赞成："If what's needed is a comment, add a comment, not a new function."（John Ousterhout）
- 一个分成许多段、每段前面有一条简单注释的方法，可以相当好读；作者自己常常觉得这样全放在一处，比拆散到许多函数里更容易读。
- **判据**：要不要把代码移到新函数里，应当根据结构和复杂性方面的考虑来决定，而不是因为那里需要一条注释。

**作者没有回应的**：Peter 在 [4] 提的局部变量扩散问题——这其实正是一条"结构/复杂性方面"的理由，按作者自己的判据是可以成为抽函数的正当理由的，但作者没有接这个话。

## 挂到站点哪里

- **第 13 章 13.2 / 13.6"边界与反方"**：在现有讨论组块后加一两句即可（**与书的 13.6 及该块已有内容部分重复**：块里已有作者"方法内部的注释成块地放在每个主要代码段之前"的习惯）。可写的是：有读者觉得 13.2 的滚动条反例把"小标题式注释"也否定了，作者在讨论组里明确说这种导航用的短注释很好（2019-06）；13.2 反对的是逐行复述，不是分段标题。
- **专题 clean-code、第 9 章 9.7**：作者那句判据值得引用——Martin 一派的做法是"需要注释的地方说明该抽函数"，作者的回答是两件事要分开判断。站点 clean-code 专题"关于方法长度"一节可以加这一条（2019-06），现有条目里没有。
- 反方要一起写上：Peter Ludemann 的局部变量论据是抽函数一方较强的理由（读者的话），而且符合作者自己说的"结构上的考虑"。
- **训练场**：可出一道判断题（原创 C++）：一个按顺序搭建若干部件的长函数，给三种改法——逐行注释、分段小标题注释、每段抽成函数——再给两个变体（各段之间共享很多局部变量 / 各段基本独立），问哪种改法在哪个变体下更好。
