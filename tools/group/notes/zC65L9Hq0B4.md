# Thoughts on fork()

- 原帖：https://groups.google.com/g/software-design-book/c/zC65L9Hq0B4
- 精读：2026-10-03，读到第 7 条（2022-08-18 ～ 2022-12-05）
- 主题：POSIX 的 fork() 算不算一个简单的接口；作者把问题理解为"fork/exec 两步"对"CreateProcess 一步到位"，并用"把复杂性往下拉"为前者辩护；一位读者唱反调并指出还有第三种设计。末尾两条转到线程与进程。
- 对应：专题 ostep（进程 API：fork/exec）；第 8 章（把复杂性往下拉）；第 4 章（接口简单 vs 参数爆炸）；第 20 章（简单接口的性能代价，写时复制）；训练场
- 性质：真正的分歧 + 可改编成训练题的例子
- 优先级：A。作者用书里的原则分析了一个书里没有的经典操作系统接口，并明确说出取舍；反方（Dan Cross）的论据同样扎实。专题 ostep 目前没有任何讨论组材料，也没有 fork/exec 的内容，这一串可以直接补上。

## 读者说了什么（转述）

1. **提问**（Jonathan Camenisch，[1]）：很多人称 fork() "简单"，但读完文档里的各种情形和边角之后，怀疑它是否真的像应有的那样简单（窄）。
2. **要和 exec 一起看**（Brent Welch，[2]）：fork 之后子进程设置好文件描述符再调 exec，实际没人单独用 fork，应当按这个用法来评价。
3. **反方**（Dan Cross，[4]）：
   - fork 起初简单，后来（借用一场 OSDI 2021 主题演讲的说法）"凝结"成了糟糕的接口。引 HotOS 2019 的一篇论文：慢、与几乎任何其他操作都不可交换、和线程配合很差、从父进程继承来的状态可能需要清理。
   - 承认 fork+exec 的好处：能在启动程序之前布置子进程的环境，做管道、重定向。
   - spawn 式的调用避开了 fork 的很多问题，但要把进程所有可能的状态都做成参数，接口笨重（让读者去看 `posix_spawn` 的手册）。
   - **"fork 的替代品只有 spawn"是假二分**。第三种：先创建一个尚不可运行的进程，再用一组调用去操作它，最后标记为可运行。举研究系统 Akaros 为例：一个调用按文件名、参数、环境创建已加载程序但不可调度的进程，父进程随后用别的系统调用调整它的文件描述符等，最后让它运行。更进一步可以创建一个真正空的进程，连地址空间都在创建后布置，这样可执行文件的解析和加载可以完全放在用户态。
   - 这种设计带来的问题（谁有权操作别的进程的状态、开始运行后还能不能改），这位读者认为不难给出合理规则：父进程在子进程被调度之前可以操作，之后不行。
   - 结论："they are conceptually simple until they aren't"（Dan Cross）。
4. [5] 提问者致谢，称这是一个有意思的接口设计难题。
5. **线程**（Peter Ludemann，[6]；**这一条在本地文件里正文缺失，以下据 [7] 的引文转述**）：POSIX 线程在某些方面像 CreateProcess（传一个函数指针来创建），在另一些方面像 fork（能访问对方的内存，所以不需要一大堆选项）。如果有纪律只用消息队列、不用共享内存和互斥锁，线程似乎两头的好处都占；但各有地址空间的进程更安全。还提到声明式语言的闭包不可变所以更安全，并附了作者旧作《Why Threads are a Bad Idea》的指引。
6. **进程不只是地址空间不同**（Dan Cross，[7]）：进程之间还可以有不同的凭据、能力、命名空间（容器、chroot）、环境变量、调度属性、资源限制；很多东西是进程全局的，线程之间必然共享。认为 Peter 描述的"只用消息队列"基本就是 Go 的并发模型。对作者那份旧幻灯片，回敬了两篇为线程辩护、以及线程与事件并用的论文。

## 作者的回应

作者 1 条：[3]。

**立场：喜欢 fork/exec**

- 先确认问题：是不是指 Unix/Linux 的 fork 与 exec 分开，对比 Windows 的 CreateProcess 一步到位。
- 喜欢分开的理由：两个系统调用各自都简单；父进程可以在两次调用之间任意修改子进程的环境（I/O 重定向、改工作目录等）。
- **承认的代价**：最直接的实现很低效——fork 要复制父进程的全部状态，几微秒后 exec 又把它丢掉。要让它实用，底层系统得承担不少额外的复杂性来避免复制（例如写时复制的虚拟内存）；而且即使用了写时复制，也可能更慢。
- **结论用的是书里的原则**：对使用者干净简单，对底层系统的建造者更费事，"I am comfortable with that tradeoff: pull complexity downwards."（John Ousterhout）

**对一步到位方案的批评（书里没有的例子）**

- 容易高效实现，但使用者用起来别扭：CreateProcess 的接口很复杂，子进程可能和父进程不同的每一种方式都要一个参数。
- **难以演进**：想增加一种定制子进程的新方式，就得给 CreateProcess 加参数。fork/exec 下则可以新增一个独立的系统调用，只有需要它的程序才会调用。

**留的余地**

- 最后说这大概是一个人们会永远争下去的取舍。

**没有回应的**

- Dan Cross 的全部反驳：fork 与线程的交互、继承状态要清理、以及"先建空进程再配置"的第三种设计。作者在 [3] 之后没有再发言（[3] 与 [4] 同一天，[4] 不是对 [3] 的回复而是对原帖的回复）。
- 末尾关于线程的两条，包括对作者旧幻灯片的回敬。

## 挂到站点哪里

- **topics/ostep.html（目前没有讨论组材料，也没有 fork/exec 的内容）**：新开一节"用 APOSD 的眼光看 fork/exec"。OSTEP 在进程 API 一章里正面夸过 fork/exec 分开的设计，可以把三方摆在一起：作者的理由（两个简单调用 + 中间任意定制；新功能加新调用而不是加参数；代价由内核承担）；反方的理由（与线程、与继承状态的交互让它"简单到不简单为止"）；第三种设计（建一个不可运行的进程，配置好再启动）。这是"同一个接口，深不深取决于你用到多少边角"的又一个例子，和页里已有的 fsync 讨论（OCSMlVYmQTE，挂在第 4 章）可以互相引用。
- **第 8 章"边界与反方"**：作为"把复杂性往下拉"的操作系统级实例，同时也是 8.3"做过头"的讨论素材——往下拉的复杂性（写时复制）并没有完全藏住，fork 的性能和它与线程的交互都漏到了使用者面前。现有块只有配置参数一条，这是新内容。
- 第 4 章可带一句：一个调用带一大堆参数（CreateProcess / posix_spawn）与一组小调用的对比，作者选后者的理由是"用不到的人不必知道"，和页里 fsync 一段的逻辑一致。
- 训练场：设计题（原创 C++）。给一个 `spawn(path, args, SpawnOptions)`，`SpawnOptions` 有十几个字段；要求比较三种接口形状：一步到位加选项结构体、fork/exec 式、"建好—配置—启动"式，分别回答"新增一种定制方式要改哪里""不关心这项定制的调用者要不要知道它"。
- 末尾线程与进程的两条：与本书关系不大，作者未参与，不挂。
