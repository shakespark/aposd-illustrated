## 读者说了什么（转述）

1. **开帖**（Eric Smith，[1]）：只贴了自己博客书评的链接，说里面有一些亲身经历，书里的原则本可以帮自己避免一个失败的项目。博客内容不在文件里。
2. **注释**（Steven Rose，[2]）：以前信 Robert Martin 的"注释是失败"，后来和别的优秀开发者共事、接手新系统时体会到好注释的价值。现在大体同意书的看法：注释应说"为什么"，很少说"做了什么 / 怎么做"；需要解释"怎么做"多半说明代码该重写。例外是为性能优化过的或位运算密集的代码。
3. **两个与测试结合的做法**（Steven Rose，[2]）：
   - 对难读的优化代码，除常规单元测试外，再把"本来想写的那个易读的逐步版本"放进测试里，断言两者输出一致——既验证又充当文档。
   - 方法文档里的用法示例，都用真正的单元测试覆盖，并在文档里指向这些测试，避免示例过期。
4. **关于拆长方法的不同做法**（Steven Rose，[2]）：这位读者认为差异来自语境不同而非谁对谁错。所在项目大量使用依赖注入，采用"工具类（全是静态纯函数）+ 辅助类（需要状态，靠构造函数注入）"的模式，把"工具性代码"从业务类里搬出去。给出的好处：
   - **几乎不留私有方法**：只接受相当于宏的一行替身或很简单的条件判断；稍复杂的都放到非私有方法里以便单独做单元测试。
   - **工具/辅助类充当"本地词汇表"**：读一遍它们的 API 就知道这个模块关心什么，业务逻辑读起来停留在高抽象层。
   - **依赖管理**（这位读者认为最重要）：抽出后，业务类原本直接依赖的二十来个包里有不少转移到工具类，业务类只通过工具类间接依赖；并尽量让工具类和辅助类的依赖互不相交。
   这位读者同时承认：多数重度使用依赖注入的项目用得不对，反而增加复杂性。

## 作者的回应

一条（[3]），只针对"拆长方法"：

- **澄清立场**：作者说自己完全赞成拆长方法，只要能拆得干净。书里想说的只是拆了不一定更好，并举了两种情形：实现本身已经分解成相对独立的几部分；或者拆开后得到的几个方法彼此纠缠。
- **给了一句定性的话**：要盯住的目标是降低复杂性——

  > "breaking up long methods can be a means to that end, but it is not an end in itself."（John Ousterhout，[3]）

- **没有回应的**：注释部分；把易读版本放进测试的做法；"不留私有方法、为了可测试而公开"；工具类/辅助类模式和依赖管理的论点。尤其是"为了测试把方法从私有改成公开"和"一堆静态工具类"，按书的标准很可能被看作扩大接口、制造浅模块，但作者在这里没有评论——不能替作者下结论。
