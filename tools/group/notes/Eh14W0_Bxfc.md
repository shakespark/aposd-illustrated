# Thank you and two questions about the book

- 原帖：https://groups.google.com/g/software-design-book/c/Eh14W0_Bxfc
- 精读：2026-10-03，读到第 3 条（2024-02-23 ～ 2024-03-05）
- 主题：读者问两件事——设计是否应当同时从问题领域的建模（DDD、Grammar of Graphics）和代码两头入手；深类会不会让单元测试的准备和维护成本变高（Java 社区拆小类、靠 IoC 加 mock 的做法正是为了压低这项成本）。作者只回答了后者。
- 对应：第 19 章 19.3（单元测试）；第 4 章（深与浅、4.6 类过多症）；专题 clean-code；领域建模一问无对应章节
- 性质：真正的分歧
- 优先级：B。作者把"浅类是否更好测"拆成两问并分别作答，是站点现有测试材料里没有的说法；但领域建模那一问作者直接说不懂，整串只有一条实质回复。

## 读者说了什么（转述）

1. **领域建模**（Lukasz Bartnik，[1]）：觉得这本书关注的是代码本身的设计，较少谈软件要模拟的问题领域。举了《领域驱动设计》（实体、值对象、聚合、限界上下文、通用语言、"深模型"）和《The Grammar of Graphics》（ggplot2 是它的成功实现）两本书，共同点是为问题领域找到最好的概念划分。这位读者设想：照本书的原则反复试验模块划分，最后模块会对上领域专家用的名词、动词、形容词。于是问：是否应当两头并进，一头学会系统地描述问题领域，一头照书里的办法在代码上试验？
2. **可测试性**（Lukasz，[1]）：经验是，不为单元测试而设计的代码，类和方法会膨胀、行为搅在一起，测试准备（构造输入、把对象摆到所需状态）很贵；团队人多、流动率高时，大家就不愿写测试。由此理解 Java 社区为什么把代码拆成很多小类：A 依赖 B、C、D，运行时由 IoC 容器自动装配，测试时让 mock 库自动生成 B、C、D 的替身。这位读者自己承认这让系统怎么装起来变得不明显（用了书里的"隐晦"一词），但测试准备简单得多。问作者：把测试准备和维护成本算进去之后，对设计有没有额外建议。
3. **补充**（Artem Shevchenko，[3]）：针对作者的 (a) 问——如果按方法写测试，浅函数可能好测些；如果按行为写测试，多半没区别。推荐《Software Engineering at Google》的单元测试和测试替身两章。

## 作者的回应

作者 1 条：[2]（整段回复，已对照 full.txt，不是插话式）。

**没有回答的**

- 领域建模：直说没有 DDD 和 Grammar of Graphics 的经验，无法评论。

**坚持**

- 自己用深类写单元测试没遇到过大问题。用过的测试框架都能为一个类写共享的准备代码，供该类所有方法的测试使用；写这些准备代码不算费时。
- mock 下层模块确实要花时间和心思。作者没量过成本，给的是经验判断：一开始投入不小，建好以后维护成本很低，放在整个项目周期里不算显著。

**书里没有的新说法**

- **浅类对测试是两面的**：接口多了，可供测试切入的点多了；但接口多了，要 mock 的也可能更多，要写的测试多半也更多。
- **把问题拆成两问**：(a) 用浅类写单元测试是不是更容易？(b) 就算更容易，够不够抵消浅类带来的其他工程成本？作者的回答是 (a) 不知道，(b)"unlikely"（John Ousterhout）。

也就是说，作者没有否认读者描述的现象，只是认为即使成立也不足以改变结论。

## 挂到站点哪里

- **第 19 章"边界与反方"的讨论组块**：现有"单元测试会不会把结构冻住"一条（2023-04）说的是维护成本，专题页 2020-07 一条说过"小方法更好测，但要测的也更多"。这一串可以补成第三条：读者给出了 Java 社区拆小类的最好理由（测试准备便宜、IoC 加 mock），作者的 (a)/(b) 两问是回应它的现成框架。与已有内容**部分重复**（"接口多、测试也多"），新的是两问的拆法和"mock 一次投入、长期便宜"的经验判断。
- 可与 DofyDeG57yo（浅模块 + 大量单元测试 = 改不动）并列：一位读者说浅类让测试便宜，另一位说浅类让测试把结构钉死，正好是两面。
- Artem 的"按方法测 vs 按行为测"值得作为读者意见带一句：它解释了为什么 (a) 的答案取决于测试风格。
- 领域建模一问：站点没有对应章节，作者也没答；可在"怎么读这本书"之类的地方提一句"本书不谈领域建模，作者自己也这么说"，可有可无。
