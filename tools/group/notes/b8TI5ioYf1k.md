# Interface vs. Concrete Type Declaration for a Variable

- 原帖：https://groups.google.com/g/software-design-book/c/b8TI5ioYf1k
- 精读：2026-10-03，读到第 5 条（2019-01-25 ～ 2019-02-05）
- 主题：18.2 节反对"声明为 `List`、实际分配 `ArrayList`"的写法；读者指出这是面向接口编程的常规做法，有明确好处。
- 对应：第 18 章 18.2（声明与分配的类型不一致）；次要：第 19 章 19.1（面向对象）、专题 clean-code（SOLID）。**第 18 章目前没有讨论组材料，这一串可以补上。**
- 性质：真正的分歧 · 勘误或澄清
- 优先级：A。作者自己说这不是最在意的问题、并不强烈反对读者；被指出 `List` 是接口不能实例化之后承认疏忽，并把书里一刀切的建议改成了有条件的：不在乎具体是哪种 List，就声明为 List；在乎，就声明为具体类型。这是对 18.2 的实质修正，而第 2 版正文没有改。

## 读者说了什么（转述）

1. **开帖**（Reuven Yagel，[1]）：这种写法是 Java 和其他面向对象语言里的常见惯用法，好处有三：
   - 变量只能按接口的契约来用，更抽象；
   - 将来换成另一个实现该接口的类型，其余代码不用动；
   - 更符合开闭、里氏替换、依赖倒置这些原则——其余代码只依赖 `List` 这个抽象。
   另外 Java 标准库自己也倾向返回更抽象的类型（如 `Arrays.asList`）。这位读者认为这些好处压过了"类型与实际类不一致"带来的那点割裂。顺带建议书里专门把这些 SOLID 原则拿来对照（比如放在讲设计模式的那一章之后）。
2. **折中**（Peter Ludemann，[3]）：反过来说，有时就是只想用 `List` 的操作，以便将来换成别的实现；选 `ArrayList` 的原因（比如内存占用）正适合用一条注释说明。不过总体上同意作者，并嫌 Java 里两边都写 `ArrayList` 的写法啰嗦。
3. **指出作者回帖里的错误**（Reuven，[4]）：作者说"不在乎就直接实例化一个 `List`"，可是 `new List()` 不是合法的 Java——`List` 是接口，不能实例化。

## 作者的回应

作者共 2 条：[2]、[5]。都是整段回复。

**先说明分量**

- [2] 这不是作者最在意的问题之一，对读者的几点也并不强烈反对。

**[2] 的论证（书里只有一句话，这里展开了）**

- 关键问题是：实际的值是 `List` 还是 `ArrayList`，要紧吗？作者猜多数情况下要紧——`ArrayList` 有它的性能特点。既然要紧，所有人就都该知道它是 `ArrayList`，才能去用在它上面高效的操作；把类型藏起来，是不给人使用这个对象时需要的信息。
- 如果真的不要紧，那为什么不干脆把它实例化成 `List`，让两边一致？声明一种、实例化另一种，在作者看来自相矛盾：一边说类型差别要紧（所以才分配更具体的类型），一边又说谁也不必知道。

**让步**

- [5] 被指出 `List` 不能实例化后："Good point; I missed that."（John Ousterhout）
- [5] 修正后的立场是有条件的：**如果确实不在乎它是哪一种 List，那么声明为 `List`、实例是别的类型，是说得通的；如果它是 `ArrayList` 这件事要紧，声明就应当反映出来。** 作者说自己的答案"大体不变"，但这已经不同于书里"声明最好与分配一致"的无条件说法。

**作者没有回应的**：SOLID / 开闭 / 依赖倒置的论据；把 SOLID 与本书对照的建议（作者后来在 2025 年与 Robert Martin 的书面辩论里做了一部分，见专题 clean-code）；Peter 的"用注释说明为什么选这个实现"。

## 挂到站点哪里

- **第 18 章"边界与反方"**（目前为空，**特别标出**）：新建"讨论组 · 读者质疑 / 作者补充"块。写法建议：
  - 18.2 这一条是全书少数直接与"面向接口编程"的常规做法相冲突的建议。读者一方的三条理由。
  - 作者的回答把问题换成了一个判据：**这个变量的使用者需不需要知道具体类型？** 需要（依赖随机访问是 O(1)、依赖线程安全性质）→ 声明具体类型；不需要 → 声明接口没问题。并承认书里的说法没考虑到接口不能实例化。
  - 可以接一句本站看法：这与第 5 章信息隐藏的标准是同一个——藏起来的应当是使用者不需要的信息。C++ 里对应的是成员声明成 `std::vector<T>` 还是某个抽象的序列接口，或者 `auto` 该不该用。
- **训练场**：可出一道判断题（原创 C++）：给几处声明——函数参数收 `std::span<const T>` / 成员变量声明为抽象基类指针而实际持有某个具体派生类 / 局部变量 `auto`——让读者判断哪些地方具体类型"要紧"、藏起来会误导读者，哪些地方藏起来正好。
- 专题 clean-code 的 SRP/SOLID 一节可加一个链接：2019 年已有读者建议作者正面对照 SOLID。

## 待核实

- 本地第 2 版 18.2 节原文仍是无条件的建议（声明最好与分配一致），并把 `List` 称作 `ArrayList` 的"superclass"；Java 里 `List` 是接口。作者 2019 年的这次修正没有体现在第 2 版正文里——这是对照本地文本得出的，没有对照第 1 版。
- 作者说"ArrayList 相对 List 有性能优势"，严格说是相对其他 List 实现；回帖里措辞不严，引用时按意思转述即可。
