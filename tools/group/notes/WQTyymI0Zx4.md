# Enforcing properties via code instead of by convention

- 原帖：https://groups.google.com/g/software-design-book/c/WQTyymI0Zx4
- 精读：2026-10-03，读到第 3 条（2022-08-03 ～ 2022-08-03）
- 主题：14.1 节那个文件块号 / 磁盘块号混用的 bug，该靠起名字还是靠给两种块号各定义一个类型来防；推而广之，要不要把"能让代码强制的性质就别靠约定"写成一条设计原则。
- 对应：第 14 章 14.1（坏名字导致 bug）；次要：第 10 章（让错误无从发生）、第 5 章 5.3（时序）、第 4 章 4.5（浅类型也是浅模块）
- 性质：勘误或澄清 + 真正的分歧（程度上的）
- 优先级：B。作者说已记下要在下次修订时把 typedef 写成 14.1 的另一种（"也许更好的"）解法，这是明确的"会改"；并给了书里没有的两点——薄包装类型的代价具体是什么、时序要求本身就是复杂性。站点第 14 章已有 2023 年同一话题的一段，所以与已有内容部分重复，不到 A。

## 读者说了什么（转述）

1. **Adam Morrison（[1]）**，正准备在自己系里开一门仿 CS 190 的课。主张 14.1 的问题不该靠变量名解决，而该用两个不同的类型：在 C 里各用一个只含一个 32 位整数成员的结构体。这样赋值、传参时混用会直接编译失败，区别在代码里一目了然，也不必费神维持命名约定。
2. 同一条进一步提议一条总原则：系统的性质尽可能由代码强制，而不是靠约定。又举两例：接口设计上强制先后次序（必须先 open 拿到文件描述符才能读写）；用断言表达方法的前置、后置条件。
3. **Artem（Artie）Shevchenko（[2]）**：附议并补例——"当它不可变"的集合在后续修改面前很脆弱，应当用真正的不可变集合库；Java 里靠约定把变量都当 final 也脆弱，这位读者认为大概只能换到区分 var / val 的 Kotlin。让编译器（至少运行时检查）来保证，能减轻读、调、改代码时的认知负担。

## 作者的回应

作者只有 [3] 一条（整段回复，不是逐段插话）。

**接受**

- 让编译器能查出错误（如 typedef）：总体赞成。
- **会改书**：已给自己留了备忘，下次修订时把 typedef 作为块号命名问题的另一种解法写进去，并称它"也许更好"。原话："mention typedef as an alternate (and maybe even better) solution to the disk block naming problem"（John Ousterhout）
- 时序：越能自动强制越好。

**保留**

- 作者特意说自己是"总体上"而非"热情地"赞成，因为这在有些情况下会增加复杂性。以这两个块号类型为例，代价是两条：
  - 多了两个新的（浅的）类型，可能遮住变量的含义——看到这种类型的变量，也许得点进定义才知道它只是重新包装的整数；
  - 真要拿它做计算时，得去取结构体里的成员，而不能直接用值。
- 随后自己把这个保留收窄：在这个具体例子里额外的复杂性很小，尤其是如果有一套一致的用法——某某 `_t` 总是表示"用于某种专门用途的整数"，内部成员总叫同一个名字。
- **时序要求本身就是复杂性的来源**：其他条件相同时，没有次序要求的接口比有次序要求的更好。也就是说，"强制次序"是次优解，最优是把次序要求设计掉。

**没有回应的**：把"由代码强制而非靠约定"上升为一条独立设计原则的提议；断言；Artem 的不可变集合与 final。

与 2023 年那一串（YHNMr_FgnRY，站点第 14 章已采用）对照：那里作者的保留是"会不会造出一大堆本质都是整数的类型、难以事先判断哪些值得"。这里早一年，态度更积极（答应写进书），保留的理由也更具体（要点进去看、要取成员）。两处合起来才是完整的立场。
