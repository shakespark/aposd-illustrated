# Opinion on using very short and simple functions to encapsulate mathematical operations

- 原帖：https://groups.google.com/g/software-design-book/c/V1guAyS_Jh0
- 精读：2026-10-03，读到第 4 条（2022-12-28 ～ 2023-01-31）
- 主题：图形代码里常见的一两行数学小函数（如"两点距离的平方"）值不值得写；几位读者各给了一个判断标准。作者没有参与。
- 对应：第 4 章（浅模块，4.5）；第 9 章 9.7～9.8；专题 clean-code；次要：第 2 章 2.2（行数不是复杂性的度量）；训练场
- 性质：可改编成训练题的例子 · 仅作背景
- 优先级：C。没有作者发言；"浅函数能不能靠命名／造词汇而有价值"这个问题，已有另一串（Function names as a language，作者亲自回答过）的笔记谈得更充分，这里只多出几个数学例子；那一串的例子目前在站点页面上搜不到，要用应以那一串为主、这一串为辅。

## 读者说了什么（转述）

1. **提问**（Rose K，[1]）：图形代码里常用很短的函数把数学运算包起来，例子是 `distance_squared(a, b)`（先求差再平方）。它没藏多少细节，但有人说放进复杂公式里更好读；这位读者自己不太信，觉得直接写 `square(a-b)` 最好懂。
2. **名字要说"做什么"，函数体说"怎么做"**（Jonathan Camenisch，[2]）：自认偏向小函数一派，但认为这个例子没有价值——`distance_squared` 和 `square(a-b)` 说的是同一件事，"怎么做"并没有被藏起来。认可的小函数是另一类：二维的 `distance(point, point)`，以及 `gross_profit`、`net_profit`、`profit_margin` 这种只有一行、却是值得命名和复用的业务概念。价值在于给系统的"积木"命名并保持定义只有一份。自己也说这可能和"深模块"的想法相悖，是另一种价值。反对的是：随手把一段代码塞进函数，再用代码里的操作给函数起名——猜测这是对 DRY 的误用。
3. **公式的密度**（Paul Becker，[3]）：数学公式信息密度高，很久没碰的人很难从中读出含义；例子是 `angleBetween(a, b)`（点积除以两个模长之积，再取反余弦），放在更大的表达式里比展开写好读得多。这类函数还搭起了一套更高层的工具，就像没人愿意每次手写 `indexOf()` 或 `trim()`。并联系到书第 2 章：复杂性看的是理解它要花多少脑力，不是代码长短。
4. **SICP 的做法**（Joshua Klein，[4]）：《计算机程序的构造和解释》里大量使用只有一行的选择函数和构造函数作为积木；认为这些场合确实有信息隐藏，降低的认知负荷足以值回成本。

## 挂到站点哪里

- 与已有笔记重复：浅函数靠"命名／词汇"获得价值的讨论，Function names as a language 一串的笔记更充分（作者在那里把"词汇"归回到抽象上）；站点页面上目前搜不到那一串的例子。这一串不必单独写一块，若将来把那一串写上站点，可把这里的例子并进去。
- 可取的只有一条判断标准（Jonathan Camenisch，[2]）：名字说的是不是和函数体同一件事。如果名字只是把运算念了一遍，就没藏任何东西；如果名字是一个领域概念（距离、夹角、毛利），即使只有一行也有用。可以在第 4 章讲浅模块处或专题 clean-code 里加一句，注明是读者的说法。
- 训练场：三个例子正好构成一道判断题（原创 C++ 代码，不照搬）——`distance_squared(a, b)`、`angle_between(a, b)`、`profit_margin(...)` 各只有一两行，问哪个值得成为函数、为什么；答案的关键是"名字是否提供了函数体里看不出的概念"，而不是行数。出题前先查训练场里有没有取材于 Function names as a language 的题，避免重复。
