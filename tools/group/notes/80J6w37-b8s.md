# Thoughts on Section 7.5 "Pass-through variables"

- 原帖：https://groups.google.com/g/software-design-book/c/80J6w37-b8s
- 精读：2026-10-03，读到第 3 条（2024-02-15 ～ 2024-02-16）
- 主题：7.5 节透传变量的又一种解法——作用范围限定在"一次请求"（通常对应一个线程）内的 context，例如 Java 的 ThreadLocal；以及把 context 做得尽量局部。
- 对应：第 7 章 7.5（透传变量、context 对象）；次要：第 8 章（把复杂性关在关心它的子系统里）
- 性质：仅作背景
- 优先级：C。作者没有发言。三位读者的意见都合理，但站点第 7 章已有"作用域式 context"和本站补充的 thread_local 注意事项，与已有内容基本重复；只有"用完即弃的子系统级 context"这个小例子算新的。

## 读者说了什么（转述）

1. **Bentley Drake（[1]）**：全局 context 的毛病是可见范围过大、共享过度。常见而好用的折中是"请求内的全局"：对一次请求全局可见，而一次请求通常对应一个执行线程。Java 的 ThreadLocal 对此支持不错。好处是可见范围刚好（一次请求在整条调用栈上共享同一份数据），又避开了并发访问的顾虑。提醒：线程常被池化复用，请求结束时必须清理这些数据。
2. **Daniel T.（[2]）**：需要这份数据的各部分其实处在某个特定的上下文里，只是开发者往往不把这个上下文在代码里表达出来，于是要么一路透传、要么做成全局。如果把上下文定义成代码里的一个对象，数据就放在其中，只对处在这个上下文里的部分可见——这是中间道路。
3. **Venkat Dinavahi（[3]）**：自己的项目里也走到了这个模式，偏好 context 尽量局部，认为这样模块也更深。例子：渲染 PDF 的那部分代码里，每个元素都要知道默认字号、文本测量接口、是否输出调试信息等；做法是临时构造一个 context，调用渲染入口时传进去，用完就扔。这位读者把它归到封装和"把复杂性往下压"：谁真的需要知道这个 context？能不能把这些细节关在只关心它的子系统里？

## 挂到站点哪里

- 第 7 章"边界与反方"：与已有内容重复为主。已有段落讲了 2022 年读者提出的调用栈作用域式 context、作者的评价，以及本站关于 thread_local 和线程池的提醒。本串可以补的只有两处，都很短：
  - "请求结束要清理，因为线程会被复用"——这是 ThreadLocal 方案在实践中最常见的坑，可并入本站那句 thread_local 提醒，注明是读者经验。
  - Venkat 的 PDF 渲染例子：context 不必是全系统一个，可以是某个子系统一次调用期间的临时对象。站点现有的纪律写的是"每个系统实例一个"，可以加一句"也可以更小：一次操作一个"，并说明这是读者的做法，书里没有。
- 训练场：不需要新题。
