## 读者说了什么（转述）

1. **两本书的建议都依赖语境**（Mahmoud，[2]；Jason Neal，[4]）：系统开发还是应用开发、大团队还是小团队、新写还是维护……不同场景下结论不同，别把任何一本当教条。
2. **"接口简单比实现短小重要得多"**（Artie Shevchenko，[3]）：这是对"深度"之争的一句概括。但这位读者不同意作者说的"什么都起得出名字"——如果既要清楚又要简短，起不出好名字本身就是该不该拆的护栏。同一条还说：在 Google 等公司的生产代码里很少见到 5 行方法，也没见过谁先写测试。
3. **"只做一件事"太含糊**（Artem Zakirullin，[6]）：让五个人按这条原则抽方法会得到五种结果。
4. **批评 TDD 要批评原版**（Eivind Jahren，[7][8]）：Kent Beck 写过 "Canon TDD" 明确什么才算 TDD，其中第 1 步（先列出要测的场景清单）在辩论里没被提到。
5. **替 Martin 补的论据**（Nmhor Kmhor，[10]）：小方法、小类有利于开闭原则和依赖倒置；素数生成器这个例子偏向数值算法，换成"歌曲库"这类需求会不断长出新变体的业务代码，细粒度拆分的好处更明显。这位读者自己说明没读过 APOSD。
6. **最长的一条反方向批评**（Dan Cross，[12]～[14]），要点：
   - 辩论两边都只谈"注释"，更准确的对象是"文档"：文档注释能被工具抽成手册，Rust 的文档测试还会被编译器检查，所以"注释不受编译器检查"并不总成立。
   - `addSongToLibrary(String title, String[] authors, int durationInSeconds)` 的问题不只是缺注释，更是类型太弱：用 `Author`、`Duration` 这样的类型，作者问的"作者字符串有没有格式要求"就不必问了。（引 Alexis King 的 "Parse, don't validate"。）
   - 素数算法应归于 Dijkstra（《Structured Programming》），Knuth 的论文里自己也这么写。
   - 他声称 Martin 的最终版本有实际缺陷：n=1 时数组越界；素数倍数在第 4793 个素数附近溢出 32 位整数；状态放在静态成员里所以线程不安全。还说自己测不出 Martin 所称的性能优势，三个版本差距在 1～2% 内。**这些是读者的说法，引用前要自己验证**（代码在 GitHub 文档里，可以实际跑）。
   - 把 `candidate` 做成类成员再拆成小方法，造成"远距离的隐式作用"：要看懂主循环必须把另外两个方法也读了。他试过改成迭代器式的 `nextPrime()`，结论是状态耦合太紧，拆开得不偿失。
7. 后面两位读者（[15] C#、[16][18] Python）各自重写了素数生成器，思路是"先用一段文字讲清算法，再给不拆散的代码"。
