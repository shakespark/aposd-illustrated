**后半：模块大小与整体复杂性（[10]～[13]）**
1. **两位作者的观点**（Rafael Anschau，[10]）：
   - Pressman《软件工程》：模块少，则每个模块成本高、集成成本低；模块多则相反；存在一个使总成本最小的模块数，但没法预测。
   - Kanat-Alexander《Code Simplicity》：有效的系统整体上必然复杂，唯一的希望是让各个部件保持简单。
   - 由此提问：如果整体"总会复杂"，架构是不是多余的？是不是只该关注部件的简单？这似乎和 Robert Martin 一致，但集成复杂性怎么办？这位读者还注意到书里避开了"高层/低层设计""架构/组件设计"这些常见术语。
2. George-Dee Jempty（[11]）：架构绝对必要，正是为了降低复杂性。
3. Dan Cross（[12]）：对 Kanat-Alexander 和 Martin 都持强烈保留，认为两位都提出很大的主张而缺乏证据；并说没见过 Martin 拿出大量软件作品证明其专长。（人身评价性质，不宜引用。）
4. **Brent Welch**（[13]）：极端都不行——一大堆简单但关系复杂的东西不行，少数几个复杂但关系有限的东西也不行。得把东西用几种方式做几遍，事后才知道哪个好；第一次做总会太复杂。另外：扔掉重来是可以的，周期性地对有限范围重做很有益。这位读者说自己不擅长预测演化，原因有二：需求没完全理解；别人也在改代码。还描述了一个现象：一连串改动单看都"还行"，到某一刻才惊觉不对。

**设计问题（[14]）——这一条是全串的价值所在**

作者先说明没读过 Pressman 和 Kanat-Alexander 的书，然后：

1. **"集成成本 vs 模块成本"是假二分**。这个说法暗含：各模块可以在完全不受其他模块及其接口影响的情况下设计好，然后在"集成阶段"付出让它们协作的代价。作者认为这不符合实际：做一个模块时必须了解它依赖的所有其他模块，依赖多了就直接抬高做这个模块的成本。所以"集成成本"其实已经包含在"模块成本"里。
2. **重新表述大小模块的权衡**：小模块也许比大模块简单，但更多的模块通常带来更多接口，而每个接口都增加系统整体的复杂性。所以是在"单个模块内部的复杂性"与"许多模块累积的接口复杂性"之间权衡。作者加了一个书里没有的判别式：如果能把一个模块拆开而**不增加任何新接口**，那是纯赚——只是大概很难做到。
3. **对"让部件简单就行"的批评**：过于简化，漏掉了关键点——接口给系统增加复杂性，部件越小，接口复杂性（多半）越多。
4. **大系统总会复杂，但不等于认命**：好的设计能降低复杂性；仍然复杂，但比坏设计少得多。
5. **总复杂性不是关键，"表面复杂性"才是**：

   > "What matters is "apparent complexity": how much complexity a developer is faced with at any given point in time."（John Ousterhout，[14]）

   作者接着说，模块化设计的全部意义就是把系统的总复杂性和表面复杂性分开——即使整个系统复杂到没人能全懂，开发者仍能轻松地在单个部件上工作。"apparent complexity" 这个词在书的正文里搜不到（2.1 节的说法是各部分的复杂性按开发者花在上面的时间加权），这里是更直白的表述。
6. **关于术语**：作者说不确定"高层/低层设计""架构/组件设计"确切指什么，猜测前者相当于自己说的接口设计，后者相当于实现 API。并说明一条**写书的规矩**：只有自己大量用过并觉得有用的东西才写进书里；这些术语至今没有影响过作者做设计的方式。

没有回应的：Dan Cross 对两位作者的人身评价；Brent Welch 的"做几遍才知道"（与第 11 章一致，作者未置评）。

## 挂到站点哪里

- 第 4 章"边界与反方"（或 4.4～4.6 正文旁的补充）：
  - "拆小模块的代价是接口"——用作者第 2 点，特别是"能不加接口地拆开就是纯赚"这个判别式。
  - 反方：Pressman 的"最优模块数"曲线、Kanat-Alexander 的"部件简单即可"，以及作者为什么认为前者是假二分、后者过于简化。
- 第 2 章：在复杂性定义处补"表面复杂性 vs 总复杂性"这一说法，说明模块化的目的就是让两者脱钩。
- 第 9 章 / `topics/clean-code.html`：Rafael 把"部件简单"归到 Martin 一边、作者的回答可作为方法长度之争的理论背景。
- 第 11 章：Brent Welch 的"做几遍才知道哪个好""周期性小范围重做"可作读者经验补充。
- 站点"关于本书/版本"处（如有）：一句话——第二版改动集中在少数几章，作者网站提供了新增内容的摘录 PDF（含两处 Clean Code 对比）；第二版因亚马逊关联问题有两个 ISBN。
- 序言或第 1 章旁注：作者"只写自己大量用过且有用的东西"这条规矩，可以解释为什么书里没有很多常见的软件工程术语。
