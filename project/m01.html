背景与对应章节

"日志文件长什么样"这个设计决定，现在有几个类知道？改它要动几个文件？

minikv 把每次修改追加写到一个日志文件，启动时重放。负责这件事的代码是团队里一位同事"按职责拆分"写的：写一个类、读一个类、解析一个类，再加上文件描述符、字节编解码几个小工具类。每个类都很短，单看都挺整洁。

这个任务练的是第 4、5 章的核心判断：模块的价值在于它替使用者藏住了多少东西，而不在于它有多小。做之前请读完 第 4 章 · 模块应该深 和 第 5 章 · 信息隐藏（与泄漏），尤其是原书 4.6（类炎）、5.2～5.4（泄漏与按时间顺序分解）、5.7（默认值与过度暴露）。

任务与约束

  1. 重新划分日志模块，让"记录在磁盘上的格式"只出现在一个源文件里。
  2. 让最常见的用法最简单：Store 打开日志时不应该再接触 open(2) 标志、权限位、起始偏移、errno。
  3. Store 不再自己计算记录大小。
  4. 处理部分写、EINTR 的循环各只保留一份。

约束：

  • make test 必须全绿，不许修改 tests/。测试只通过 Server 的命令接口和重新打开日志文件来检查行为，所以只要外部行为不变，你可以随意重组内部。
  • 日志文件格式保持不变（用基线写出的旧日志，改完的程序要能读）。
  • 只做本任务的事。Store 里那些看着重复的 set/incr/append、一路往下传的 WriteOptions、含糊的成员名，都是后面任务的题目，先别碰，免得改动混在一起没法对照。
  • 更新 README.md 里的文件结构。

自查清单

  • 在 src/ 里搜头部大小（13）和各字段的偏移：它们只出现在一个 .cpp 文件里，而且不在任何头文件里。
  • store.cpp 不再 include 任何与文件格式、fcntl.h、errno（打开文件相关）有关的东西。
  • 新模块的公有接口，你能用 3～5 句话写完注释，而且注释里不需要提"头部""偏移""标志"。
  • 不存在"必须先调 A 再调 B"的调用顺序约束；如果有，它被构造函数或类型系统强制了。
  • 用基线程序写的日志文件，改完后的程序能正常打开（自己用 ./minikv 试一次）。
  • make test 全绿，编译零警告。

提示

卡住了再一条一条打开。

提示 1：先数一数调用者要知道多少东西

把 Store::load() 和 Store::compact() 里所有跟文件打交道的代码列出来，每一行问一句："Store 为什么要知道这个？"你会发现几乎每一行的答案都是"因为下层没替它做"。这份清单就是新模块该藏住的东西。

提示 2：按知识分，不按时间分

写、读、解析三个阶段用的是同一份知识（格式）。书里对按时间顺序分解给的建议是：把共享同一份知识的代码放到一起（原书 5.3 节）。试试一个类同时负责写和读。至于 FileHandle、ByteWriter 这些小类：把它们合进去以后，还有谁需要它们？

提示 3：顺序约束怎么消失

"必须先重放完才能追加"是现在接口里最隐蔽的一条规则。如果打开日志的那个操作本身就包含重放（比如构造时传一个回调，每读出一条记录就交给调用者），这条规则就不需要任何人记住了。压缩时的"写临时文件、rename、重新打开"同理：它们全是文件层面的知识，可以收进同一个模块，对外只露一个"用这些记录整体替换日志"的操作。

参考解法把 5 个类合并成一个 LogFile（solutions/m01/src/log_file.h）。先看 Store 打开日志的代码前后对比：

void Store::load() {
    LogReader reader;
    uint64_t end = 0;
    if (reader.open(path_)) {
        std::string raw;
        while (reader.next(raw)) {
            Record r;
            try {
                r = RecordParser::parse(raw);
            } catch (const std::exception& e) {
                throw std::runtime_error(path_ + ": bad record at offset " +
                    std::to_string(reader.offset() - raw.size()) + ": " + e.what());
            }
            handle(r);
        }
        end = reader.offset();
    } else if (errno != ENOENT) {
        throw std::runtime_error("cannot open " + path_ + ": " + std::strerror(errno));
    }
    if (!writer_.open(path_, O_WRONLY | O_CREAT | O_APPEND, 0644, end)) {
        throw std::runtime_error("cannot open " + path_ + " for writing: " + std::strerror(errno));
    }
}

使用者要知道的东西

改之前，Store 需要知道改之后
记录格式头部 13 字节、记录大小的公式不需要
打开文件3 个 open 标志、权限位、ENOENT 的含义、起始偏移只传路径
调用顺序先 LogReader 读完，再 LogWriter 打开构造即完成
压缩临时文件名、O_TRUNC、fsync、rename、重新打开、新文件大小交出记录即可

日志相关代码从 9 个文件 421 行变成 3 个文件 258 行，store.cpp 从 205 行变成 151 行。行数不是目标，但"浅类合并后总代码变少"很常见：浅类之间的胶水代码（搬偏移、转错误信息、重复的重试循环）随着接口一起消失了。

顺带修掉一个潜在 bug：基线的 compact() 先关写端再 rename，rename 失败后写端已经关了，之后所有写都会失败。rewrite() 先 rename 成功再切换描述符。

代价与取舍

也可以设计成 open(path) + forEach(visit) 两步，更"常规"。但那样"必须先重放再追加"的顺序约束又回到了接口上。参考答案选择让构造一次做完，代价是 Store 的成员声明顺序变得重要（重放时要写 index_，所以 log_ 必须最后声明），代码里为此留了一句注释。这是一个真实的权衡，你选两步式也说得过去，只要把顺序约束写进接口注释。

rewrite 接收"一个接收 sink 的函数"，读起来不如 rewrite(const std::vector<Record>&) 直观。vector 版的代价是压缩时多一份全部数据的内存拷贝。小项目里选 vector 版完全合理；这里选回调，是因为 minikv 本来就把全部数据放在内存里，再翻一倍就太多了。

书中在 5.5 节也提醒过：类变大能改善信息隐藏，但不是越大越好。LogFile 只收了"同一份知识"（文件格式和文件生命周期）相关的代码；内存索引、垃圾统计、压缩时机都留在外面，因为它们用的是另一份知识。

审稿人仍会指出的问题

  • Store 的 set/incr/append/del 仍然各自重复"组记录 → 追加 → 记垃圾 → 更新索引"：这是 m02 的题目。
  • WriteOptions 仍然一层层透传到 LogFile::append：m03。
  • Store::compact() 的注释还在讲实现步骤，total_、dead_ 这样的名字仍然含糊：m07。
  • rewrite() 只保证进程崩溃时旧日志完好；要扛住掉电，rename 之后还得 fsync 所在目录。好在现在加这几行只需要改 log_file.cpp，这正是深模块的回报。
