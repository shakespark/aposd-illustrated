背景与对应章节

如果明天要加一个 DECR 命令，你得改几个类？存储层为什么要知道"整数溢出"这回事？

minikv 的命令是一个一个加上去的：先有 SET/GET/DEL，后来产品要计数器，于是 Store 里多了 incr；又要拼接日志行，于是多了 append；再后来要取子串，多了 getRange。每次都是"给新命令在存储层开一个新方法"，最快、最顺手。

这个任务练的是第 6 章的判断：接口应该反映"这个模块能做什么"，而不是"今天有哪些调用者"。做之前请读完 第 6 章 · 通用的模块更深（尤其是 6.2～6.6 节）和 第 11 章 · 设计两次。本任务的特别之处是：写代码之前，先在本页写下两个截然不同的接口方案并比较。

提示

提示 1：存储层真正要提供什么

把每个命令拆成"读了什么、写了什么"：INCR 读一个值、写一个值；APPEND 读一个值、写一个值；GETRANGE 只读；DEL 只去掉一个键。拆完你会发现，存储层只要支持三件事就能拼出所有命令。剩下的都是"拿到值以后怎么算"，那是命令语言的事。

提示 2：重复的簿记代码收到哪里

启动重放时调用的 handle() 已经在做"把一条记录应用到内存"这件事了。如果写操作先把记录写进日志，再交给同一个函数处理，重放和正常写就不可能算得不一样。可以让它返回记录大小，顺便给统计用。

提示 3：DEL 的错误怎么保留

"去掉一个不存在的键"对存储层来说不必是错误，告诉调用者"原来有没有"就够了（返回 bool）。要不要把它当错误回复给用户，是命令层的决定。行为保持不变即可，至于是否该把这个错误彻底定义掉，留给 m06。

参考答案选 A：minikv 是单线程的，get 和 put 之间不会有人插进来；A 的每个方法一句话就能说清，B 光是把 nullopt 的两种含义和异常语义讲明白就要一段注释。多查一次哈希表的代价可以忽略（m08 会测量 GET 的时间到底花在哪里）。

一旦 minikv 支持多个客户端并发，用 A 实现的 INCR 会丢更新：两个客户端同时读到 5，各自写回 6。那时需要一个在存储层内部原子完成的读-改-写操作，也就是 B。好在参考答案里所有修改都经过一个私有函数，以后补一个 update 并不难。这也是第 11 章的意思：比较过的方案不会白费，它告诉你什么条件下该换。

同一段簿记代码五份；命令规则（整数、溢出、闭区间）在存储层，以异常的形式穿过三层再翻译成回复。

// Makes `value` the value of `key`, replacing any previous value.
void put(const std::string& key, const std::string& value, const WriteOptions& wo);

// Makes sure `key` has no value. Returns true if it had one (and a
// delete was logged), false if there was nothing to remove.
bool erase(const std::string& key, const WriteOptions& wo);

void Store::put(const std::string& key, const std::string& value, const WriteOptions& wo) {
    Record rec;
    rec.type = RecordType::Put;
    rec.key = key;
    rec.value = value;
    writer_.append(rec, wo);
    stats_.add("bytes_written", handle(rec));   // same code path as replay
}

写操作和重放共用 handle()；INCR、APPEND、GETRANGE 在 Server 的处理函数里用 get + put 实现，错误回复直接在那里产生。

数字：store.cpp 205 → 127 行，database.cpp 78 → 63 行，server.cpp 232 → 246 行（命令语义本来就属于这一层）。Store 和 Database 的公有接口一共少了 6 个方法。现在加一个 DECR 或 STRLEN，只改 server.cpp。

代价与取舍

基线的 incr/append/getRange 直接查索引，不计入 keyspace_hits/misses；现在它们通过 get 读值，会被计入。命令回复完全不变，测试也不检查这两个计数。我们认为这样更一致（这三个命令确实读了键），但这是一个外部可见的变化，提交时应该写清楚。

更"通用"的做法是让 Store 只暴露 write(const Record&)，上层自己组记录。那会把日志记录这个实现细节泄漏到 Server，上层反而更难写。书中 6.5 节提醒过：太通用的接口（比如只能一次删一个字符）同样会让今天的使用变难。put/erase 是对上层最顺手的那一级通用。

命令语义集中到了 Server 的处理函数里，handleIncr 变长了。如果命令继续增多，可以把它们挪进单独的 commands.cpp，但不该再沉回存储层。处理函数之间大量重复的参数检查是 m05 的题目。

审稿人仍会指出的问题

  • get 返回 std::pair<bool, std::string>，读的人得猜 .first 是什么：m08。
