# m08 参考答案：先测量，再围绕关键路径改

对应章节：第 18 章（代码应该一目了然）、第 20 章（为性能而设计，尤其 20.2 测量、20.3 关键路径、20.4 的例子）。

查看完整改动：`diff -ru --exclude=build minikv solutions/m08`

## 原来的问题

### 1. 不明显的代码（第 18.2 节）

- `std::pair<bool, std::string> Store::get()`（以及透传它的 `Database::get()`）：调用处写的是 `r.first`、`r.second`，读的人得回头查声明才知道哪个是"找到没有"、哪个是值。
- `bulk(s, true, true)`、`bulk(db_.stats(), false, false)`：两个 bool 参数在调用处完全看不出含义。更糟的是，`bulk(x, false, false)` 其实什么也没做，只是绕了一圈 `ostringstream` 把 `x` 复制了一遍——不读实现根本发现不了。
- **出人意料的副作用**：`Store::exists()` 会把这次查询记成一次 keyspace 命中或未命中。`handleGet()` 先调 `exists()` 再调 `get()`，于是每次 GET 命中被记了**两次**；`EXISTS` 命令也会污染命中率。在基线里执行 `SET a 1`、`GET a`、`STATS`，会看到 `keyspace_hits=2`。名字叫 exists 的函数，读的人不会猜到它在改统计。

### 2. 关键路径慢

基线里一次 GET 命中大约 1.2 µs（见下面的表）。对一个纯内存的哈希表查询来说，这个数字值得问一句"时间都去哪了"。

## 第一步：先测量，不要先猜（第 20.2 节）

这台机器（WSL2）上没有 `perf`，所以用最朴素的办法：把基线复制一份到临时目录，写一个小程序把 `Server` 的私有成员暴露出来，**单独计时**关键路径上的每一段（每段跑 100 万次，取 5 轮里最好的一轮）：

| 环节 | ns / 次 |
|---|---:|
| 完整的 `Server::handle("GET key:N")` | 1130 |
| 切分命令 + 转大写 + 查处理函数表 | 70 |
| `db_.exists(key)`（一次哈希查找 + 一次 `std::map<std::string>` 计数） | 132 |
| `db_.get(key)`（查找 + 两次值拷贝：optional 一次、pair 一次） | 311 |
| 　其中 `Index::get()` 返回 optional 拷贝 / `Index::find()` 只查不拷 | 198 / 87 |
| 　`Stats::add("keyspace_hits")` 一次 | 11 |
| `bulk(value, true, true)`，即 `ostringstream` 逐字符输出 | 665 |
| 　同样的转义，手写拼接（不调用 `isprint`） | 77 |
| `Database::get()` 与 `Store::get()` 比较（透传层的开销） | 311 vs 318，测不出差别 |

几个结论：

1. **一半以上的时间花在格式化回复上。** 一个 100 字节的值，用 `ostringstream` 一个字符一个字符地 `<<`，要 665 ns。直觉上最可疑的"两次查找""值拷贝"加起来也没它多。
2. **透传层在 -O2 下没有可测量的开销。** `Database::get` 直接转发给 `Store::get`，编译器内联掉了。第 20.1 节说浅层会增加开销，这在跨模块、虚函数、跨进程时是真的；但在这里它不是性能问题——它是 m03 要解决的**设计**问题。所以 m08 不动这些层。
3. 其余各项（两次查找、两次拷贝、字符串键的计数器）每项几十到一百多纳秒。

## 第二步：一次改一处，每次都再测

**改 1：回复格式化不用 `ostringstream`。** 只改这一处，GET 命中从约 1216 ns 降到约 540 ns。这一步里还有一个意外：手写版本一开始逐字符调用 `std::isprint()` 再 `out += c`，单独测要 230 ns（含一次内存分配，下同）；改成直接判断 0x20～0x7E 的范围、并把不需要转义的连续字节一次 `append` 进去，降到约 75 ns。所以代码里那段注释写明了为什么不用 `isprint`——这是一个读代码的人会觉得"多此一举"的地方，必须解释。

**改 2：一次查找、不拷贝值、计数器用普通字段。** 用交替运行、绑定 CPU 的方式比较，从约 535 ns 降到约 490 ns，大约 8%，和测量噪声（±30 ns）在一个量级。按第 20.2 节的建议，没有明显收益的优化应该撤回——**除非它让代码更简单**。这几处恰好都是：去掉 pair、去掉重复查找、去掉"exists 改统计"的副作用、拼错计数器名字从运行时的静默错误变成编译错误。所以保留，但我们老实地说：它们主要是为了第 18 章，而不是为了速度。

**剩下的 490 ns 去哪了？** 单独测哈希查找只要约 105 ns，但放进完整路径里，"切分 + 查找"一起要将近 300 ns。原因是缓存未命中：10 万个键、每个值 100 字节，加上 `unordered_map` 的节点，数据量超过了这颗 CPU 16 MB 的 L3；随机访问时每次查找要沿着"桶 → 节点 → 值"连续跳几次内存。单独循环查找时，CPU 能让相邻几次查找的内存访问重叠，所以看起来便宜。这部分已经不是"代码写得浪费"，而是数据结构本身的访存代价；再往下要做的是第 20.3 节说的根本性改动（换成开放寻址、把短值内联进表里），代价是一大块新代码。我们没做，原因见下。

## 结果

测量方法：基线与 m08 的 `make bench` 交替各跑 5 次，用 `taskset` 绑定同一个 CPU 核，取中位数。测量时机器上还有其他编译任务，所以每组数字的波动在 ±5% 左右，交替运行是为了让两边受到同样的干扰。

机器：AMD Ryzen 7 8745H（16 个逻辑核），WSL2（Linux 6.6），g++ 14.2，`-O2`。**你的数字会不同**，看相对变化。

| ns / 命令 | 基线 | m08 | 变化 |
|---|---:|---:|---:|
| GET（命中） | 1216 | 503 | 快 2.4 倍 |
| GET（未命中） | 305 | 314 | 无变化（本来就没有格式化值） |
| SET | 3242 | 3307 | 无变化（主要是 write(2) 和压缩） |

再从整个程序的角度看一次：把 10 万个键装好后，用管道给 `./minikv` 喂 100 万条 GET（输出丢到 /dev/null），总耗时从约 1.98 s 降到约 1.28 s，其中约 0.21 s 是启动时重放日志。折算下来每条 GET 从约 1.77 µs 降到约 1.07 µs，而这 1.07 µs 里有大约 0.6 µs 是 `std::getline` 和 `std::cout`。也就是说，**现在终端 I/O 已经和命令本身一样贵了**，继续压缩 GET 的 490 ns，对真实使用的收益越来越小。这就是我们没有去换哈希表的理由。

## 改了什么

- `Store::get()` / `Database::get()` 换成 `const std::string* find(key)`：找不到返回 `nullptr`，这是 C++ 里读者一眼就懂的约定。接口注释写明指针在下一次写操作前有效。
- `handleGet()` 只查一次：`value ? quoted(*value) : "(nil)"`。
- `bulk(s, bool, bool)` 删掉，换成两个有名字的函数：`quoted(s)` 和 `appendQuoted(out, s)`（KEYS 直接往结果里追加，少一次临时字符串）。STATS 直接返回 `db_.stats()`。
- `Stats` 从 `std::map<std::string, uint64_t>` 换成 4 个普通字段的结构体。
- `exists()` 不再修改统计；命中/未命中只在 `find()` 里各记一次，并写进了 `find()` 的接口注释。
- 不再使用的 `Index::get()`（返回 optional 拷贝）删掉。

`src/` 总行数基本不变（1418 → 1422）：`server.cpp` 多了 19 行（手写转义 + 解释为什么不用 `isprint` 的注释），`stats.h` 少了 7 行。

## 行为变化（测试未改动，全部通过）

- STATS 的 `keyspace_hits` / `keyspace_misses` 现在每次 GET 只记一次，`EXISTS` 不再计入。
- STATS 总是输出全部 4 个计数器（值为 0 也输出），顺序和以前一样按名字排列。基线只输出出现过的计数器。

## 代价与取舍

- **指针的生命周期是一条新的非正式接口。** 返回 `const std::string*` 省掉了拷贝，但调用者必须知道"下一次写之后它可能失效"。这正是第 18 章说的那种需要用注释补偿的不明显之处，所以写进了 `Store::find()` 的接口注释，`Database::find()` 也指回那里。替代方案：返回 `std::optional<std::string>`（安全，但每次多一次拷贝，约 100 ns）；返回 `std::string_view`（和指针一样有生命周期问题，还丢了"不存在"这个状态）；`withValue(key, callback)`（最安全，调用处最别扭）。对一个单线程、只有 `handleGet` 一个调用者的接口，我们选了指针 + 注释。
- **统计仍然藏在 `find()` 里。** 把计数挪到 `handleGet()` 可以让 `find()` 成为纯查询，但那样"命中率"的定义就分散到了命令层。我们保留在 `find()` 里，并在注释中明说。你也可以选另一边，关键是**写出来**。
- **手写转义比 `ostringstream` 多几行，也更容易写错。** 测试里的 `values_are_escaped_in_replies` 正好覆盖了引号、反斜杠和 `\x09`，所以这一步是有保护的。

## 审稿人仍然会指出的问题

- 剩下的 GET 时间主要是哈希表的访存。如果哪天 minikv 变成网络服务、每秒几十万次查询，值得考虑第 20.3 节的根本性改动；现在没有证据表明需要。
- `Database::find()` 仍然是一个纯透传方法，`exists()` 和 `find()` 两个查询接口并存——前者是 m03 的题目，后者可以讨论要不要合并。
- 命令切分、`toUpper` 拷贝、`std::map` 处理函数表还有几十纳秒可省，但 m05 会重写这部分，没必要现在为它增加复杂度。
- SET 的成本几乎全在每条命令一次的 `write(2)` 上（以及摊下来的压缩）。要让写更快，根本的办法是批量提交（group commit），那会改变持久性语义，需要先想清楚。
- 基准只测了进程内的 `Server::handle()`；真实使用里终端 I/O 占了一半，这一点在上面的端到端测量里已经看到了。
