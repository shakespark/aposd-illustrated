# m04 参考答案：把配置参数收回模块内部

对应章节：第 8 章（把复杂性往下拉，尤其 8.2 节"配置参数"、8.3 节"做过头"），以及第 5.9 节（别把使用者真正需要的信息藏起来）。

查看完整改动：`diff -ru --exclude=build minikv solutions/m04`

## 原来的问题

基线的 `Options` 有 5 个字段，`main.cpp` 为它们提供了 5 个命令行参数，README 里有一整节"调参"，`Options::validate()` 专门检查参数组合是否合法，`Database` 的构造函数还要先校验再使用：

```cpp
struct Options {
    double compaction_ratio = 0.5;
    uint64_t compaction_min_bytes = 1 << 20;
    uint32_t compaction_check_interval = 100;
    size_t index_reserve = 1024;
    bool sync_writes = false;
    std::string validate() const;
};
```

每个参数都是一个没做完的决定：写代码的人不确定该怎么选，于是把问题交给使用者。可使用者比写代码的人知道得更少——README 里的建议（"写多读少可以调高，磁盘紧张可以调低"）本身就说明作者也说不清该怎么调。第 8 章的说法是：模块的使用者比开发者多，复杂性应该由开发者承担一次，而不是由每个使用者各承担一次。

## 逐个参数做 8.2 节的检验

检验问题只有一个：**使用者能不能选出一个比模块自己算出来的更好的值？**

| 参数 | 使用者知道得更多吗？ | 处理 |
|---|---|---|
| `compaction_ratio` | 不。它权衡的是磁盘空间和压缩带来的额外写入，这两个量模块在运行时都精确知道（`total`、`dead`），使用者只能猜 | 删掉，改成内部规则：垃圾 ≥ 有效数据时压缩 |
| `compaction_min_bytes` | 不。它防止"小文件反复压缩"，这是实现层面的成本，跟使用者的业务无关 | 删掉，变成内部常量 `kMinGarbageToCompact = 1 MiB` |
| `compaction_check_interval` | 不。它存在的理由是"检查有开销"，可检查只是两次整数比较 | 删掉，每次写都检查 |
| `index_reserve` | 不。`std::unordered_map` 会自己扩容，摊还代价是常数；预留只影响启动时重放的那几次 rehash | 删掉 |
| `sync_writes` | **是。** "回复了 OK 的写在掉电后能不能丢"是业务决定：缓存可以丢，账本不能丢。模块无从得知 | 保留，并把注释写清楚它到底换来了什么、付出了什么 |

最后一行就是书中说的"使用者确实知道得更多"的情形（书里举的例子是请求优先级）。保留一个参数不是失败，关键是每个留下来的参数都要经得起这个检验。

## 改了什么

- `Options` 只剩 `sync_writes`；`options.cpp`（`validate()`）整个删除。
- `Database::maybeCompact()` 用两次比较做决定，不再需要计数器 `writesSinceCheck_`：

```cpp
void Database::maybeCompact() {
    uint64_t garbage = store_.dead();
    uint64_t live = store_.total() - garbage;
    if (garbage >= kMinGarbageToCompact && garbage >= live) store_.compact();
}
```

- `Index` 不再有带 `reserve` 参数的构造函数；`Store`、`Database` 的构造函数不再接收 `Options`。
- `main.cpp` 只认 `--sync`，参数解析从 94 行缩到 66 行；README 的"调参"一节换成"选项"，只讲 `--sync` 换来什么、付出什么，再用两句话说明其余的事情 minikv 自己怎么决定。

整体：`src/` 从 1418 行变成 1346 行，diff 为 +48 / −121 行。测试一行未改，自动压缩的测试（`log_compacts_itself_under_overwrites`）在新规则下照样通过。

## 内部规则是怎么来的

"垃圾 ≥ 有效数据"不是拍脑袋的数字，它有一个可以讲清楚的理由：压缩只重写有效数据，花费约等于 `live` 字节的 I/O，回收 `garbage` 字节。等到 `garbage ≥ live` 再压缩，意味着压缩写出的每个字节至少换回一个字节的垃圾，于是：

- 日志文件最多约为有效数据的 2 倍；
- 压缩造成的额外写入不超过命令本身写入量的 1 倍（总写放大 ≤ 2）。

有意思的是，基线的默认值 `compaction_ratio = 0.5`（垃圾占日志一半）和这条规则其实**完全等价**。也就是说默认值本来就是对的，问题出在把它做成了参数：任何人都可以把它改坏，而改坏的后果（比如把 ratio 和 min_bytes 都设得很小，几乎每次覆盖写都会触发一次全量重写）没有任何地方提醒。

`1 MiB` 的下限仍然是一个决定，只是现在由模块作者来做，并且写在代码注释里：低于 1 MiB 的垃圾，回收它省下的磁盘空间无人在意，却要付出创建文件、fsync、rename 的固定成本。内部常量和配置参数的区别不在于"有没有数字"，而在于**谁对这个数字负责**、改它时要不要每个使用者都重新理解一遍。

`compaction_check_interval` 是另一种常见情形：一个凭直觉加的"优化"顺手变成了参数。检查本身是 O(1) 的，`make bench` 里 SET 的耗时改前改后没有可测的差别（本机约 3.1 µs/op，两边在噪声范围内）。

## 代价与取舍

- **磁盘最坏会用到有效数据的 2 倍左右。** 对磁盘很紧的部署，这可能不可接受。如果真有这样的使用者，他们知道的是"我最多能给 X 字节"，那么该暴露的是一个**磁盘预算**，而不是把 ratio 放回来——参数应该用使用者懂的语言表达。这正是 5.9 节的提醒：确实需要被外界知道的信息不能藏。
- **压缩是同步的。** 触发压缩的那次写会停顿到整个有效数据重写完。数据量大、又在乎尾延迟的使用者可能希望控制"什么时候压缩"（比如只在低峰期）。好的回应仍然不是 ratio 参数，而是把压缩挪到后台线程，或者提供一个"现在别压缩"的开关。本任务没有做，因为 minikv 目前没有这样的使用者。
- **不要把它推得太远（8.3 节）。** `sync_writes` 看起来也能"自动决定"（比如根据写入频率），但那等于替使用者做一个关于数据安全的业务决定，而且一旦猜错就是丢数据。往下拉的复杂性必须和模块本来的职责紧密相关；"这份数据值不值得等磁盘"不属于键值存储能知道的事。
