## 原来的问题

### 1. 本可以不存在的错误（第 10.3、10.5 节）

- `DEL` 一个不存在的 key 回复 `ERR no such key`。可是调用 DEL 的人想要的是"这个 key 别存在了"，key 本来就不在，目标已经达成。报错只会逼每个调用者写"先 EXISTS 再 DEL"或者"忽略这个特定错误"的代码。书中 10.3 节讲作者自己语言里的一个删除命令，犯的是同一个错误。
- `GETRANGE` 对越界、`start > end`、负数下标、key 不存在全都报错。调用者想取"前 100 个字符"时，必须先 `GET` 一次知道长度再自己截断。10.5 节讨论的取子串方法是同类例子。

这两个错误在 `Store` 里以 `KeyNotFound`、`std::out_of_range` 的形式抛出，再由 `Server` 一路翻译成错误回复——为一个本不需要的错误，写了两层代码。

### 2. 每个处理函数各自 catch（第 10.7 节）

基线 `server.cpp` 里有 16 个 `catch`。几乎每个 handler 都套着同一段 `try { … } catch (const std::exception& e) { return "ERR " + e.what(); }`，`handleIncr` 还分别 catch 了 `invalid_argument`、`overflow_error`、`exception`，三个分支做的事一模一样。

更糟的是这种写法**不区分错误的性质**。`INCR` 一个非数字值，是这个请求的问题，回一句 ERR 就好；写日志失败（磁盘满、I/O 错误）是 minikv 自己出了问题，基线也只是回一句 `ERR log write failed` 然后继续接受写入——而此时日志末尾可能已经留下半条记录，后面新写的记录会把它"埋"在文件中间，下次启动就从"尾部残缺"变成了"中间损坏"。

### 3. 崩溃留下的残缺尾部让程序起不来（第 10.6 节）

`append` 写到一半进程被杀，日志最后一条记录不完整。这是追加写日志**必然会遇到**的正常情况，基线却把它当成损坏：`LogReader` 抛异常，`main` 打印一行错误退出。用户只能自己去研究文件格式、手工截断。

### 4. 真正的损坏处理得含糊（第 10.8 节）

日志中间某条记录 checksum 不对，基线同样是抛 `runtime_error`、由 `main` 打印 `minikv: …: bad record at offset N: checksum mismatch` 后退出。退出本身没错，但信息不够：用户不知道这和"崩溃留下的尾部"有什么区别，也不知道该怎么办。

## 改了什么

| | 改之前 | 改之后 |
|---|---|---|
| `DEL` 不存在的 key | `ERR no such key` | `(integer) 0`，不写日志 |
| `GETRANGE` 越界 / 反向 / 负数 | `ERR index out of range` | 截断到值的范围；负数从末尾数；空范围返回 `""` |
| `GETRANGE` 不存在的 key | `ERR no such key` | `""` |
| 请求级错误（INCR 非整数、溢出） | 每个 handler 自己 catch | `Store` 抛 `RequestError`，`Server::handle` 里唯一的 catch 转成 ERR |
| 系统级错误（写日志失败） | 回 ERR，继续服务 | 不在请求级捕获，传到 `main`，进程退出 |
| 最后一条记录不完整 / checksum 错 | 启动失败 | 截掉这条记录，stderr 警告，正常启动 |
| 更前面的记录损坏 | 抛异常，`main` 打印后退出 | 打印位置、原因和处理办法后 `abort()` |

要点：

- **定义掉**：`Store::del` 改为返回 `bool`（"原来在不在"），`Store::getRange` 不再有任何失败路径。`KeyNotFound` 这个异常类整个消失了。
- **聚合**：新增 `src/request_error.h`，只有一个类 `RequestError`，它的注释写清了"哪些错误该回 ERR、哪些不该"。`server.cpp` 的 `catch` 从 16 个降到 3 个：`Server::handle` 里 1 个，另外 2 个是解析整数参数时把 `std::stoll` 的异常就地翻译成错误回复（这两段重复的解析代码是 m05 的题目，这里没动）。`server.cpp` 从 232 行变成 194 行。
- **屏蔽**：`LogReader` 用新的异常类型 `TruncatedRecord` 区分"文件在记录中间结束"和其他读错误；`Store::load()`（重放循环是整个系统里唯一看得到整份日志的地方）据此截断残缺尾部。上层的 `Database`、`Server`、`main` 和测试都不知道这件事发生过，只会在 stderr 看到一行警告。
- **崩溃**：`store.cpp` 里的 `fatal()` 打印诊断信息后 `std::abort()`。信息里写了文件、偏移、原因、为什么判断它不是写到一半，以及两种处理办法（从备份恢复，或截断到该偏移）。

`store.cpp` 从 205 行变成 263 行：重放多了对两种损坏的区分。复杂性往下拉到了一个地方，换来的是上面每一层都不用处理这些情况。

## 怎么区分"写到一半"和"损坏"

`append` 用一次 `write(2)` 写出整条记录，所以写到一半留下的一定是**最后一条记录的前缀**。由此：

1. 头部或记录体读到一半就到了文件末尾 → 写到一半。
2. 最后一条记录长度完整但 checksum 不对 → 也按写到一半处理。掉电时文件长度可能已经更新，数据块却还没落盘。
3. 其他任何位置出问题 → 不可能是写到一半，是损坏。

第 2 条有代价：如果日志里**恰好只有最后一条**记录被磁盘弄坏了，我们会把它当残缺尾部丢掉，而不是崩溃。这条记录本来也读不回来了，所以损失相同；区别只在于用户看到的是警告而不是致命错误。警告里写了丢掉的字节数和偏移。

## 什么时候崩溃是**不**可以的

`abort()` 对 minikv 这样的单进程命令行工具是合理的：日志中间坏了，任何"继续运行"的做法都意味着带着一个不知道有多大的数据缺口对外服务，比停下来更危险。但这个判断依赖使用场景（书中 10.8 节也说取决于应用）：

- **做成库，嵌在别人的进程里**：库调用 `abort()` 会把宿主程序一起带走。那时应该改成抛出一个明确的"日志损坏"异常（或返回错误码），让宿主决定是退出、换一个数据目录，还是只读打开。
- **有副本的存储服务**：坏了一份数据是可以从副本恢复的，恢复正是这种系统存在的意义。崩溃会把可恢复的故障变成停机。
- **"写日志失败就退出"同理**：对单机工具，退出并在重启时按残缺尾部处理，是最简单且正确的恢复路径（书里叫错误提升，把小错误变成一个已有恢复路径的大错误）。对需要高可用的服务，可能要切换到只读模式或拒绝写入，而不是退出。

## 做过头的风险（第 10.9 节）

- 屏蔽只适用于**上层不需要知道**的情况。残缺尾部丢的最多是崩溃前最后一次写，这次写本来也没有向客户端确认成功（或确认后马上崩溃），丢掉它与"崩溃发生得早一点"等价。如果丢掉的是更早的、已经确认过的数据，就绝不能悄悄屏蔽——所以中间损坏必须崩溃，而不是"跳过坏记录继续"。
- 现在的格式**没有单独校验头部**。如果中间某条记录的长度字段被磁盘翻了位，算出来的记录可能"越过文件末尾"，看起来就像残缺尾部，结果会把它后面的好数据一起截掉。在不改格式的前提下我们分辨不了这两种情况。真正的修复属于文件格式：给头部加一个独立的 checksum。在那之前，警告里打出被丢弃的字节数是一道保险：写到一半最多丢一条记录，如果警告说丢了几 MB，运维应该立刻警觉。
- `DEL` 和 `GETRANGE` 定义掉错误后，个别调用者如果**确实**想知道"key 原来在不在"，仍然有办法：DEL 的返回值是 0 还是 1；GETRANGE 前可以 `EXISTS`。少数人需要的信息换个途径提供，而不是逼所有人处理错误。

## 审稿人仍然会指出的问题

- 两处解析整数参数的代码仍然各自 try/catch `std::stoll`，而且严格程度不一致（INCR 拒绝 `12abc`，GETRANGE 接受）：这是重复带来的问题，见 m05。
- 参数个数不对、key 太长这类错误仍然在每个 handler 里各写一遍并直接 `return "ERR …"`。可以统一改成抛 `RequestError`，但那属于 m05 的"消除重复"。
- 日志格式知识仍散落在 `LogReader`、`RecordParser`、`Store` 里（m01）；把残缺尾部的判断放进 m01 的 `LogFile` 里会更自然。
- `Store` 的成员名 `total_`、`dead_` 仍然含糊（m07）。
