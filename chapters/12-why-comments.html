读前：这一章要回答什么

如果代码写得足够好，还需要注释吗？如果需要，注释承担的是哪一部分代码承担不了的工作？

这一章开启了全书的第四部分：注释与命名（第 12～15 章，第 16 章讲注释的维护）。它是一篇"辩护词"：作者逐一反驳开发者不写注释时最常用的四个借口，然后说明好注释能带来什么。具体怎么写，留给第 13 章。

如果你认真读了第 4 章，这一章的核心论证其实已经埋好了伏笔：接口分正式部分（签名）和非正式部分（行为、约束、副作用），而非正式部分只能用注释写。作者在这里把这条线索推到结论：没有注释，就没有抽象。注释不是锦上添花的文档工作，而是模块设计的一部分。

  1. 12.1 节的后半段有一个只含两个参数的取子串函数的例子。读之前先想一想：只给你这个函数的声明，你有几件事不能确定？
  2. 12.2 节有一段很简单的算术（敲代码占开发时间的比例）。用你自己最近一周的工作估一下这个比例，看作者的结论在你身上是否成立。
  3. 12.6 节作者和 Clean Code 唱反调。留意作者同意对方的那半句话：好的设计能减少哪一类注释？

核心观点

注释是抽象的组成部分

没有注释，一个方法唯一的抽象就是它的声明；声明缺少太多关键信息。使用者如果必须读实现才能用，就根本没有抽象。

"读代码就行"会制造浅方法

如果指望使用者读实现，你会尽量把方法切短，结果是一堆浅方法；而且读者照样要理解被调用的那些方法。

代价不大

敲代码通常只占开发时间的一小部分（作者估计不超过 10%），即使注释敲得和代码一样多，总时间也只多出约 10%。

过期是可以管理的

代码大改时文档才需要大改，而改代码本身更费时间。避免重复、让文档贴近代码、靠代码审查发现过期注释。

"注释都没用"是最有道理的借口

大多数现存注释确实质量平平。但这是能学会解决的问题，第 13 章开始给方法。

好注释治什么病

它减轻认知负担和未知的未知，讲清依赖、消除模糊性。它不能减少变更放大，那是设计的事。

注释不是失败

注释和代码承载的是不同的信息，各有所长。好的设计能减少注释，特别是方法体内的注释，但不能取代它们。

心智模型：设计者脑子里的信息去哪了

写代码时，你脑子里装着大量信息：这个函数在什么情况下被调用、返回 0 代表什么、为什么这里要多判断一次、那个奇怪的常量从哪来。代码只能装下其中一部分。剩下的，要么写进注释，要么随着你忘记而消失，后来的人只能重新推导或者猜。

注意第三条路里有"几周后的你"。作者特别指出，即使是原作者自己，离开一段代码几周后也会忘掉很多设计细节。

一个原创例子：声明到底缺了什么

书中 12.1 节用一个只有起止两个参数的取子串函数说明：光看声明，你连"终点含不含"都不知道。下面是一个后端开发里常见的、同样性质的例子：分布式锁的客户端接口。

class LockClient {
public:
    bool tryLock(const std::string& name, std::chrono::seconds ttl);
    void unlock(const std::string& name);
};

名字起得不差，类型也清楚。可是调用者想正确使用它，还有一串问题没有答案：tryLock 拿不到锁时是立即返回还是等待？返回 false 是"别人持有"还是"网络出错"？ttl 到期后锁会自动释放吗？到期前需要续约吗？同一个进程对同一个 name 再调一次会怎样？unlock 一个已经过期、被别人拿走的锁会怎样？

// 基于协调服务的分布式互斥锁客户端。每个 name 是一把独立的锁；
// 同一时刻全集群最多一个持有者。线程安全。
class LockClient {
public:
    // 尝试获取锁，不等待：已被持有时立即返回 false。
    // 成功后锁最多保持 ttl；到期自动释放，期间进程崩溃也一样。
    // 需要更久时，在到期前再调用一次 tryLock 续期（自己已持有时返回 true）。
    // 与协调服务通信失败时抛 LockServiceError，而不是返回 false。
    bool tryLock(const std::string& name, std::chrono::seconds ttl);

    // 释放锁。如果锁已经过期、或已被别人持有，什么也不做。
    void unlock(const std::string& name);
};

加上注释后，声明才变成一个可用的抽象：调用者不用读实现，也不用去翻协调服务的协议，就知道怎么用、出错时会怎样。实现里怎么续约、怎么和协调服务通信，一个字也没写，它们仍然被藏着。

换一个角度看：如果没有这些注释，每个使用者都得去读实现、甚至读协调服务的文档，才能回答上面那串问题。那么 LockClient 就算接口再短，也没有替任何人隐藏复杂性，第 4 章意义上的"深"也就无从谈起。

边界与反方

作者并不是说"注释越多越好"。书中明确同意：选好名字、做好设计，确实能减少对注释的需要，特别是方法体内部的注释。作者反对的是把这推到极端，认为好代码完全不需要注释。第 13 章还会说，很多短方法根本不需要实现注释；而重复代码的注释是红旗。所以正确的读法是：注释的重心在接口，不在逐行解释。

Robert Martin 在 Clean Code 里把注释看作"未能用代码表达自己"的补偿：

Comments are always failures.— 第 12.6 节（作者引用的 Clean Code 原话）

Martin 的替代方案是把代码块抽成方法、用方法名代替注释。作者认为这会产生又长又晦涩的名字，信息量反而不如一条好注释，而且每次调用都等于把"文档"重新敲一遍；更担心的是文化上的副作用：写注释的人会被质疑"你的代码有什么问题才需要注释"。两人后来有过一次公开的长篇讨论，本站的专题：APOSD 与 Clean Code 对这场分歧有完整对照。

12.2 节的"不超过 10%"是作者基于两个假设的估算：敲代码不超过开发时间的 10%，注释最多和代码一样多。本站补充：真正的代价往往不在敲字，而在想清楚要写什么：写不出一句简洁的接口注释，常常说明你还没想清楚这个接口。这部分时间算不算"写注释的成本"？第 15 章的回答是：它本来就是设计工作，提前做甚至可能更省。

作者对"注释会过期"的回应比较乐观。本站补充一个现实的提醒：一条错误的注释会误导读者，危害可能大于没有注释。所以这个借口的正确结论不是"不写"，而是认真对待注释的位置和粒度：接口注释紧贴声明、同一件事只写一处、代码审查时把注释当代码一样审。这些正是第 16 章的内容。

有人认为现在可以让 AI 读代码、替你解释，注释不那么重要了。作者本人在一次访谈里谈过这个问题，承认 AI 工具在一定程度上能弥补注释的缺失，但认为如果原作者当初花一点时间写注释，会比事后让 AI 去猜容易得多。见专题：AI 时代读这本书。

以下不在书里，来自书中给出的读者讨论组。2023 年有读者反对本章"接口的非形式部分只能用注释描述"这句话：一个名字起得好的单元测试既说明了行为、给了例子，又能在行为被改动时自动报警，至少对团队内部的接口，它比注释强。

Ousterhout 的回应分两步（2023-12）。先是把书里的说法放宽了一点：也许有注释以外的方式来描述接口，但它必须完整、好找、好懂，而测试既不好找也不好懂。被另一位读者追问后又让了一步：好的单元测试对接口的刻画可能比文字注释更精确（尤其是各种边界情况）；问题是它难读得多，读的人还得先弄懂测试框架和各种模拟设施，所以使用者从一段文字说明里拿到所需信息通常更快。Ousterhout 把"用测试当文档"和"用形式化规约描述接口"归为一类：更精确，但实际用起来困难得多。同一帖里还收回了自己前一条里"很多测试只测实现不测接口"的说法，承认措辞草率。

没有人接的一点是那位读者的另一半论据：测试不会悄悄过时，注释会。这正对着本章"注释会过时"那个借口，值得你自己想一想：精确且不过时，和好找且好读，你的团队更缺哪一个？两者并不互斥，边界情况多的接口，注释写规则、测试列例子，是常见的搭配。

自测题

作者说"注释是抽象的基础"，最核心的理由是什么？
抽象的意义在于"只看接口就能用"。声明只有名字和类型，表达不了结果的含义、边界、约束。注释补全这些信息，抽象才完整。注意 C 恰好说反了：作者承认自然语言不如代码精确，但表达力更强，能写出简单直观的描述。
按书中 12.1 节，"想知道方法做什么就去读代码"这种做法会导致什么？
指望读者读实现，就会想办法让每个方法都短到好读，于是拆出很多浅方法。这不仅没有减少阅读量（要理解顶层方法，还得理解嵌套调用的那些方法），还违背了第 4 章的"模块应该深"。
四个借口里，作者认为哪一个"最有道理"？
作者承认，几乎每个开发者都见过毫无信息量的注释，大多数现存文档质量也一般。但作者认为这是可以解决的：写好注释不难，学会方法就行。第 13 章就是这套方法。
关于 12.2 节"没时间写注释"的反驳，下列说法哪个最准确？
项目永远有时间压力，永远有看起来更紧急的事，所以"以后再写"的结果就是不写。作者用投资心态（第 3 章）回应：先投入一点，长期获得更高效率；而且类和方法的接口注释在设计阶段就能立刻回本（第 15 章）。
作者对 Clean Code"注释是失败"观点的回应，哪一项不符合原书？
B 正是作者反对的立场。作者认为注释提供的信息和代码不同，目前无法用代码表达；即使能，也不见得更好。D 是作者明确同意的部分，A 和 C 是反驳理由。
一个模块的接口注释写得很好，但同一个设计决定分散在五个模块里。修改它时，这些注释主要能帮上什么忙？
作者在 12.5 节说，好文档帮助的是认知负担和未知的未知，不包括变更放大。要减少需要修改的地方，得靠设计（例如消除信息泄漏）。

小结与读后一句话

  • 注释保存设计者脑中、代码装不下的信息：接口的非正式部分、结果含义、设计理由、调用条件。
  • 没有注释就没有抽象：使用者必须读实现时，复杂性就完全暴露了。
  • 四个借口：自解释代码（不成立）、没时间（约 10% 的投资）、会过期（可管理）、都没用（最有道理，但可以解决）。
  • 好注释减轻认知负担和未知的未知，讲清依赖、消除模糊性；它不减少变更放大。
  • 作者同意好设计能减少注释（尤其方法体内的），但不同意"注释是失败"。

第 13 章回答这一章留下的问题：什么样的注释才不是"没用的注释"？答案的核心是一句话：注释应该描述代码里看不出来的东西。
